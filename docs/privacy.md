# What's in the repo about you (and what isn't)

> If you forked this or are auditing it, here's exactly what becomes public when you push, what stays on your machine, and what only lives in cloud-managed vaults.

## What IS public after you push

Anything committed to git is public the moment you push. This repo deliberately keeps the public surface small.

| What | Where | Why it's okay |
|---|---|---|
| **Your full name** | [site.config.ts](../site.config.ts) `ownerName` | Rendered into the footer, page metadata and structured data; the entire point of a personal portfolio is to attribute it to you. |
| **Your apex domain** | [site.config.ts](../site.config.ts) `domain` | Public anyway, anyone can `whois` it. |
| **Your GitHub username** | [infra/main.parameters.json](../infra/main.parameters.json) `githubOwner` | Already public on the GitHub profile that owns the repo. |
| **The Azure region** | [infra/main.parameters.json](../infra/main.parameters.json) `location` | Not sensitive. |
| **The storage account hostname** | [site.config.ts](../site.config.ts) `blobHost` (after first deploy) | Public-by-design, the lightbox uses it to fetch full-res images. |
| **Your iNaturalist username** | `userId` in [src/content/hobbies/](../src/content/hobbies/) | The hobby pages link to your public observations by design. They show them at town or region level, on a grid of about 11 km, never at the spot ([security.md](security.md#photo-locations)). |
| **Hobby records** | [src/lib/hobbies/](../src/lib/hobbies/) and [src/content/hobbies/](../src/content/hobbies/) | Fish you've caught by named water, birds you've seen, the waters and parks you visit. Named public places only, never coordinates of a spot. |
| **Commit metadata** | Every commit's author name and email | Public on GitHub forever. Commit with your GitHub noreply address, see [security.md](security.md#secret-hygiene). |

Nothing else about you is committed: **no address, no phone, no subscription/tenant IDs, no keys.**

## What is in this repo about *the project* (not you)

Open source code, design decisions, architecture diagrams. Anyone reading the repo can:
- Reproduce the architecture
- See what Azure services we provision
- Read every workflow YAML
- See the security headers
- See cost estimates

None of that is sensitive, it's documentation by design.

## What is gitignored (lives on your machine only)

| What | Where | Why hidden |
|---|---|---|
| **WHOIS contact info** | `~/.config/photography-website/contact.json` (deliberately outside the repo) | Your real name, address, phone, email. Used once during `az appservice domain create`. Even if you accidentally put it in the repo, [.gitignore](../.gitignore) lines `contact.json` and `contact.*.json` would block it. |
| **Photos themselves** | `src/content/sessions/<slug>/images/*` | 2,400 px build copies the prebuild gets from Blob; never committed. |
| **Per-session sidecar JSON** | `src/content/sessions/*.json` | Same, regenerated every build from `_session.json` in Blob. |
| **Built site** | `dist/` | Regenerated by `npm run build`. |
| **Astro type cache** | `.astro/` | Tooling artifact. |
| **Local prebuild cache** | `.cache/` | Build copies of the photos, keyed by ETag. |
| **`node_modules/`** | top-level | npm install output. |
| **`.env*`** | anywhere | Gitignored. Read locally by helper scripts (e.g. `scripts/upload-session.sh` uses it to pick the Azure tenant/account for uploads). Never committed. |
| **Local credentials** | `local.settings.json`, `*.pem`, `*.key`, `*.pfx`, `*.p12` | Gitignored, so an Azure Functions settings file or a certificate can't be committed by accident. |

## What lives in **GitHub Actions secrets** (vault, never in code)

These are real secrets. They're set in **GitHub → Settings → Secrets and variables → Actions**, never in a file.

| Secret | Sensitive? | Source |
|---|---|---|
| `AZURE_CLIENT_ID` | Identifier only | Output of `scripts/setup-federated-credential.sh` |
| `AZURE_TENANT_ID` | Identifier only | Same |
| `AZURE_SUBSCRIPTION_ID` | Identifier only | Your Azure subscription |
| `AZURE_STATIC_WEB_APPS_API_TOKEN` | **Yes, real secret** | Bicep deploy output (`scripts/bootstrap-swa-token.sh` writes it) |
| `AZURE_STORAGE_ACCOUNT` | Identifier only | Bicep deploy output |
| `GH_PAT_FOR_SECRETS` (optional) | **Yes, real secret** | A fine-grained PAT you create manually |
| `IG_ACCESS_TOKEN` (optional) | **Yes, real secret** | Instagram token for [social posting](social.md) |
| `SOCIAL_SECRET_KEY` (optional) | **Yes, real secret** | Random key that seals the refreshed Instagram token in Blob |
| `IG_USER_ID` (optional) | Identifies the Instagram account | Only with Facebook Login; kept secret so it's masked in logs |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` (optional) | **Yes, real secret** | Vision model for [photo captions](photos.md), only when not using keyless Azure OpenAI |

The three "identifier only" Azure IDs are technically not secrets in Microsoft's threat model, knowing them doesn't grant access. They're stored as secrets out of tidiness.

Additional runtime settings live in **Azure SWA app settings**, not GitHub:

- `AZURE_STORAGE_CONNECTION_STRING`, a real storage-account credential written by the Infra workflow.
- `ANALYTICS_SALT`, a derived secret used for one-way visitor/rate-limit hashes.
- `ADMIN_GITHUB_USERS`, a non-secret comma-separated allowlist.
- `GITHUB_TOKEN`, an optional fine-grained PAT for the admin rebuild button. The optional Instagram timer (a Logic App) reads the same token when it's deployed and keeps it as a secure parameter, hidden from its run history.

The true credentials with meaningful blast radius are:
- The SWA deploy token (rotated by re-running the Bicep deploy)
- The storage connection string (rotate the storage keys, then re-run Infra)
- Optional fine-grained GitHub PATs (you decide whether to create them)

## Social posting (optional)

If you turn on [social posting](social.md), nothing in this repository or its public Actions logs says which Instagram account it posts to:

- the token and account id are GitHub secrets, which are masked in logs
- each photo's record, the posting plan and history live in the private `metadata` container
- images reach Meta through links that expire after two hours, and are deleted after posting
- the workflows log counts only, through a redactor that strips tokens, ids and signed URLs
- the facts in posts come from Wikipedia's public API. Its requests name your site's domain, as Wikimedia's etiquette asks, and never the Instagram account

The workflow runs themselves are visible, so someone reading the repo can tell the feature is in use, but not where. The photographs are the same ones on the site, so a reverse image search could still connect the two, and your Instagram bio links to the site by design. Nothing links the other way.

Checked in October 2026, after posting went live: the tracked files, the full git history including commit messages, and the logs of every workflow run since the feature was added contain no account name, Meta app name, access token or signed link. The only identifiers in the logs are ones that grant nothing on their own: the storage account (already public in `blobHost`) and the Azure OpenAI endpoint hostname, which the logs print because it's a repository variable and which only accepts your Azure sign-in.

To repeat that check on your own copy, search for your handle and app name, and for token shapes:

```bash
git grep -niE 'your_handle|your-app-name'                      # files today
git log --all -p | grep -iE 'your_handle|your-app-name'         # every commit ever
git log --all -p | grep -E 'IGAA[A-Za-z0-9_-]{20,}|EAA[A-Za-z0-9]{30,}|github_pat_|AccountKey='
gh run list --limit 100 --json databaseId --jq '.[].databaseId' |
  xargs -I{} sh -c 'gh run view {} --log | grep -iE "your_handle|your-app-name|IGAA"'
git log --all --format='%ae %ce' | sort -u                     # every email commits were signed with
node scripts/location.mjs blobs                                 # public photos that still record a position (az login first;
                                                                # or Actions → Photo locations → Run workflow)
```

## What lives in **Azure** (not in this repo, not in GitHub)

| Thing | Where |
|---|---|
| Your domain registration's WHOIS record | Azure's registrar partner (GoDaddy under the hood). Privacy protection on by default → your real address is hidden from public WHOIS lookups but still on file with the registrar. |
| The bootstrap managed identity's principal ID | Azure RBAC tables. |
| Your actual photos | The `originals` + `derivatives` containers in Blob Storage. **Anyone who knows the URL can read individual blobs.** The container itself cannot be listed by anonymous users, there's no directory index, so URLs cannot be enumerated. Every photo is stripped of its GPS position before it's readable, so a photo taken at home doesn't carry the address ([security.md](security.md#photo-locations)). |
| Site analytics (pageviews) | Custom privacy-friendly pipeline → `pageviews` table in Table Storage. No IP and no cookies stored; unique visitors counted via a daily-rotating salted hash. See [docs/analytics.md](analytics.md). |
| Contact form submissions | `contactmessages` table in Table Storage (the name, email, and message a sender chose to send you). Rate limiting uses a separate `contactratelimit` table that stores only a salted hash of the sender's IP plus a count, never the raw IP. |
| Session descriptions and image captions | `_session.json` in the private-to-listing `originals` container. They become public text on the next site build because they describe public photographs. |
| What the photo pipeline knows about each photo | `metadata/photos/` in the private container: the model's notes on each frame, its iNaturalist match, and what was last written. Captions only ever use place names you wrote yourself, never an iNaturalist observation's place, which can be a street address. See [docs/photos.md](photos.md). |

## What is published to **the public website**

| What | Where |
|---|---|
| Your name (footer, meta tags, structured data) | Every page |
| Every photo you upload, minus its GPS position | The relevant gallery page + as a lightbox URL pointing at Blob |
| Each photo's camera, lens and exposure settings, and its caption | Under the photo in the lightbox, and in the page's structured data |
| Roughly where each session was | A globe pin from a hand-kept table of public places, never a photo's GPS ([src/lib/geo.ts](../src/lib/geo.ts)) |
| Your iNaturalist observations | Hobby pages, at town or region level and on an ~11 km grid |
| The video of your tank, and so your YouTube channel | The aquarium page plays it in YouTube's privacy-enhanced player and links to it on YouTube (`video` in [aquarium-keeping.json](../src/content/hobbies/aquarium-keeping.json)) |
| What the site keeps about visitors, in plain words | `/privacy/` ([src/pages/privacy.astro](../src/pages/privacy.astro)), linked from the footer and under the contact form's Send button. Update it, and its "Last updated" date, whenever the contact form, analytics, browser storage or the outside hosts a page loads from change |
| The site's full set of pages | Indexable by search engines (`robots.txt` allows it) |

## Specifically NOT collected, exposed, or stored

- No photo locations. GPS is removed from every photo before it's public, and nothing on the site derives a position from one.
- No visitor IP addresses are stored. The analytics endpoint uses the IP only to compute a daily-salted hash for unique-visitor counting, then discards it; the raw IP is never persisted.
- No visitor cookies (analytics uses an ephemeral `sessionStorage` id only, cleared when the tab closes).
- No visitor accounts. The site owner's `/admin` access uses SWA GitHub OAuth and a server-side allowlist.
- No third-party analytics scripts: analytics is self-hosted in your own Azure Table Storage, and nothing leaves your tenant.
- No third-party ad networks. The one outside player, the YouTube video on the aquarium page, uses YouTube's privacy-enhanced mode, where views don't personalize ads or recommendations, and it loads only when a visitor scrolls to it.
- No payment info.

## TL;DR

**Public:** your name, your domain, your GitHub and iNaturalist usernames, your storage hostname, your photos (without their GPS), and whatever email your commits are signed with.
**Private (lives only on your machine):** your address, phone, email.
**Private (lives only in GitHub vault):** the SWA deploy token.
**Private (lives only in Azure):** contact messages, analytics rows, runtime credentials, and private metadata. Individual public photo URLs are intentionally readable when known, but their containers are not anonymously listable.

If you ever change your mind about your name being visible, edit [site.config.ts](../site.config.ts), it's a one-line change → commit → next build redeploys with the new value.

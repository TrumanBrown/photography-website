# Image pipeline: how a photo gets from your camera to the live site

> Audience: anyone uploading photos. Read this once to understand what happens when you drop a folder in Blob.

## The end-to-end path

```
   You                Azure Blob              GitHub Actions          Visitor's browser
    │                     │                         │                         │
    │  upload folder ──►  │ incoming/ (private)     │                         │
    │                     │                         │                         │
    │                     │ ◄── publish: remove GPS,│                         │
    │                     │     move to originals/ ─│                         │
    │                     │                         │                         │
    │                     │ ◄── list blobs ──────── │                         │
    │                     │                         │                         │
    │                     │ ◄── download copies ────│                         │
    │                     │                         │                         │
    │                     │ ◄── (if RAW) upload ── │                         │
    │                     │      JPEG sidecar       │                         │
    │                     │                         │                         │
    │                     │                         │── astro build ──►       │
    │                     │                         │   creates dist/         │
    │                     │                         │                         │
    │                     │ ◄── upload variants ───│                         │
    │                     │                         │── deploy small app ──►  │
    │                     │                         │                         │
    │                     │ ◄────────────────── direct image URL (lightbox) ──│
    │                     │                                                   │
    │                     │ ◄── responsive variants + admin thumbs ─────────│
```

Two paths to the visitor:
- **Responsive variants** are generated by Astro, uploaded to `variants/`, and referenced directly from Blob. Keeping them out of the SWA artifact avoids its app-size cap.
- **Full-resolution originals** (exactly the image you uploaded; only a GPS position is ever removed) stay in Blob and load only when a photograph is opened in the lightbox, and only for the one actually on screen — see [Viewing: full resolution without the wait](#viewing-full-resolution-without-the-wait). The lightbox has a **download button** that saves the original file (fetched cross-origin from Blob, allowed by the storage account's CORS rules and the site's `connect-src` CSP).

## Step 1: you upload

### Tools

- **`./scripts/upload-session.sh`** (recommended): uploads one or more folders or zips from `staging/` to the private `incoming` container, flattens iCloud folders, checks the folder name for misspelled places, and can start a build. The build removes any GPS position and publishes the photos to `originals` (step 2). See [staging/README.md](../staging/README.md).
- **Azure Storage Explorer** (free desktop app from Microsoft, GUI), or **`az storage blob upload-batch`** (CLI). Upload to `incoming/originals/<session>/` for the same result. Uploading straight to `originals` works too, but a photo is then public by exact URL until the next build removes its location.
- (Future) **admin upload UI on the site itself**: not built yet; see [architecture.md](architecture.md).

### Folder convention

Each top-level prefix in the `originals` container is one session (uploads arrive as `incoming/originals/<session>/...` and keep the same layout). (Azure Blob doesn't actually have folders, it uses "prefixes" in blob names, e.g. `2025-china-trip/IMG_0001.jpg`. Same thing visually in any GUI.)

Prefix names are lowercased and URL-sanitized for `/sessions/<slug>`. Every
prefix must produce a non-empty, unique slug of at most 200 characters. For
example, `Hiking 2025` and `Hiking-2025` conflict and the build tells you to
rename one instead of silently overwriting generated content.

```
originals/
├── 2025-china-trip/
│   ├── _session.json           ← optional metadata
│   ├── IMG_0001.jpg
│   ├── IMG_0002.ARW            ← Sony RAW
│   └── ...
└── tidepools-spring-2026/
    ├── _session.json
    ├── DSC03421.jpg
    └── ...
```

### Optional `_session.json`

Put one at the root of each session prefix to override defaults:

```json
{
  "title": "China, Spring 2025",
  "date": "2025-04-12",
  "location": "Beijing → Xi'an → Chengdu",
  "description": "Three weeks across three cities.",
  "cover": "IMG_4421.jpg",
  "order": 10
}
```

| Field | Required | Default if omitted |
|---|---|---|
| `title` | no | humanized folder name (`2025-china-trip` → `2025 China Trip`) |
| `date` | no | earliest EXIF `DateTimeOriginal` across the photos |
| `location` | no | empty |
| `description` | no | empty |
| `cover` | no | first image alphabetically |
| `banner` | no | derived from `cover` — the photograph cropped into the session page header |
| `bannerFocus` | no | `center` — any CSS `object-position`, steering where the session banner crops its photograph |
| `order` | no | sessions without `order` sort by date desc; sessions with it sort first (lowest = top) |
| `images` | no | discovered automatically; provide an array of filenames to enforce ordering or attach captions |

If `images` is provided as an array of objects, each can carry a `caption` that the lightbox displays:

```json
"images": [
  { "file": "IMG_0001.jpg", "caption": "Mutianyu at sunrise" },
  { "file": "IMG_0042.ARW", "caption": "Terracotta warriors" }
]
```

Captions are limited to 500 characters. You rarely need to write them: the photo pipeline writes one for every photo from the photo itself and your iNaturalist identification ([docs/photos.md](photos.md)), and leaves any you've edited alone. They can also be edited from `/admin`;
Admin writes the same ordered `images` array back to `_session.json`. A caption
becomes the photograph's accessible name. Without one, the gallery uses a
contextual fallback such as “Session title, photo 4 of 20” rather than exposing
the camera filename.

Use the source filename in `cover` and `images`, including `.ARW`, `.HEIC`, or
other converted extensions. Prebuild maps it to the generated `.jpg`. The
sidecar is validated before image processing; malformed JSON, invalid dates,
wrong field types, and invalid image entries fail with an actionable path.

### Accepted formats

- **Standard:** JPG, JPEG, PNG, WebP, AVIF, TIFF, HEIC, HEIF. HEIC/HEIF conversion uses the workflow-installed `pillow-heif` helper so iPhone HDR files work reliably.
- **RAW:** Sony `.ARW`, Nikon `.NEF`, Canon `.CR2` / `.CR3`, Adobe `.DNG`, Fuji `.RAF`. Handled via `libraw-bin` → `dcraw_emu`.

Anything else is silently ignored. Add the extension to the matching set in `scripts/prebuild.mjs` if you need more.

## Step 2: the build pipeline runs

Three triggers can start a build (see [cicd.md](cicd.md)):
- Push to `main` (you changed code)
- Hourly cron (picks up new photos automatically, though GitHub skips many scheduled runs)
- `upload-session.sh --build`, or **Rebuild Site** in the admin panel
- Manual "Run workflow" click (impatience)

What happens inside `scripts/prebuild.mjs`:

1. **Authenticate to Azure** via OIDC. The build runs as the build identity created by Bicep (`AZURE_DEPLOY_CLIENT_ID`), which has `Storage Blob Data Contributor` permission on the storage account and nothing beyond it.
   - **Publish new uploads.** `publishIncoming` takes everything in the private `incoming` container, removes any GPS position with exiftool (metadata only: the image data is byte for byte what you uploaded), uploads it to the same name in `originals/` (or `hobby-media/`), and only then deletes it from `incoming`. A photo that can't be cleaned stops the build and stays private.
2. **Load the manifest** from `metadata/manifest.json` (a JSON file with last-seen blob ETags). On the first ever run, this doesn't exist yet and that's fine.
3. **List session prefixes** under `originals/` (one directory listing call).
  - Validate that every prefix has a unique, filesystem-safe public slug before clearing the previous local content.
4. **For each session prefix:**
  - Download and validate `_session.json` if present.
   - List image blobs under that prefix.
  - Reject sources that would produce the same case-insensitive output name (for example `DSC0123.ARW` plus `DSC0123.jpg`) instead of overwriting one.
   - **For each image blob:**
     - Compare its ETag to what's in the manifest.
     - If the manifest says this exact version was already checked for a location and records its full size → use its **build copy** (below): the cached one, else `metadata/build-copies/<session>/<file>`. Skip the full download.
     - If unchanged AND a cached local copy exists → reuse it. Skip download.
     - If it's a RAW file → check whether `derivatives/<session>/<base>.jpg` already exists with metadata `source-etag` matching the RAW's current ETag.
       - **Yes** → reuse the existing derivative.
       - **No** → download the RAW, convert it (see Step 3 below), upload the JPEG sidecar to `derivatives/`.
     - If it's a standard image → download it.
   - Read width/height with sharp and EXIF with exifr. A photograph the camera stored sideways (EXIF orientation 5–8) has its width and height swapped, so the recorded shape is the upright one the site shows. That's what the admin's 3:2 check and the home page's lead box go by. The earliest `DateTimeOriginal` becomes the session date; per-photo capture settings (camera, lens, focal length, aperture, shutter, ISO) are stored on each image and shown beneath it in the lightbox. EXIF survives RAW conversion because sharp is told to `keepExif()`. The HEIC converter writes none, so iPhone HEIC photos show no settings, and synthetic fixtures and stripped images simply have none either.
   - **Keep locations private (backstop).** For photos that reached `originals/` without going through `incoming`, and ones published before this check existed: once per photo and ETag, `keepLocationsPrivate` checks the working copy Astro will read and, for RAW/HEIC, the source file. Any that records a GPS position is stripped with exiftool (metadata only) in every place it's published: the working copy, the derivative, and the original in `originals/`, which keeps its name and headers. A working copy, derivative, linked original or new RAW/HEIC source that can't be cleaned fails the build; a RAW/HEIC source an earlier build already published gets a warning and another try. See [security.md](security.md#photo-locations).
   - **Swap in the build copy.** Every photo read in full (a new one, or every photo once after the copy settings change) is replaced by a 2,400 px copy: JPEG quality 95 with full colour resolution and the camera's EXIF, at the smallest width from 2,400 that keeps the photo's exact aspect ratio, so every page image comes out at the size it would from the original. The copy is uploaded to the private `metadata/build-copies/` with `source-etag` and `buildcopy` metadata, so it's made again only when the photo or the copy settings change, and the photo's full size goes in the manifest. This comes after the location check, which uploads a cleaned working copy back as the original.
   - Write `src/content/sessions/<slug>.json` for Astro to consume.
5. **Save the updated manifest** back to `metadata/manifest.json`.
6. **Prune the cache.** Anything in `.cache/prebuild/` this run didn't use is deleted, so it holds exactly one build copy per photo.

The cache key hashes the full blob name, ETag, and generated target filename
with SHA-256. Azure changes the ETag whenever content changes, while the name
and target prevent renames or conversion-format changes from aliasing old bytes.
A build copy's key also carries the copy settings' version.

### Why the build works from copies

The site never shows a page image wider than the 2,000 px session banner, and
the lightbox loads the original straight from Blob, so the build has no use for
a 6,192 px original. It matters because GitHub's runners are Azure VMs in other
regions: every byte prebuild downloads from Blob is billed as transfer between
regions. Full-size photos also made the prebuild cache about 9 GB, which with
Astro's variants passed GitHub's 10 GB of cache per repository. GitHub then
evicted one of the two on most runs, and the next build downloaded every
original again, about 1,300 GB in the month before this changed. The copies
are about a fifth of the size, so both caches fit with room to grow, and a
build that does start cold downloads about 2 GB rather than 9.

They look the same: tested on the hardest photos in the archive (smooth blur,
saturated colour on black, sky gradients, night noise), page images made from
a copy score within SSIMULACRA2's noise of ones made from the original, and
the difference is far smaller than moving Astro's WebP from quality 80 to 75.

## Step 3: RAW files (Sony `.ARW` and friends)

**The problem:** browsers can't display `.ARW`. Neither can sharp (the image library Astro uses under the hood).

**The solution:** convert RAW → TIFF → JPEG during the build:

1. Download the RAW from Blob.
2. Run `dcraw_emu -w -q 3 -T -o 1 <file>`, produces a high-quality TIFF in sRGB.
   - `-w` = use the camera's white balance
   - `-q 3` = highest-quality demosaicing (AHD)
   - `-T` = TIFF output
   - `-o 1` = sRGB color space
3. Pipe the TIFF through `sharp(...).keepExif().jpeg({ quality: 95, mozjpeg: true, chromaSubsampling: '4:4:4' })` → a full-resolution JPEG with the camera's EXIF. The TIFF is lossless, so this is the only lossy step, at a quality and with full colour resolution that are visually identical (a GPS position, if any, was removed before upload or is removed before it's published).
4. Upload that JPEG to `derivatives/<session>/<base>.jpg` with:
   - `Content-Type: image/jpeg`
   - `Cache-Control: public, max-age=31536000, immutable`
   - Metadata `source-etag=<RAW's ETag>` and `derivative=<conversion version>` (so the next run knows whether to reconvert: when the source changes, or when the conversion itself improves)

**The original RAW stays in `originals/`.** You never lose the negative; the only change a build ever makes to it is removing a GPS position. The derivative is what the site shows and what the lightbox treats as "full resolution."

HEIC/HEIF and TIFF take the same route through `processConvertBlob`: iPhone HEIC is decoded by [scripts/heic-to-jpeg.py](../scripts/heic-to-jpeg.py) (`pillow-heif`) to a lossless TIFF, TIFF goes straight to sharp, and both get the same single JPEG encode and land in `derivatives/` with the same metadata. Browsers can't display HEIC or RAW, so this one conversion is the only time the site re-encodes a photo at full size; JPEG, PNG and WebP uploads are served exactly as uploaded.

**dcraw_emu** comes from the `libraw-bin` apt package, installed in the build workflow (cached between runs so it's instant after the first install).

If you add a new RAW format, just add its lowercase extension to the `RAW_EXTS` set in `scripts/prebuild.mjs`.

## Step 4: Astro builds the site

Once `src/content/sessions/` is populated, Astro's `astro build` does the rest:

- **Content collection.** Astro reads each `<slug>.json` against the Zod schema in `src/content/config.ts`. This independently validates generated output after the earlier sidecar checks.
- **Image optimization**: every reference to a session image goes through `<Picture>`, which during build calls sharp to produce:
  - Multiple widths: 320 to 960 px on cards, 480 to 1600 px in a session's grid, and up to 2000 px for the session banner, the widest image on any page
  - Two formats per width: WebP (broadly supported, small) and JPEG (universal fallback). AVIF is intentionally **not** generated: its encoder is several times slower than WebP and would dominate build time for little extra savings.
- **Static HTML**: every page is pre-rendered to a `.html` file. The `<picture>` tags contain `srcset` listing every variant; the browser picks the right one.
- **Lightbox sources.** Each gallery link carries two URLs: `href` points at a size-capped WebP that paints quickly, and `data-pswp-full` points at the original. The declared `data-pswp-width`/`height` are the **original's**, read from the session JSON because Astro itself only sees the build copy, so zoom is never capped. See [Viewing: full resolution without the wait](#viewing-full-resolution-without-the-wait).
- **Loading priority.** The first homepage cover and first photograph on each session page are eager/high priority because they are the likely LCP elements. All remaining photographs stay lazy. Pages preconnect to the Blob origin so DNS/TLS negotiation can begin before the browser discovers the first image in the body.

The output starts as a `dist/` folder containing static files and generated
variants. `scripts/sync-variants.mjs` then uploads photo variants to Blob,
rewrites HTML references, and removes those images from `dist/`.

---

## Step 5: deploy to SWA

After the variant sync, the `Azure/static-web-apps-deploy@v1` action uploads the
small remaining `dist/` payload to SWA using the deploy token. SWA fans the new
HTML, CSS, and JavaScript out to its CDN edge locations.

PR builds get their own preview environment automatically.

## Viewing: full resolution without the wait

Originals here run to 6192 px and 3–22 MB. A gallery has to end up showing
exactly that — it is a photography site — without making someone wait on a
20 MB download before anything appears.

The site separates **what you see immediately** from **what you end up with**,
using three tiers that each do one job:

| Tier | Source | Size | When it is fetched |
|---|---|---|---|
| 1. Placeholder | The grid thumbnail | 0 bytes | Already decoded on the page behind the lightbox |
| 2. Bridge | Capped WebP (`VIEW_MAX_WIDTH`, 1600 px) | ~200 KB | On open, and preloaded for near neighbours |
| 3. Full | The original, image data untouched (only a GPS position is ever removed) | 3–22 MB | Always, for the photograph actually on screen |

PhotoSwipe normally reuses the gallery thumbnail only on the first slide; a
`placeholderSrc` filter in `src/components/Lightbox.astro` lets every slide use
one, so a photograph is on screen immediately rather than after a round trip.
The bridge arrives next, then `upgradeToOriginal()` swaps in the original once
it has decoded, so the visible image never flashes blank.

Two details make this cheap rather than merely clever:

- **Only the current slide is upgraded.** `preload` fetches *bridges* for
  neighbours, never originals, so skimming past a photograph costs ~200 KB
  instead of ~12 MB. You pay full resolution only where you actually stop.
- **Originals are cached hard.** They previously had no `Cache-Control` at all,
  so every viewing re-downloaded the whole file. The prebuild now backfills
  `public, max-age=31536000, immutable` while it is already enumerating blobs
  (see `ORIGINALS_CACHE_CONTROL` in `scripts/prebuild.mjs`), which makes it a
  no-op after the first run. Repeat views cost nothing.

Measured against the previous approach, where `href` pointed straight at the
original and PhotoSwipe's default `preload: [1, 2]` therefore pulled **seven**
of them to show five:

| | Before | After |
|---|---|---|
| Session page, 34 photographs | ~7 MB | **0.58 MB** |
| Time to first pixel in the lightbox | full original (3–22 MB) | **~80 ms** (cached thumbnail) |
| 5 photographs viewed | 72.2 MB | **59.6 MB** (57.7 MB of it the originals you looked at) |
| Viewing the same photograph again | full re-download | **free** |

The remaining 57.7 MB *is* the deliverable: five untouched originals. The win is
that nothing else is paid for, and none of it blocks the first paint.

### The tradeoffs

Nothing here makes a 12 MB file arrive faster — it only stops that download from
blocking what you see. Two consequences follow, and both are real:

**There is an upgrade window.** Between the bridge appearing and the original
replacing it, you are looking at 1600 px. How long depends entirely on the link:

| Connection | First pixel | Original arrives | Window |
|---|---|---|---|
| Unthrottled | 191 ms | 1.4 s | ~1.3 s |
| Fast 4G (20 Mb) | 204 ms | 2.0 s | ~1.8 s |
| Slow 4G (4 Mb) | 269 ms | 10.1 s | ~9.9 s |
| 3G (1.5 Mb) | 471 ms | 25.7 s | ~25 s |

At fit-to-screen the difference is hard to see — 1600 px already exceeds what
most viewports resolve — so in practice the window shows up as a faint
sharpening rather than a blurry placeholder. Zoom in during it and the softness
is obvious, which is the honest cost of not making everyone wait.

**Total bytes go up, not down, for a visitor who views many photographs.** Six
photographs on a phone is about 60 MB of originals.

That is a deliberate choice, not an oversight. This is a photography portfolio:
anyone who opens a photograph is shown it as it was taken, on every connection,
with no exception and no quality switch to get wrong. The bytes saved by
serving something smaller would come straight out of the only thing the site
exists to do.

What is avoided instead is *waste* — originals for photographs nobody stopped
on, and re-downloads of ones already seen.

> **Changing the cap.** `VIEW_MAX_WIDTH` in `src/pages/sessions/[slug].astro` is
> deliberately a width the grid already generates, so no bespoke variant is
> built. Raising it improves the bridge on very large displays at the cost of
> bytes spent on photographs people skim past. It does not change the ceiling:
> what you end up looking at is the original either way.

## How long does it take?

| Event | Time to live |
|---|---|
| You push a code change | ~3 minutes (full build + deploy) |
| You upload a new photo and wait for the cron | an hour or more (GitHub skips many scheduled runs); private until then |
| You upload a new photo and click "Run workflow" | ~3 minutes |
| Future Event Grid path | ~1 minute |

Incremental builds (only one new photo since last run) are usually under 90 seconds thanks to the ETag cache.

## What's stored where

| Container | Contents | Public? | Listable? |
|---|---|---|---|
| `incoming/` | New uploads, waiting for the next build to remove any GPS position and publish them. | No | No |
| `originals/` | Your uploads, published. Source of truth. | Reads of known URLs | No |
| `derivatives/` | RAW→JPEG sidecars. Regenerable. | Reads of known URLs | No |
| `variants/` | Responsive WebP/JPEG files + admin thumbnails. Regenerable. | Reads of known URLs | No |
| `hobby-media/` | Full/display images used only by hobby galleries. | Reads of known URLs | No |
| `metadata/` | `manifest.json` + `admin-index.json`, the 2,400 px copies the build reads (`build-copies/`), and the photo and Instagram pipelines' state (`photos/`, `social/`). | No | No |

| Path in repo | Contents |
|---|---|
| `src/content/sessions/*.json` | Per-session metadata + image list. Gitignored, written fresh by prebuild every run. |
| `src/content/sessions/<slug>/images/*` | The 2,400 px build copies Astro processes. Gitignored. |
| `dist/` | The built site. Gitignored. Recreated every build. |
| `.cache/prebuild/` | One build copy per photo (about 2 GB), keyed by ETag; whatever a run didn't use is deleted at its end. Gitignored. Persisted between CI runs via `actions/cache`. |

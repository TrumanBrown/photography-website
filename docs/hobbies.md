# Hobbies section

A second, **optional** top-level section beside Photography. Photography is unchanged and remains the home page (`/`) and default landing. Hobbies lives at `/hobbies` with one page per hobby, each able to mount a self-contained interactive "island."

This doc covers how the section is wired, how to add a hobby, the conventions every interactive follows, and the aquarium island as the original reference implementation. It is written so a future session (or you) can pick the work back up cold.

> Status: shell + six islands + one daily puzzle are live: **Aquarium keeping**, **Tide pooling**, **Fishing**, **Birding** (selfie to bird), **Herping** (night-drive road cruising), **Hiking** (trail builder + postcard studio), and **Narrow nature** (a daily where-and-when puzzle, called Day list in the code and mounted by its `dayList` content rather than an `interactive` island). More are planned (travel map and repo explorer) and meant to be built **one at a time**.

- Hobbies JSON is **hand-authored and committed** to git. Sessions are gitignored and generated by `scripts/prebuild.mjs` from Blob Storage. - A hobby page does **not** show the sessions sidebar. `BaseLayout` takes a `section` prop (`'photography'` default | `'hobbies'`); when `'hobbies'` it hides the `ArchiveRail` session list and its mobile drawer, and the Header highlights its "Things to try" nav item (the same two labels as the archive rail: "Photographs" and "Things to try").

The `sections.hobbies` flag only controls the **header nav link** (discoverability). The pages still build when it's off, turning it off "ships dark," it doesn't remove the routes.

## Adding a hobby

1. **Create the content entry** `src/content/hobbies/<slug>.json`:

   ```json
   {
     "title": "Hiking",
     "summary": "Short blurb shown on the hobby card.",
     "intro": "A sentence or two shown on the hobby page above the interactive.",
     "plateNote": "Liberty Bell · Washington Pass, July 2026",
     "order": 3,
     "interactive": "pixel-hike"
   }
   ```

   - `slug` comes from the filename (`hiking.json` → `/hobbies/hiking`).
   - The card's picture is a stipple plate drawn from one of your photos: add a subject named after the slug to the [stipple-plates skill](../.github/skills/stipple-plates/SKILL.md) and render it into `src/assets/plates/`. `plateNote` is the caption under it. `npm test` fails while a hobby is missing any of its plates.
   - `order` sorts the landing grid (ascending); entries without `order` fall to the end, alphabetical.
   - `interactive` is one of the enum values in the schema, or omit it for a static page.

2. **(Optional) build the interactive island**: see the pattern below. If you only want a static page (text/photos), skip this and leave `interactive` unset.

3. **Wire the island** in [src/pages/hobbies/[slug].astro](../src/pages/hobbies/%5Bslug%5D.astro): import the component and add a branch:

   ```astro
   {interactive === "pixel-hike" && <PixelHike />}
   ```

4. **(Optional) give the card an opening scene** in `src/lib/scenes/`, keyed by the slug in [index.ts](../src/lib/scenes/index.ts). See [Opening scenes](#opening-scenes). Without one, clicking the card plays the plain dive into its plate.

That's it for a dependency-free hobby without a photo gallery. Optional media, third-party data, or a new package may also require the documented Blob, CSP, dependency, or CI updates.

## Interactive island conventions

Every island follows the same rules so they stay cheap, safe, and consistent with the rest of the site:

1. **Self-contained core.** The playable interaction should not depend on a runtime API: geometry and game data are baked in, and graphics are procedural or local assets. Optional personal-data and CC-photo enrichments may use the allow-listed iNaturalist API/CDNs, but they load lazily and degrade without breaking the island. Birding separately bundles and self-hosts its landmark model; see [the birding implementation](#reference-implementation-the-birding-island-selfie-to-bird).
2. **CSP-safe by construction.** Use Astro's processed `<script>` (with `import`), **never** `is:inline`. Astro emits it as a same-origin module under `/_astro/…js`, which satisfies the strict `script-src 'self'` policy in [staticwebapp.config.json](../staticwebapp.config.json). No per-script hashes to maintain. (Confirmed in the build output: the aquarium ships as `/_astro/AquariumTank.astro_…js`.)
3. **Lazy by route.** An island's script only loads on its own `/hobbies/<slug>` page, so Photography pages stay zero-JS and the build stays light.
4. **Mobile-first-ish.** Works on touch, even if richer on desktop, same bar as the photography section. Responsive sizing (`ResizeObserver`), touch input (`pointerdown`, native range inputs), and pausing offscreen.
5. **Keyboard too.** Anything a tap does needs a key. A canvas sits in a frame with `tabindex="0"`, `role="application"` and an `aria-label` that names the keys (the canvas itself is `aria-hidden`); the frame, not the canvas, takes focus because the frame's `overflow: hidden` would clip a ring on the canvas. Arrow keys move a pick that's ringed in dark and light while the frame has `:focus-visible`, Enter or Space does what a tap would, and a `sr-only` `aria-live="polite"` line says what's picked. Dialogs the toy opens hand focus back to the frame. Tide pooling, herping and the fishing maps work this way, the day-list map uses the same focusable frame, and the hiking canvas has its own arrow-key editing.
6. **Minimal dependencies.** Prefer vanilla + canvas/SVG. Add a small library only if it _meaningfully_ improves graphics/accuracy, and document it here.
7. **Still under a scene.** While a card's opening scene plays over the page (`landing-scene` on `<html>`, see [Opening scenes](#opening-scenes)), an island keeps to its first frame: don't start an animation loop while `covered()` ([covered.ts](../src/lib/covered.ts)), and start it from `whenUncovered()`. A canvas that's read back with `getImageData` while the page loads is made with `{ willReadFrequently: true }`, so reading it doesn't hold up the GPU the scene is drawing with.

Markup lives in a `.astro` component under `src/components/hobbies/`; non-trivial logic lives in `src/lib/hobbies/<name>.ts` and is imported by the component's `<script>`. The component binds to the engine via `data-*` hooks, so the engine owns behavior and the markup stays static.

## Shared parts and the look

The hobby pages are dressed like the photography archive: ink on paper, hairline rules, tracked caps labels, square corners, one typeface. Every color comes from the tokens in [src/styles/global.css](../src/styles/global.css) (`--paper`, `--band`, `--ink`, `--ink-2`, `--ink-3`, `--rule`, `--rule-soft`, `--hover`), which switch for dark mode on their own. The same tokens are Tailwind colors (`text-ink-2`, `border-rule`, `bg-band`, `hover:bg-hover`...) in [tailwind.config.mjs](../tailwind.config.mjs). The Astro Tailwind integration reads that config once, so restart `npm run dev` after editing it.

Things the hobby UI deliberately doesn't use, because they read as generated: Tailwind's default hues (sky, emerald, lime, amber...), pills and `rounded-*` chrome, drop shadows and blur, an icon on every control, emoji, a badge above a headline, and Title Case. The toys' own pixel art and photographs are the only color.

A few interaction details come from React component libraries (Cult UI, Watermelon UI, Skiper UI). The site is Astro with no React, so each one is rewritten in plain CSS or TypeScript, keeping the mechanic and dropping the library's look:

## Opening scenes

Clicking a hobby card, on `/hobbies/` or in the home page's band, plays a short scene made from the card's own stipple plate, two and a half to three seconds long. The plate's dots lift off the card onto a sheet of paper and act something out, and the way the scene ends opens the hobby page.

| Hobby            | Scene                                                                                                                                                                                                                                        | Module                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Narrow nature    | The globe spins and stops on a random inland spot; a red finder box closes in and locks on with its coordinates; the camera dives in, and the page opens through big dots.                                                                   | [globe.ts](../src/lib/scenes/globe.ts)       |
| Aquarium keeping | Bubbles rise, the gourami swims right, turns around head first, backs up a touch as its tail comes round and darts off the left of the screen; ripples spread from its wake with the page inside them.                                       | [aquarium.ts](../src/lib/scenes/aquarium.ts) |
| Tide pooling     | The crab rears up bigger and raises its right claw, open; it draws back and jabs in one go, snaps it on the screen, and a shockwave rings out from the pinch, sweeping the dots away.                                                        | [crab.ts](../src/lib/scenes/crab.ts)         |
| Fishing          | The trout holds in the current, tail working, while a rod swings in and casts; the lure lands a little way off its nose, the trout draws back and strikes, and it's hauled off the top of the screen; the page opens in dots behind it.      | [fishing.ts](../src/lib/scenes/fishing.ts)   |
| Birding          | The oystercatcher tips and turns its head, crouches and springs up, wings opening, and flies up out of the screen with its legs trailing; its shadow thins away and the page opens along its trail.                                          | [birding.ts](../src/lib/scenes/birding.ts)   |
| Herping          | A hand slides in along the ground, scoops up the salamander, lifts it up close and holds it there while its tail sways, then pulls it off the side; the page opens where it went. The hand is drawn in [hand.ts](../src/lib/scenes/hand.ts). | [herping.ts](../src/lib/scenes/herping.ts)   |
| Hiking           | A little hiker walks the ridge to the summit (the mountain's real skyline, read off its dots), turns to face you with his arms up, and the view rushes in on him as it fades.                                                                | [hiking.ts](../src/lib/scenes/hiking.ts)     |

Most scenes end by uncovering the hobby page itself, so that part has to play over the hobby page. Those scenes change page as soon as the plate has lifted off its card (`LEAVE` in [engine.ts](../src/lib/scenes/engine.ts)), before anything in them moves, and hold still until `ACT`, about 0.4 s later, while the hobby page loads. From the moment the page changes, the camera pushes in a touch, easing out over 1.4 s by the clock (`pushZoom`), so a hobby page that's slow to pick the scene up still shows it moving rather than frozen; the hobby page does the same in CSS until the scene's canvas is up (`landing-hold` in [global.css](../src/styles/global.css), timed off the note, on the same curve). The old page leaves a note with the scene's seed, the plate it was drawn from, its timing and the frame it left on, as dots, and, under a key of its own, the plate's dots and the scene's props ([carry.ts](../src/lib/scenes/carry.ts)), so the hobby page doesn't decode the plate or draw the props again.

On the hobby page, the head script ([landing.ts](../src/lib/landing.ts) `landingBootstrap`) paints that frame once, on a canvas of its own, before the first paint. As a CSS picture, the GPU would draw its thousands of dots again for every tile just as the scene needs it to start up. The same script starts the scene worker on a canvas under the frame, with what the last page carried, and puts `landing-scene` on `<html>`, which keeps the page's own animations still until the scene is gone ([covered.ts](../src/lib/covered.ts)). Once the worker has the scene's next frame up, the painted frame comes down and the scene plays all of its action over the page. If the hobby page is slow to come up, the scene waits in its hold rather than skipping ahead. If the worker can't start, the page plays the scene itself ([index.ts](../src/lib/scenes/index.ts) `resume`); if that can't load within a couple of seconds, the frame just fades; and if the page's scripts never run at all, it shows itself after four seconds anyway. Pointing at a card also fetches its hobby page and that page's scripts and styles, so it comes up quickly. The globe works the other way: it ends zoomed into a few dozen big dots, and the hobby page opens through those, each one hollowing into a ring and then a window onto the page ([landing.ts](../src/lib/landing.ts) `planReveal`).

How it fits together:

- [worker.ts](../src/lib/scenes/worker.ts) plays scenes in a Web Worker on an `OffscreenCanvas`, so nothing the page does while it loads or runs its own scripts can make a scene stutter: the worker reads the plates, sets the scene up and draws every frame. Getting cards ready ahead of a click (reading their plates, drawing their props) goes one piece at a time behind anything a click needs, a card that's pointed at going ahead of the rest, and waits while a clicked card's scene sets up and plays. When a card is pointed at, focused or pressed, the worker also sets its scene up once and draws a few moments of it out of sight: the browser readies code slowly the first time it runs, so this way a click starts the scene in well under a tenth of a second rather than a quarter of one. On the page, [player.ts](../src/lib/scenes/player.ts) puts the canvas up, passes input on, draws the globe's labels in the page's fonts and changes page when it's told; [protocol.ts](../src/lib/scenes/protocol.ts) has the messages. Where a browser can't run a canvas in a worker, scenes play on the page itself, the same way.
- [pen.ts](../src/lib/scenes/pen.ts) works out where each dot lands, through the camera and any warp, and hands them to a sink: WebGL ([gl.ts](../src/lib/scenes/gl.ts): instanced circles, holes by blending, lines as quads, labels as textures) where the GPU runs it, or a 2D canvas. The two match to within a level of grey.
- [stage.ts](../src/lib/scenes/stage.ts) has everything that doesn't touch the page: dot sets, affine moves, the camera, easing (`cubicBezier`, for curves the scenes share with CSS), splitting a plate into named parts, `stipple()`, which draws props (the rod, the wing, the hand, the hiker) as blue-noise dots in the plates' own pen size and spacing, and the wakes (`wakeTimes`, `wakeHoles`): when the opening behind a moving figure reaches each point of the screen.
- [hand.ts](../src/lib/scenes/hand.ts) builds the herping hand out of rounded tubes, shaded as if lit from the upper left, with contours, creases and nails; the dark plates draw light as dots, so its shading flips for them. Pale props like it lay down discs of paper first (`pass: "halo"`), or whatever is behind would show through their few dots.
- [engine.ts](../src/lib/scenes/engine.ts) runs a scene: the lift off the card, the paper, the draw calls (`part`, `dots`, `line`, `label`, `cut` to open holes onto the page underneath, `look` to fade or blur the whole sheet) and the handover. `stageScene` sets a scene up on any sink without touching the page, which is how the worker uses it; `show` and `play` put it on a canvas on the page. [table.ts](../src/lib/scenes/table.ts) is the table of scenes both sides share.
- [plate-dots.ts](../src/lib/plate-dots.ts) reads the dots off a plate image, for the scenes on either page and for the plain dive.
- [open.ts](../src/lib/open.ts) loads the scenes on demand (fetched when the page is idle), gets a card ready when it's pointed at, focused or pressed, or has been in view a moment, and falls back to the plain dive into the plate if the scenes can't load. A click never waits more than about 0.6 s for its plate or the scene worker, however slowly they're arriving (the deadline runs from the click, in the worker too); once the worker has the plate, it gets to set the scene up. Past the deadline, the card dives into its plate, or, where the page can't read the plate's dots (production's plates come from the storage account, which only the worker reads with CORS), the plate itself sinks into paper, and the hobby page opens through its halftone. A home-page card shows the small mini plate; its scene plays from the finer card plate, the mini handing over to it during the lift.

Plate parts are outlines in card units (880 × 660; a mini plate's dots are scaled up to match), and the first part that claims a dot gets it. [scenes.test.ts](../src/lib/scenes/scenes.test.ts) plays every scene through a stand-in painter at desktop and phone sizes: each one that changes page has to do so as its lift ends and hold still from `leave` to `depart`, come out the same when it's built again, and end with the page open and none of its dots left on screen; the globe has to end on its big dots alone. The push in has to follow the same curve as the CSS. A scene draws each frame in well under a couple of milliseconds of script, so it keeps up with a 120 Hz screen: anything that works out a dot's place does what depends on the time alone once a frame, not once a dot.

A second click, tap, Enter or Space plays the rest of a scene about three times faster, on either page; Escape puts the page back before it changes. Under reduced motion a card just opens its page.

To look at a scene frame by frame, open `/hobbies/?scene-debug` on `npm run dev`, click a card, and call `__scene.seek(ms)` from the console (`__scene.duration`, `leave` and `depart` are its timings; `__scene.hand()` changes page, and the hobby page then has its own `__scene`). `?scene-main` plays scenes on the page rather than in the worker, `?scene-2d` keeps to the 2D canvas, and `?scene-gl` takes WebGL even where it's only in software, to compare them. Each switch carries over to the hobby page, and all of them are left out of production builds.

## Reference implementation: the hiking trail studio

A creative **build → walk → develop** experience. Visitors shape a route, add up to ten trail moments, change landscape, season, weather, light, distance, and jacket color, then watch a tiny hiker traverse it. Route length controls the scale of the world: a 3-mile outing is an intimate single mountain, while an 18-mile route expands into a seven-mountain chain with smaller, denser scenery. The same scene recipe develops into a more detailed `2400 × 1600` postcard for local download or the device share sheet.

**Files**

- [src/components/hobbies/PixelHike.astro](../src/components/hobbies/PixelHike.astro), the accessible controls, responsive canvas, action bar, and postcard dialog.
- [src/lib/hobbies/hiking-model.ts](../src/lib/hobbies/hiking-model.ts), the validated state, four biome morphology profiles, variable mountain generator, moment-driven terrain deformation, smart moment placement, distance-based profile resizing, and playful effort estimate.
- [src/lib/hobbies/hiking-renderer.ts](../src/lib/hobbies/hiking-renderer.ts), the shared Canvas 2D renderer. Editor and postcard modes share elevation/aspect-driven rock, alpine turf, soil, treeline, snow, and terrain-aware moments; editor density is capped for responsive dragging. Postcard mode adds finer contour bands, cloud shadows, scree, gullies, ledges, trail stones, footprints, denser vegetation, and foreground depth.
- [src/lib/hobbies/hiking.ts](../src/lib/hobbies/hiking.ts), DOM binding, undo, pointer/keyboard editing, local persistence, animation lifecycle, responsive sizing, and PNG/share export.
- [src/lib/hobbies/hiking-model.test.ts](../src/lib/hobbies/hiking-model.test.ts), pure model coverage including variable mountain counts, silhouette variety, moment deformation and placement, distance resizing, legacy migration, and untrusted saved-state normalization.

The controls are plain HTML (radio groups, buttons, a text field, native selects and ranges) styled with the shared parts above; there are no icons and no UI dependencies. The model, animation, both canvas renderers, persistence, and export path remain dependency-free and make no runtime network requests.

**Variety is deterministic, not a fixed template.** Mileage determines a target of one through seven mountains. Seeded generation then chooses nonuniform horizontal spacing, height progression, and a form for every mountain: narrow spire, one-sided shoulder, broad massif, or near-plateau, weighted differently for Cascades, fjord, karst, and Himalayan terrain. Shuffle changes both seed and mileage; changing landscape regenerates the current route using that biome's morphology. Dragging the length slider resamples the authored profile into a larger or smaller world instead of merely changing a number.

**Trail moments change the route.** Clicking a moment adds it immediately at a sensible location: lakes seek low basins and carve them deeper, lookouts seek high points and raise a spur, waterfalls prefer steep faces and cut a drop, camps flatten sheltered ground, and meadows/wildflowers create broad benches. Forests clear and repopulate a corridor, while snowfields create a high crossing. Waterfalls inspect the local grade, choose the actual downhill direction, become stepped streams on gentler slopes or plunges on steep faces, cross rock ledges, and finish in a laterally aligned pool with foam and mist. Wildflowers grow in clustered, terrain-clipped alpine bands with restrained yellow/red/blue/violet/white/orange species variation; camps sit on sampled pads and lookout cross-braced footings reach the real left/right grade. Every placed moment has a visible route handle and can be dragged horizontally; terrain, effort, artwork, and the eventual postcard update together.

**One scene recipe, two renderers.** Both canvases consume the same `HikeState`, so the developed image cannot silently invent a different route. The responsive editor uses the same terrain-sampled moments and elevation materials at reduced branch/grass/bank detail so direct dragging stays fast; the export canvas is created only on request at a fixed `2400 × 1600`. Mountain materials are biome-specific and driven by elevation, local steepness/aspect, and continuous seeded noise rather than a single green fill: Cascades transition from dark lower forest through patchy olive alpine turf/heather into neutral volcanic/granitic rock, ledges, and scree; fjords expose vertically jointed gray walls; karst uses pale limestone with vegetation pockets; Himalaya uses brown-gray metamorphic faces and sparse tundra. Summer snow is generated as separate retained couloirs with blue-gray melt shadow and embedded rock, while Winter permits broader connected accumulation with avalanche gullies and exposed arêtes. Postcard mode adds finer contour bands, cloud shadows, hundreds of scree marks, gullies, ledges, biome-specific waterfalls/vines, trail stones, footprints, denser vegetation, and foreground depth. Lakes find the spill line inside their actual carved basin and use the sampled basin floor as their submerged boundary, behind irregular banks, stones, and reeds. Forests use individually grounded conifers with local slope, root shadow, altitude-aware size, varied age, and feathered edges; meadows are clipped grass-and-heather bands that follow and extend down the local face rather than horizontal decals. Generation uses only the visitor's CPU/GPU and browser memory. It makes no API calls, uploads nothing, and incurs no per-generation Azure cost.

**Persistence and sharing.** The normalized scene is saved under `trail-studio-v2` in `localStorage`; a saved v1 five-point route is migrated and blended into the new distance-scaled profile on first load. Export uses `canvas.toBlob()` rather than a base64 data URL. Browsers supporting file sharing receive a real PNG through `navigator.share`; other browsers always retain the download action.

**The postcard develops.** When the dialog opens, the finished canvas comes up like a print in the tray: pale, warm and soft under a dot grain, reaching full contrast in about 1.7 seconds while the status reads "Developing at 2,400 × 1,600...". It's only CSS on top of the finished canvas, so the downloaded PNG is identical either way, and under reduced motion the print is simply there. Once it's up, a round postmark with the trail's name and the day slams onto the top right corner (`makePostmark` in the renderer); it's painted into the canvas as it lands, so the PNG does keep that, in dark ink on a pale sky and pale ink on a dark one.

**Input parity.** Every generated terrain point has a visible canvas handle and a dynamically generated native range control under “Fine-tune the terrain”; points support direct pointer dragging and arrow-key editing on the focusable canvas. Moment buttons are immediate commands; moment handles support pointer dragging and the itinerary tags remove a moment. Landscape and light are underline-tab radio groups (arrow keys move between them), and every other option is a real button, select, or slider. Reduced-motion users get an immediate completed walk instead of a forced animation.

## Reference implementation: the aquarium island

A planted-tank **stocking sandbox**. Tap a species to add it, resize the tank, and watch a bioload meter react. It is meant to be fun and roughly believable, not a real stocking calculator.

**Files**

- [src/components/hobbies/AquariumTank.astro](../src/components/hobbies/AquariumTank.astro), the markup (canvas, the species picker rendered at build time, the tank panel) and the mounting `<script>`.
- [src/lib/hobbies/aquarium-species.ts](../src/lib/hobbies/aquarium-species.ts), the species data: a pure module, so the page can render the picker from it at build time.
- [src/lib/hobbies/aquarium.ts](../src/lib/hobbies/aquarium.ts), the whole engine: the canvas pixel rendering, adding and removing fish, and the UI sync. **Zero dependencies.**

**Single source of truth.** The `SPECIES` array in `aquarium-species.ts` (35 freshwater species) drives everything. The picker lists them grouped by where they swim (top, middle, bottom), each with a two-color swatch taken from its own sprite colors and its minimum tank size; the stocking list is built from it at runtime. Each entry stores an approximate adult length (inches), a relative `bioload` weight, a sensible `minGallons`, a swim `zone` (top/mid/bottom), a body `shape`, and two colors.

### How the stocking math works

Two tunable constants at the top of `aquarium.ts` plus one sum:

```
capacity = gallons × PLANTED_CAPACITY_PER_GALLON     // 0.55 "load units" per gallon
load%    = Σ(bioload of every fish in the tank) / capacity
```

So a 20-gallon tank has a capacity of `20 × 0.55 = 11` units. Seven neon tetras at `0.3` each (`2.1`) plus four pygmy cory at `0.35` (`1.4`) plus five cherry shrimp at `0.05` (`0.25`) plus one honey gourami at `0.9` come to `~4.65`, or about 42% of capacity, which reads **Healthy**. The formula lives in [src/lib/hobbies/stocking.ts](../src/lib/hobbies/stocking.ts), a pure module split out from the canvas engine and unit-tested in `stocking.test.ts`.

The meter label comes straight from `load%`. The meter itself is a 1px ink rule (`.hair`) with the percent rolling to its new value, so the word carries the state rather than a color:

| Load      | Label           |
| --------- | --------------- |
| `< 40%`   | Lightly stocked |
| `40–85%`  | Healthy         |
| `85–100%` | Heavily stocked |
| `> 100%`  | Overstocked     |

Separately, each species carries a `minGallons`. If the current tank is smaller than any stocked species likes, a note appears (for example "Angelfish likes 29+ gallons"). That check is independent of the bioload percentage, because some fish need swimming room regardless of waste.

**Tank size also scales the scene, not just the meter.** The canvas stays the same size, but a bigger tank renders the fish smaller (apparent size roughly 1/∛volume, clamped ~0.72–1.3×) and grows the plant and floating-cover density (~0.65–1.7×); a small tank shows big fish and sparse planting. So dragging the gallons slider has an immediate visual effect: fish resize live and the planting re-aquascapes on a short debounce. See `fishScale()` / `plantFactor()` in [src/lib/hobbies/aquarium.ts](../src/lib/hobbies/aquarium.ts).

### Where the numbers and species come from

Being upfront, because the request was that anyone can learn how this works:

- **The species roster is hand-picked from general fishkeeping knowledge** (the fish people actually keep in planted community tanks), not pulled from any database, API, or dataset.
- **The per-species numbers are approximate and tuned by feel.** The adult sizes are ballpark hobby figures; the `bioload` weights roughly track how big and messy a fish is; the `minGallons` values are common community recommendations. None of them are precise or authoritative, and the bioload weights are not derived from measured waste data, they were chosen and play-tested until the meter behaved sensibly.
- **The model is a miniature of real stocking heuristics.** The old rule of thumb is "one inch of fish per gallon," and community tools such as AqAdvisor estimate stocking from a large species database. This sandbox uses the same idea with a single "load per gallon" constant instead of a database. The `0.55` figure and the 40 / 85 / 100% thresholds were picked so a normal community tank reads healthy and obvious overstocking turns red.
- **Bottom line: it is a toy.** If you are stocking a real tank, research each species properly rather than trusting this meter.

### How the pixel art is made

Everything you see in the tank (fish, plants, rocks, driftwood, bubbles, light) is **drawn in code** with canvas `fillRect` calls. There are no image files, sprite sheets, stock photos, or AI-generated art anywhere in the scene, so there is nothing to license or attribute. (Real tank photos are separate, see [Photo galleries](#photo-galleries-hobby-media) below.)

- **The pixel look** comes from a fixed block size `PIX` (4 CSS pixels). Every shape snaps to that grid and image smoothing is turned off, which gives the chunky 8-bit feel. Dropping `PIX` makes finer pixels; raising it makes chunkier ones.
- **Fish are procedural.** Each one is built from its species params: a body drawn as horizontal pixel rows of an ellipse (`fishBody`), a tail, fins, a lateral stripe or vertical bars, and a small eye. A `shade()` helper mixes the body color toward white for the top rows and toward black for the bottom for a bit of lighting. There are eight silhouettes: `fish` (tetras/barbs/livebearers), `gourami` (oval body with its signature trailing pelvic feelers), `betta` (small body, big flowing fins), `angelfish` (tall diamond with long swept-back dorsal/anal fins + ventral filaments), `tall` (oval cichlids/rams), `long` (cories/loaches/plecos, with a downturned barbeled snout), `shrimp`, and `snail`, routed in `drawFish` by `shape`. Fish are drawn back-to-front by depth `zone` for layering.
- **The scene is layered for performance.** A **baked** offscreen background (water gradient, dark silhouette plants for depth, four rocks, two driftwood pieces, gravel substrate, and a carpet of plants along the front) is rendered once and only redrawn on resize. Each animation frame just blits that image and then draws the moving parts: slanted caustic light, two swaying foreground plant types (tall vallisneria and stems), fish, floating surface plants with dangling roots, and rising bubbles.
- **Layout is seeded, not random each frame.** Plant, rock, and bubble positions come from a tiny seeded pseudo-random generator (`makeRng`) keyed to the tank width, so the scene is stable but adapts when the canvas resizes.

### Mobile and performance

- The canvas resizes to its container via `ResizeObserver`; height clamps to 220–460px and fish scale with canvas width.
- Because the static background is baked and blitted, only fish, foreground plants, floaters, and bubbles are recomputed per frame.
- The loop pauses when the canvas scrolls offscreen (`IntersectionObserver`) or the tab is hidden (`visibilitychange`), so it costs nothing when not in view.
- Touch friendly: native range slider, a species list with 32px rows, and tap-to-add (after picking a species, tapping in the tank drops one at that point).
- **Adding a fish is a jump.** It leaps from the swatch you tapped, growing from the two-colour swatch into its sprite and flicking water off its tail, comes down through the surface with a splash, and sinks to its depth nose-first, levelling out and trailing bubbles. A tap in the tank drops one in over that spot the same way. The leap is drawn on a fixed canvas that only exists while something's in the air, snapped to the tank's pixel grid so the fish lands on the pixels it flew on; the tank takes over at the surface. Each tap is its own jump, so tapping fast sends a run of fish in, and the stocking list counts each one as it lands. See [aquarium-jump.ts](../src/lib/hobbies/aquarium-jump.ts).
- **Taking a fish out is a net.** The "−" beside a species takes one off the list at once and sends a pixel net down for it: in from above the surface, a quick scoop, then up and out with the fish (`netPath`). Several can be in the water at once.
- **Start over tips the tank.** The frame leans over on its low bottom corner (`tipLean`); everything in it rushes for the low corner of the rim and pours out with the water, falling clear on the same layer the jumps use, and the tank rocks back level, empty.
- `prefers-reduced-motion` slows everything, stops the plant sway, and adds and removes fish straight away, without the jump, the net or the tip.
- A hard cap of 55 fish keeps the loop smooth on phones.
- It all runs in the visitor's browser, so frame rate depends on their device, not on the hosting tier.

### Tweaking it later

- Species roster and balance: the `SPECIES` array in [aquarium-species.ts](../src/lib/hobbies/aquarium-species.ts). The picker, the swatches and the "35 species to stock" line all follow it.
- Overall stocking feel: `PLANTED_CAPACITY_PER_GALLON` (now in [src/lib/hobbies/stocking.ts](../src/lib/hobbies/stocking.ts), unit-tested).
- How tank size scales the visuals: `fishScale()` (fish shrink in bigger tanks) and `plantFactor()` (denser planting).
- Starting community shown on load: `STARTER`.
- The look of anything: the `draw*` / `bake*` functions and the `PIX` constant.

## Reference implementation: the tide pooling island

A **"flip a rock" beach.** A pixel Pacific Northwest shoreline at low tide, scattered with rocks and driftwood logs. Tap one with the little hand cursor and it flips up to reveal a tide-pool critter, drawn as a pixel sprite, with a real fact about it. Click the same rock again and it lowers back down over the same critter. Flip everything you can, then start a new beach for a fresh set. A **field journal** tracks how many of the 40 species you've turned up and remembers them between visits. It's a collect-them-all, not a simulator.

**Files**

- [src/components/hobbies/TidePool.astro](../src/components/hobbies/TidePool.astro), the beach canvas and its caption, plus the shared [FieldJournal](../src/components/hobbies/FieldJournal.astro) row and [SpecimenCard](../src/components/hobbies/SpecimenCard.astro) reveal card, and the mounting `<script>`.
- [src/lib/hobbies/tidepool.ts](../src/lib/hobbies/tidepool.ts), the engine: scene building, the flip mechanic, every pixel sprite, the reveal card, and the journal. **Zero dependencies.**
- [src/lib/hobbies/tidepool-species.ts](../src/lib/hobbies/tidepool-species.ts), the species dataset (the single source of truth).
- [src/lib/hobbies/tidepool-photos.json](../src/lib/hobbies/tidepool-photos.json), optional real photos per species (see “Real photos in the reveal card” below).

### The species data and where the facts come from

The dataset is **40 common PNW tide-pool species**, each tagged with a `category` (16 in all: crabs, hermit crabs, sea stars, anemones, nudibranchs, chitons, snails, limpets, urchins, barnacles, mussels, sculpins, eel-shaped fish, shrimp, sea cucumbers, octopus), two display colors, a relative `size`, a `rarity`, and **two short facts**. On each reveal one fact is picked at random.

Being upfront, since the point is that anyone can learn how this works:

- **The facts are curated, not generated live.** They were written from standard references (Wikipedia and field guides such as _Between Pacific Tides_ and the Walla Walla University / Rosario intertidal key) and a representative sample was grounded with live web research while building the dataset. They favor well-established, interesting tidbits over obscure claims.
- **It's a learning game, not a textbook.** A quick review pass by someone who knows these animals is recommended before treating any single fact as authoritative; the dataset header says the same.
- **`rarity` weights which species a rock hides** when it's first flipped (common appears far more than rare). Each rock keeps that one critter for the life of the beach, so re-clicking a rock shows the same animal rather than rerolling. To turn up new species you start a new beach. The journal counts _distinct_ species found and persists them in `localStorage` (`tidepool-discovered-v1`), so it accumulates across visits. “New beach” reshuffles the layout without wiping the journal.

### How the pixel art is made

Like the aquarium, the whole beach is **drawn in code** with canvas `fillRect`, no image files in the scene itself.

- **One sprite function per category** (16 of them) draws the critter from its colors and size, snapped to the same `PIX` (4px) grid with image smoothing off. A long species list stays cheap because the art is bounded to ~16 shapes parameterized by color/size, not one drawing per species.
- **The beach is baked once per scene.** An offscreen layer holds the static parts, a sky→water→wet-sand gradient, a foam line at the waterline, dry and wet sand blotches, ripple marks, scattered pebbles and shells, rockweed tufts, and tide pools with a wet rim and a sky reflection. Each frame just blits that and draws the rocks and logs on top, so the per-frame cost is tiny.
- **Rocks and logs are detailed and varied.** Rocks are rounded boulders with moss, barnacle clusters, and pock texture in a few stone tints; logs are driftwood billets with end-grain rings, wood grain, knots, and a mossy top edge. Each gets a soft contact shadow.
- **Layout is seeded, stable, and reshuffleable.** Positions come from a seeded RNG keyed to the canvas width (so resizing doesn't reshuffle the beach), plus a “scene salt” the “New beach” button bumps to deal a fresh layout. The rock-to-log ratio is fixed (~78% rock) so every beach reads as a rocky flat instead of occasionally coming up all logs.
- It pauses offscreen and when the tab is hidden, honors `prefers-reduced-motion`, and is touch-friendly (tap a rock to flip it).
- **From the keyboard**, the beach takes focus as one stop. The arrow keys (and Home/End) walk the rocks and logs from left to right, Enter or Space flips the one they're on, and a ring marks it. A screen reader hears "Rock 3 of 14", and the reveal card hands focus back to the beach when it closes.

### Real photos in the reveal card

The reveal card shows the **pixel sprite by default and a real photo when one is available**: the sprite still appears under the rock on the beach either way.

A first find gets "New to your journal" stamped in ink on the blank card beside the picture as the card opens, the way a new specimen gets its accession stamp. It lands under the names, level with the picture's bottom edge, so it never covers the animal. A find you already have just says "Found again". The herping card is the same card and does the same ([specimen.ts](../src/lib/hobbies/specimen.ts)).

- **Where photos come from.** Optional per-species photos live in [src/lib/hobbies/tidepool-photos.json](../src/lib/hobbies/tidepool-photos.json) as `id → { photo, credit }`. The engine merges that in when it builds the card: if a photo is present it's shown with its attribution line; otherwise, or if the image fails to load (an `onerror` fallback), the card draws the pixel sprite. So partial coverage is fine and a dead link never breaks the card.
- **Licensing is the whole point.** Photos are **Creative Commons only**, with attribution shown in the card. The helper [scripts/fetch-tidepool-photos.mjs](../scripts/fetch-tidepool-photos.mjs) (`npm run fetch:tidepool-photos`) queries the iNaturalist API for each species' scientific name, restricted to `cc0,cc-by,cc-by-nc`, prefers research-grade and most-faved observations, downloads the photo to `staging/tide-pooling/` (gitignored), and writes a manifest recording the photographer, license, and source observation URL for review.
- **Two ways to serve them.** `--wire inat` writes the iNaturalist photo URLs straight into `tidepool-photos.json` (works immediately, the iNat image hosts are allow-listed in CSP). `--wire blob` instead points at your own `hobby-media` copies for self-hosting; upload `staging/tide-pooling/photos/*` to `hobby-media/tide-pooling/species/` first. Either way the attribution travels with the photo. Today it's wired with iNaturalist hotlinks (mostly CC BY-NC / CC BY, a few CC0).

## Reference implementation: the birding island (selfie to bird)

Take or upload a selfie and the page turns you into a **bird-person hybrid**: it keeps your real face from the photo and morphs/composites bird anatomy onto it. A single seamless **triangle-mesh face warp** over the face does three things at once from your own skin: it **enlarges and rounds the eyes**, **narrows the lower face** toward a bird skull, and **pulls the nose/mouth into a beak** (then shaded for 3D form). A feather crest is blended into the hairline and feathering runs down the jaw and neck. A **Shuffle** button re-rolls the bill colour + feather variation on the same selfie. It is procedural and on-device, so it reads as a stylized morph rather than the painterly reference. Given the same face + variant the result is the same hybrid (deterministic).

**How "you" shows up:**

- **It is literally your photo.** The selfie is drawn as the base, so every human feature (your eyes, skin, face shape, hair) is real — there is no synthetic face. The bird parts are overlaid and anchored to your facial landmarks.
- **Your colouring drives the plumage.** The feather crest and neck feathers are coloured from your sampled hair tone (with shaded variants); the bill colour is seeded from a small palette of believable bill colours, so two friends get different bills/plumage and any meaningful selfie change yields a new one.
- **Your features drive placement + size.** The bill is anchored between the eyes and the mouth and sized from your nose/mouth; the crest follows your hairline; feathers follow your jaw. Your iris colour is sampled too (kept for the tag/eye tint).
- It is a smooth composite over the photo (gradients, soft cast shadow, feather shapes), **not** pixel art. This is the honest ceiling of an on-device, no-AI approach: it reads as a hybrid rather than a painted artwork. (The only way to reach the painterly reference is a generative image model, which would mean sending the selfie off-device — explicitly declined to keep it private.)

**This island intentionally breaks two of the conventions above, and that is the point of documenting it here.** It is the first island with a bundled dependency and the first that ships large vendored assets. The tradeoff is deliberate: anchoring bird parts to a real face needs real facial landmarks, which a from-scratch heuristic cannot do reliably.

**How it stays safe and private:**

- **Local-only.** The selfie is read into a canvas and the landmark model runs entirely in the browser (WASM). Nothing (not the photo, not the landmarks) is ever uploaded; there is no database and the owner never sees it. The only network calls are fetching the same-origin model and WASM. The result PNG leaves the device only if the user clicks Download.
- **CSP-safe, still same-origin.** The model and WASM are self-hosted under `public/birding/`, so `connect-src 'self'` still holds. Running WASM requires `'wasm-unsafe-eval'` in `script-src` and the worker it spawns needs `worker-src 'self' blob:`; the selfie preview uses an object URL so `img-src` gains `blob:`. The camera needs `Permissions-Policy: camera=(self)` (it was fully disabled before). `.wasm` is mapped to `application/wasm` in `mimeTypes`. All of these live in [staticwebapp.config.json](../staticwebapp.config.json).
- **Lazy by route, and lazier within it.** The heavy `@mediapipe/tasks-vision` bundle and the model are dynamically `import()`ed only when the user generates a bird, so even the birding page is light until then. Other pages are unaffected.

**Input.** Two choices are always offered: live camera via `getUserMedia({ facingMode: 'user' })` (works on desktop and mobile), and a normal file upload. If the camera is denied or unavailable, it falls back to a native `<input capture="user">`, which opens the phone camera on mobile.

**Vendored assets** (under `public/birding/`):

- `face_landmarker.task` (~3.8 MB) — Google's MediaPipe Face Landmarker model (478 landmarks, including iris points), Apache-2.0. **Committed**, because it is not published to npm; committing it keeps builds offline and reproducible.
- `wasm/` — the MediaPipe vision WASM runtime, **gitignored** and copied from the pinned `@mediapipe/tasks-vision` dependency at build time by [scripts/copy-birding-assets.mjs](../scripts/copy-birding-assets.mjs) (chained into the `dev` and `build` npm scripts). Reproducible from the lockfile, so there is no need to commit ~22 MB of it.

**Files**

- [src/components/hobbies/Birding.astro](../src/components/hobbies/Birding.astro), the markup (choose / camera / busy / error / result states + privacy note) and the mounting `<script>`.
- [src/lib/hobbies/birding.ts](../src/lib/hobbies/birding.ts), the engine: camera and file input, lazy-loading the landmark model, turning landmarks into normalized features, and sampling the palette (hair, accent, skin, and iris colours). This is the only file that touches MediaPipe or the DOM.
- [src/lib/hobbies/birding-bird.ts](../src/lib/hobbies/birding-bird.ts), the **pure** feature mapping + style picker (`makeHybridStyle`, unit-tested) and the browser-only compositing renderer (`renderHybrid`) that draws the bill + feathers onto the selfie. Split out the same way `stocking.ts` is split from the aquarium.
- [src/lib/hobbies/bird-ink.ts](../src/lib/hobbies/bird-ink.ts), the ink-in: once the bird is drawn it's rebuilt as stipple, dot by dot and darkest first in its own colours (`stippleDots`, unit-tested), then the finished picture comes up through the dots. The canvas ends identical to the finished bird, and Download finishes the ink-in first.
- [src/lib/hobbies/birding-bird.test.ts](../src/lib/hobbies/birding-bird.test.ts), unit tests for the mapping and the style picker (determinism, valid colours, iris passthrough, beak-colour variety).

### Honest notes on the look

As with the aquarium, being upfront: the bill colours and feather tones are approximate, chosen by feel, not from a dataset. The bird parts are procedural canvas shapes composited over the real photo — this keeps it private and on-device, at the cost of looking like a composited hybrid rather than a painted artwork. Reaching the painterly reference would require a generative image model and sending the selfie off-device, which was deliberately not done.

## Reference implementation: the herping island (night drive)

A **road-cruising game**: a dark, wet Pacific Northwest back road scrolls toward you at night while your **headlight beam follows the pointer / finger**. Herps sit on and beside the road; as the beam nears one, a coloured **eyeshine glint** shimmers — the real herper's tell (a salamander's or frog's eyes catching the light) — faint at the edge of the beam and brightest once the light is on the animal. Steer onto it and **tap to "brake and ID"** it: the reveal card shows the common + scientific name, a real CC photo, and a fun fact, and the field journal (localStorage) tracks how many of the ~20 species you've found. It is the "dark twin" of the tide pooling flip-a-rock game: same reveal-card + journal pattern, opposite lighting.

**Files**

- [src/components/hobbies/HerpingNight.astro](../src/components/hobbies/HerpingNight.astro), the road canvas and its caption, plus the same shared journal row and reveal card as tide pooling, and the mounting `<script>`.
- [src/lib/hobbies/herping.ts](../src/lib/hobbies/herping.ts), the whole engine: the scrolling road, the headlight lighting, the eyeshine tells, the pixel sprites, tap-to-reveal, and the journal. **Zero dependencies, no runtime fetch.**
- [src/lib/hobbies/herping-species.ts](../src/lib/hobbies/herping-species.ts), the ~20-species PNW roster (salamander-forward — 12 of the 20 are salamanders/newts — led by the real animals the author has logged), each with a sprite `category`, `rarity`, `eyeshine` colour, and a couple of real facts.
- [src/lib/hobbies/herping-photos.json](../src/lib/hobbies/herping-photos.json), the CC-licensed reveal photos (falls back to the pixel sprite if a photo fails to load).

**How the lighting works.** The scene is drawn bright (road tile + animals), then a near-opaque night veil is laid over the whole canvas and the headlight beam is "punched" back out with `globalCompositeOperation = 'destination-out'` and an elliptical radial gradient centred on the beam — so only what the beam touches is visible. A warm `overlay` gradient tints the lit pool, and the car's two **headlamps** are drawn on the hood as layered round lights (dark housing ring, bright lens, hot core, soft additive glow). The **eyeshine glints are drawn on top of the veil** with an intensity that rises as the beam nears the animal (`1.25 − d/1.35`, where `d` is the elliptical distance to the beam centre), so eyes are faint at the beam's edge and brightest once lit — which is what makes sweeping the light feel like a real search. The road is a single baked tile blitted twice with a scroll offset so it slides seamlessly; the centre-line dashes are drawn live.

**How the pixel art is made.** Same approach as the other islands: six `fillRect` sprite routines (salamander, newt, lizard, frog, toad, snake) drawn pointing "up" toward the oncoming light, parameterised by each species' `color`/`accent`/`size`. The reveal card reuses the sprite for its fallback thumbnail.

**Salamander-forward on purpose.** The whole conceit is finding salamanders on a wet night, so a `CATEGORY_WEIGHT` table biases spawning heavily toward caudates (salamander 10, newt 7, frog/toad 2, snake/lizard 1.2), multiplied by each species' rarity weight. So the road is mostly salamanders with the occasional frog and a rare snake, and the ~20-species journal fills salamander-first.

**Where the species and facts come from.** Hand-picked PNW herps you'd actually meet cruising a rainy road west of the Cascades, led by the salamanders the author has logged on iNaturalist (Ensatina, Western Red-backed, Dunn's, Northwestern, Rough-skinned Newt, Pacific Giant), plus more PNW caudates (Cope's Giant, Cascade Torrent, Van Dyke's, Clouded, Western Tiger, Long-toed). Facts are curated from standard references and are meant to be interesting, not authoritative. The American Bullfrog is flagged `nonNative`, and its card reads "Non-native" where others read "New to your journal" or "Found again".

**Real photos.** Identical pattern to tide pooling. The helper [scripts/fetch-herping-photos.mjs](../scripts/fetch-herping-photos.mjs) (`npm run fetch:herping-photos`) first tries each species' iNaturalist **taxon default photo** — the community-curated, clearly-representative ID shot — then falls back to research-grade / most-faved observations, all restricted to `cc0,cc-by,cc-by-nc`. `--place 46` prefers Washington photos, and the default `--size medium` (~500px, ~120KB) is the sweet spot for the card banner — big enough to look crisp, a quarter the weight of `large`. `--wire inat` writes the iNat photo URLs into `herping-photos.json` (allow-listed hosts); `--wire blob` points at self-hosted `hobby-media` copies instead. Attribution travels with each photo and is shown in the card.

**Snappy reveals (photo preloading).** So the reveal card feels instant, the engine **preloads every species photo in the background** once the island mounts (on `requestIdleCallback`, so it never competes with the initial page load). By the time you find your first animal the image is already in the browser cache, so the card shows a real photo with no per-reveal network round-trip. This — plus the right-sized `medium` images — is why reveals are immediate rather than waiting on iNaturalist's CDN. (The site itself is served from Azure Static Web Apps' global CDN; only these CC photos come from iNaturalist, and preloading hides that hop. If you ever want to drop the third-party dependency entirely, `--wire blob` serves your own copies from the `hobby-media` blob instead.)

Like the other islands, everything is **drawn in code**, the loop pauses offscreen and when the tab is hidden, and it honors `prefers-reduced-motion` — which **parks the car** (the road stops moving) and degrades to a stationary headlamp-sweep so there's no vestibular motion. The beam still follows the pointer there; it just jumps to where it's aimed instead of easing.

**From the keyboard**, the road takes focus as one stop: ← and → steer the beam, and Enter or Space stops for the unfound animal nearest the middle of the beam (or says "Nothing in the beam yet." through a polite live region).

## Reference implementation: Narrow nature (daily puzzle)

A daily puzzle that asks you to read a **community** rather than a single organism. Six species were
all recorded at one real place in one month; they are revealed most-widely-recorded first, so the
opening line narrows almost nothing and the last one is often local enough to name the valley. The
visitor drops a pin on a world map, picks a month, and scores on distance, month accuracy, and how
few species they needed.

This is the inverse of a "what is this organism" quiz. One species gives you a range; an assemblage
gives you a point, which is how field ecologists actually read a habitat (indicator species).

There are two modes on one board. **Today's list** is the same round for everyone, picked by date.
**More lists** deals up to ten more a day per browser, from a separate set of places.

**Files**

- [src/lib/hobbies/day-list-map.ts](../src/lib/hobbies/day-list-map.ts), the map: zoom and pan,
  gestures, the terrain tiles and their palette, the graticule, and the camera moves the reveal uses.
- [src/lib/hobbies/day-list-borders.ts](../src/lib/hobbies/day-list-borders.ts), the country and
  state borders drawn over the map, from the files in `src/lib/hobbies/day-list-borders/`.
- [src/lib/hobbies/day-list.json](../src/lib/hobbies/day-list.json), the daily set, and
  [day-list-extra.json](../src/lib/hobbies/day-list-extra.json), the More lists set.

### How the page reads

People who tried the first version couldn't tell what the game was. It had three explanations with
three different metaphors, and the cost of each extra species was never shown. The page now leads
with the rules and uses one set of words throughout:

- **Premise, then steps.** The hobby `intro` is the premise in one line ("Six species were all seen
  at the same place in the same month. Guess where and when."). Under it, "How to play" is four
  numbered steps in the largest body text on the page. They use the same words as the controls
  ("show the next one", "tap the map", "Lock it in") and say that there's only one guess.
- **The six species are the board.** Six squares, three to a row at every width, sit under a
  "Most common → Rarest" rule. A shown species gets its photo, name, Latin name and worldwide
  sighting count. The next square is the button and says what it costs ("−600 points"), and the
  rest wait with their number. The photos are up to 360px across, so on a laptop the map sits below
  them. That's more than iNaturalist's 500px medium size holds on a sharp screen, so each photo
  also offers the 1024px large size (`photoSrcset`) and the browser picks whichever the screen
  needs. Preloads ask for the same size, so a reveal is still instant.
- **Photo credits are a closed footnote.** A photographer's name can give the place away, so
  credits aren't under the photos. They sit in a "Photo credits" `<details>` at the foot of the
  page, which lists only the photos on the board (`photoCredits`) and closes again whenever a new
  round loads. CC BY and CC BY-NC are still met, since the credit is on the same page as the photo.
- **The stakes stay on screen.** The guess panel opens with "Up to 6,000 points", the most a perfect
  guess can still score (`bestPossible`). It rolls down with each species you ask for (`rollTo`).
  The panel is under the map, usually off screen when you ask, so the price is also stamped in red
  on the corner of the species it bought (`stamp()` in [motion.ts](../src/lib/motion.ts)). It slams
  down, sits for half a second, then drifts down toward the points and fades. Once the answer is down,
  the verdict ("Spot on", "Not quite"...) is stamped in ink on the map's top left corner with the
  distance under it, and stays there with the result.
- **The result is a receipt.** "Lock it in" swaps the panel for the verdict, the place and where the
  points came from: Place (distance, and how many species were showing), Month, Total. The full list
  with facts follows under the board. Wikipedia's bracketed Latin name and IPA pronunciation are
  trimmed from the facts at render time (`tidyFact`), so the JSON keeps the source text.
- **The answer lands in one beat.** The map glides to frame the pin and the place together
  (`CAMERA_MS`, 650ms, no closer than 48x), then a dashed line runs from the pin to the nearest edge
  of the place over 600ms (`LINE_MS`), the same point the distance is measured to. The "km off"
  figure and the total start counting with `rollTo` as soon as you lock in, and land as the line
  arrives and the boundary closes. The line goes the short way round, so a pin in Hawaii reaches
  Japan off one side of the map and back in the other, and the distance is written on it once it's
  long enough to carry a label. Then the boundary strokes in (`BOX_MS`, 300ms), the place name
  appears, and the species still hidden fill in 70ms apart. Under `prefers-reduced-motion`, and for
  a finished round restored on load, everything is drawn at once. After locking in, the map scrolls
  into view if it's off screen, so on a phone the line can be watched with the result right under
  it.
- **Native controls.** The months are radio inputs, so arrow keys and screen readers work with no
  extra code. The lock button stays outlined until there's a pin and a month, then turns ink. A pin
  drops on a tap that didn't move, so a scroll, pan or pinch that starts on the map never drops one.
- **Keyboard and screen readers.** Revealing a species from the keyboard moves focus to the next
  square, and a polite live region reads out the new species and the new ceiling. Locking in moves
  focus to the result. A finished round restored on load doesn't move focus or replay anything.

The layout takes its structure from the daily game Originle (a guess card with the stakes on it, and
a reveal button that shows its cost) and redraws it in the archive's ink on paper.

### The map

The map is plate carrée, the projection the puzzle boundaries are published in, so a pin, a
boundary and the terrain line up with no reprojection. It's one canvas, drawn by
[day-list-map.ts](../src/lib/hobbies/day-list-map.ts), with the borders from
[day-list-borders.ts](../src/lib/hobbies/day-list-borders.ts) over the terrain.

**Zooming.** Zoom runs from the whole world (1x) to 64x, where a pixel is about a kilometre on a
laptop and the terrain is still sharp. All of these work:

| Input                      | Does                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Pinch (touch)              | Zooms around the fingers, and two fingers pan                                                                                                  |
| Double-tap or double-click | Zooms in 2x there (and drops the pin there, like any tap)                                                                                      |
| `+` and `−` buttons        | Zoom 2x, toward the pin if there is one                                                                                                        |
| Ctrl or ⌘ + scroll         | Zooms around the pointer. A trackpad pinch arrives this way, and Safari's as `gesture*` events                                                 |
| Plain scroll               | Scrolls the page. If the mouse was just moved onto the map, a "Hold Ctrl and scroll to zoom" hint shows for a moment, the way embedded maps do |
| Keys                       | `+`, `−` and `0` (whole world). Arrows move the pin, by less the further in you are; after the answer they pan instead                         |

On touch, one finger scrolls the page while the whole world is showing (`touch-action: pan-y`) and
pans the map once you've zoomed in (`touch-action: none`), the same deal as the herp map. A scale
bar shows from 1.5x, for the latitude in the middle of the view. "Whole world" zooms back out, and
after the answer "Back to your guess" reframes the pin and the place. On a phone the map runs edge
to edge.

**Terrain.** The tiles are Natural Earth's "Gray Earth with Shaded Relief, Hypsography, and Flat
Water" at 1:10m (21600 × 10800, public domain), cut by
[build-day-list-relief.mjs](../scripts/build-day-list-relief.mjs) into a six-level pyramid of
256px WebP tiles: about 2,900 files and 7.6 MB, committed under `public/day-list/relief/v1/`. Tiles
that would be all sea aren't written; the manifest says which exist and the map paints open water
itself. A tile is one grey channel: 0 is water and 48-255 is the land's relief and height shading.
The browser maps that grey through the page palette (`buildLut`), so one set of tiles serves light
and dark mode and follows the theme toggle. Light mode keeps the archive's tan sea and paper land
shaded toward ink. Dark mode turns it round, with a sea darker than the page under land lit a few
steps toward ink, because relief shaded down from near-black has nowhere to go.

The map loads the coarsest level first and keeps it underneath, so a zoom never shows a blank, then
sharpens with the level the zoom needs (and the one under it, which arrives four times faster).
Before any tile arrives, the coarse coastline from `src/lib/geo-land.json` stands in. About 100
decoded tiles are kept and the oldest are dropped. The tiles are same-origin on purpose: the map
reads their pixels to recolour them, which a tile from another origin would block without CORS.
`staticwebapp.config.json` serves them as immutable, so **bump `VERSION` in the build script when
the tiles change**.

```bash
npm run build:day-list-relief   # downloads ~46 MB to .cache/natural-earth once, then ~40 seconds
```

The free Azure Static Web Apps plan allows 15,000 files per deployment. The tiles are about 2,900
of them, and the photo variants (12,000+) move to Blob Storage before deploy, so there's room, but
another zoom level from a finer source would be about 8,000 more files.

**Borders.** Country and state borders are lines drawn over the tiles, from Natural Earth's 1:10m
boundary lines (v5.1.2, public domain).
[build-day-list-borders.mjs](../scripts/build-day-list-borders.mjs) joins Natural Earth's 53,000
fragments into about 8,700 lines and simplifies them into three levels of detail, each to within
half a pixel at the closest zoom it's drawn at. Level 0 is one file (52 KB gzipped) that loads with
the map. Levels 1 and 2 are cut into 60° and 30° cells, the largest 45 KB and 74 KB gzipped, and the
map loads only the cells in view, drawing the coarser level until they arrive. The files (about
920 KB in all) sit in `src/lib/hobbies/day-list-borders/` and load as Vite chunks, so they get
hashed names and the immutable caching `/_astro/` already has. A file groups its lines by kind and
zoom, each group one polyline-encoded string, so the map strokes a group in one go.

Country borders show at every zoom, with disputed and indefinite ones dashed. State lines stay off
at world view, then fade in country by country once that country's states average about 10 pixels
across. On a laptop-width map that's about 1.2x for the US, 2x for Mexico, 3.4x for Germany and 16x
for the UK's councils. Lines between regions, like France's regions as against its departments, go
by the size of the regions. Natural Earth's own `MIN_ZOOM` favours the big federations, which left
Mexico blank beside a fully drawn US, so the script works the zoom out from the state polygons
instead. It also drops the state lines Natural Earth draws across bays and straits, like Chesapeake
Bay, by testing both sides of each line against those polygons, which stop at the coast.

```bash
npm run build:day-list-borders   # downloads ~62 MB to .cache/natural-earth once, then ~10 seconds
```

The script overwrites its files and deletes only the ones it no longer makes. Deleting the whole
folder loses the dev server's watch on it, and the dev server keeps serving the old lines until it
restarts.

### More lists

**Ten a day, from their own places.** More lists deals from
[day-list-extra.json](../src/lib/hobbies/day-list-extra.json), 63 places that the daily rotation
never uses, so playing extras can't spoil a future daily list. The builder refuses to write if the
two sets share a place, and a test checks it too. The cap is ten a browser a day (`EXTRA_PER_DAY`):
the pool is finite, so without one a keen player would run through it in an afternoon and start
seeing repeats. The data is a dynamic import, so the daily page doesn't download it until More
lists is opened.

**What it remembers.** `localStorage` key `day-list-extra-v1` holds today's played places and
scores, every place this browser has ever started (`seen`), and the round in progress. A new list
is a place not yet seen. Once all 63 have been played it goes back to the one started longest ago.
The count resets at the date change; a list left half-played carries over as the next day's first.
Today's list (`day-list-v2`) now remembers a round in progress as well, so a reload can't wipe how
many species you've seen. Older saves from before that, which were only ever written at lock-in,
still read as finished.

**Where it shows.** The board's title is a pair of underline tabs, "Today's list" and "More lists"
(`initUnderlineTabs`, the Cult UI direction-aware-tabs port). The daily result offers "Play more
lists", and each extra result offers "Next list" until the tenth, which shows the day's total
instead. Extras have no share button, because the share string is about the daily list. A link to
`/hobbies/narrow-nature/#more-lists` opens straight onto More lists.

### Accuracy rules

The puzzle is aimed at people who know the species, so the builder is strict about provenance.

- **Locations are real iNaturalist places with published boundaries**, not arbitrary circles. Every
  query is anchored to a place id, and the reveal links to that place so a player can check it.
- **Scoring is against the boundary, not a centre point.** Madagascar is 1,500 km long; a pin on its
  north coast is a correct answer, and measuring to a centroid would call that a 700 km miss. A pin
  anywhere inside the bounding box scores as exact.
- **Every clue is a research-grade record** from that place in that month, with at least two local
  observations. A single record is too often a vagrant, an escape, or a misidentification.
- **Animals are preferred over plants.** A birder can picture a kookaburra and reason about where it
  lives; "Parry's Townsend-daisy" is a dead end for all but a handful of botanists. Animals sort
  ahead of plants inside every abundance band, a round allows at most two botanical clues, and the
  final band is reserved for animals entirely, because that last line is the one that gives the
  place away.
- **Species are labelled native, introduced or endemic for that place**, from iNaturalist's own
  establishment means. This matters: the Laughing Kookaburra on the Cradle Mountain list is
  introduced to Tasmania, and presenting it as a native indicator would be wrong. iNaturalist flags
  each record against every place that contains it, so one stray listing can mislabel a species: a
  user-made place called Mallards introduced, which tagged them introduced in the Danube Delta,
  Iceland and four other rounds. So the label goes with the majority of the place's own flagged
  records (175 native Mallard records in the Danube Delta against 3 introduced). An endemic label
  also has to hold worldwide: at least half the species' records anywhere must be flagged endemic.
  That drops island listings of a local subspecies, like Grey Wagtail on Madeira (2% worldwide),
  and keeps real endemics, which run from 66% (Red-necked Wallaby, introduced abroad) to 100%.
- **Facts come from the taxon's Wikipedia summary** and ship with the article link so they can be
  checked. iNaturalist returns those URLs with raw spaces in the title, which do not resolve, so the
  builder normalises them.
- **Photos are openly licensed only.** The builder walks `default_photo` then `taxon_photos` until it
  finds an acceptable licence, because the best-known species often have an all-rights-reserved lead
  image. The photographer and licence travel with the photo and are rendered under it on the
  board, since CC BY and CC BY-NC require attribution.
- **Clue order uses worldwide observation counts**, which measure how often a species is _recorded_,
  not how widespread it is. A well-studied European species out-records an equally widespread African
  one. The UI says this plainly rather than implying a range map.
- **A round is rejected** if its opening clue has fewer than 120,000 worldwide observations, because
  without a genuinely cosmopolitan opener the puzzle starts half-solved.

**Rebuilding the puzzles.**

```bash
npm run build:day-list                       # daily set
npm run build:day-list -- --extra            # More lists set
npm run build:day-list -- --retag [--extra]  # refresh the labels only, same species
```

A full build takes around an hour per set: the script throttles to one request a second, and it
tries up to eight candidates per abundance band so a species without a usable photo costs a request
rather than a whole round. Failed calls retry with a widening pause, because a build is well over a
thousand requests and a dropped socket is a matter of when rather than if. It refuses to write a set
with fewer than ten rounds. Rebuilding the daily set changes the rounds people are partway through,
so do it near midnight. `--retag` keeps every round's species and only relabels native, introduced
and endemic, so it's safe to run any time (about ten minutes for both sets).

**No runtime API calls.** Puzzle data ships as JSON, the terrain ships as same-origin tiles, and
photos load straight from the iNaturalist CDNs already allow-listed in `img-src`, so the island costs
nothing per play and keeps working if the API is down.

**One gotcha worth remembering.** The species squares, the result receipt and the full list are all
built by the script at runtime, so Astro's scoped styles never reach them. The component uses
`<style is:global>` with every selector namespaced under `dl-` instead.

## Photo galleries (`hobby-media`)

Any hobby can show a photo gallery, a hero image up top plus a thumbnail grid, each click opening the full-resolution original in the same PhotoSwipe lightbox the photography pages use. It's driven by the optional `media` field on the hobby (`hero` + `gallery`), with `mediaTitle` setting the heading (e.g. "My tank"). The render lives in [src/pages/hobbies/[slug].astro](../src/pages/hobbies/%5Bslug%5D.astro) and only appears when `media` is present.

**Where the photos live.** A dedicated **`hobby-media`** blob container (public read), separate from `originals/`. This is deliberate: the photography prebuild scans `originals/` and turns every folder there into a photography session, so hobby photos must live elsewhere to stay off the photography side. The container is defined in [infra/modules/storage.bicep](../infra/modules/storage.bicep). The site's CSP already allows blob images, so nothing else needs changing to display them.

**Adding photos to a hobby:**

1. Drop full-res files in `staging/hobby-<slug>/` (e.g. `staging/hobby-aquarium-keeping/`).
2. Run the uploader:
   ```bash
   AZURE_STORAGE_ACCOUNT=<account> node scripts/upload-hobby-media.mjs <slug> [--hero <file>]
   ```
   For each photo it uploads a **full-resolution** blob (`full/…`, opened in the lightbox) and a smaller **display** JPEG (`display/…`, shown inline, max 1600px wide), reading orientation and true dimensions with `sharp`. It then writes the `media` block (hero + gallery) into `src/content/hobbies/<slug>.json`. The full-resolution files go through the private `incoming` container and are published by the next build, so their lightbox links work once that build has run.
3. Optionally add `caption` text in the JSON, then commit + push. The gallery goes live on the next build. A photo without a caption is announced as "Open full-resolution photo", so captions are what make the gallery describable to a screen reader.

Web-friendly originals (JPG/PNG/WebP) are published byte for byte as uploaded, with one exception: hobby photos are often taken at home, so the build removes any GPS position before they're public (metadata only, the image is untouched; [security.md](security.md#photo-locations)). HEIC/TIFF, which browsers can't show, become one full-size JPEG at quality 95 with full colour resolution, the same settings the photography build uses (HEIC needs `libheif` available to `sharp`). The `--hero` flag (or the first file alphabetically) chooses the large image at the top.

## A personal element on every hobby

The section pairs each playful interactive with something **real and personal**, so it remains a window into the actual hobby and not just a collection of toys:

- **Aquarium** → real photos of the tank (the `hobby-media` gallery above).
- **Tide pooling** → the species photos in the game are real CC-licensed shots, plus a live grid of the author's own **iNaturalist observations** at the bottom of the page.
- **Fishing** → a gallery of the author's real catches, paired with the same species sprites used on the maps.
- **Birding** → a live **life list** built from the author's real iNaturalist sightings (rarest species featured with a fun-fact/range blurb), plus a written **"spark bird"** story shown beside the author's own observation of that bird.
- **Herping** → the game's reveal photos are real CC-licensed shots, and below the game a live **world map** heat-maps every reptile and amphibian the author has logged on iNaturalist, on a coarse grid; tap a country (or the US, then a state) to zoom in to observation pins and a details grid, with a Reptiles/Amphibians toggle.
- **Hiking** → landscape families and page copy grounded in the author's Cascades, China, Norway, and Himalayan hiking. Connecting each family directly to real trip photos is a deliberate follow-up iteration.

New hobbies should follow the same pattern: build the game, then add a genuine personal artifact (photos, a map of real trips, real observations, and so on).

### iNaturalist observations embed

The tide pooling page ends with a live grid of the author's real observations, each linking out to iNaturalist.

- **Component:** [src/components/hobbies/INatObservations.astro](../src/components/hobbies/INatObservations.astro) + logic [src/lib/hobbies/inaturalist.ts](../src/lib/hobbies/inaturalist.ts). It's reusable: any hobby switches it on with an optional `inaturalist` block in its content JSON:

  ```json
  "inaturalist": {
    "userId": "trumanbrown",
    "url": "https://www.inaturalist.org/observations?user_id=trumanbrown",
    "heading": "My tide pooling observations",
    "blurb": "…",
    "iconicTaxa": "Animalia,Mollusca,Actinopterygii"
  }
  ```

- **It's lazy and CSP-safe.** The grid stays empty (skeleton tiles) until the section scrolls near the viewport, then a `fetch` to the public iNaturalist API fills it in; thumbnails link to each observation and a “View all on iNaturalist” button links to the full profile. The script is an Astro-processed module, so it satisfies `script-src 'self'`.
- **Filtering to the right critters.** iNaturalist has no “tide pooling” concept, so the embed filters by `iconic_taxa`, the broad taxonomic buckets. Tide pooling uses `Animalia,Mollusca,Actinopterygii`, which captures crabs, sea stars, anemones, and worms (Animalia), snails/chitons/nudibranchs (Mollusca), and fish (Actinopterygii) while dropping the birds, mammals, insects, and plants from the same account. For tighter curation, make an iNaturalist project and filter by it (the component also accepts a `taxonId`).
- **CSP additions.** Showing this required allow-listing iNaturalist in [staticwebapp.config.json](../staticwebapp.config.json): the API host in `connect-src` (`https://api.inaturalist.org`) and the two photo CDNs in `img-src` (`https://static.inaturalist.org`, `https://inaturalist-open-data.s3.amazonaws.com`). Those are the only third-party hosts the hobbies section talks to, and they're documented in [docs/security.md](./security.md).

### Birding life list and spark bird

The birding page reuses the same live-iNaturalist approach in two richer forms. Both are lazy and CSP-safe (same hosts as above — no new allow-listing needed), and both degrade gracefully if the API is unavailable.

- **Life list.** [src/components/hobbies/BirdingLifeList.astro](../src/components/hobbies/BirdingLifeList.astro) + [src/lib/hobbies/birding-life-list.ts](../src/lib/hobbies/birding-life-list.ts). Switched on with an optional `lifeList` block:

  ```json
  "lifeList": {
    "userId": "trumanbrown",
    "url": "https://www.inaturalist.org/observations?user_id=trumanbrown&iconic_taxa=Aves",
    "heading": "My birding life list",
    "blurb": "…",
    "iconicTaxa": "Aves",
    "featured": 6
  }
  ```

  It calls `/observations/species_counts` for the full list, sorts by the species' **global** iNaturalist `observations_count` (fewer records worldwide = more unique), features the `featured` rarest as cards, and batch-fetches `/taxa/<ids>` for their Wikipedia summaries to use as the fun-fact/range blurb. It also pages `/observations` (most-faved first) to show one of the author's **own** photos per species rather than a generic representative one. The rest are grouped by **taxonomic family** (largest family first) into a compact list. "Rarity" here is global record count, not a formal conservation status.

  The family grouping needs no extra API calls: `species_counts` already returns each species' `ancestor_ids`, and [src/lib/hobbies/bird-families.json](../src/lib/hobbies/bird-families.json) maps every iNaturalist bird-family taxon id to its name, so the grouping is computed client-side and stays live. Regenerate that file with `node scripts/fetch-bird-families.mjs` if iNat ever adds or renames a family.

- **Spark bird.** [src/components/hobbies/BirdingSpark.astro](../src/components/hobbies/BirdingSpark.astro) + [src/lib/hobbies/birding-spark.ts](../src/lib/hobbies/birding-spark.ts). Switched on with an optional `spark` block:

  ```json
  "spark": {
    "userId": "trumanbrown",
    "taxonId": 4838,
    "heading": "My spark bird",
    "species": "Black Oystercatcher",
    "scientificName": "Haematopus bachmani",
    "story": ["First paragraph…", "Second paragraph…"]
  }
  ```

  The written `story` is server-rendered (it never depends on the network); the script pulls the author's most recent observation of `taxonId` and shows that photo, place, and date beside it.

### Herping reptiles & amphibians map (world → country/state, heatmap + pins)

The herping page ends with a live, **real geographic map** of the author's reptile and amphibian observations: a world heat map you can drill from world → country (or the US → state) down to observation pins.

- **Coarse on purpose.** An unobscured iNaturalist observation is exact to metres, a reptile's spot is what a collector looks for, and a backyard observation would map the yard. So every coordinate is snapped to a **0.1° grid (about 11 km)** before it's drawn, zoom stops at 6×, and places are cut down to a town or region ([src/lib/hobbies/inat-place.ts](../src/lib/hobbies/inat-place.ts)). The same place rule applies to the observations grid and the spark bird. For a site you'd rather keep vaguer still, set the observation's geoprivacy to **Obscured** on iNaturalist.

- **Component:** [src/components/hobbies/INatHerpMap.astro](../src/components/hobbies/INatHerpMap.astro) + logic [src/lib/hobbies/inat-herp-map.ts](../src/lib/hobbies/inat-herp-map.ts). Switched on with an optional `herpMap` block:

  ```json
  "herpMap": {
    "userId": "trumanbrown",
    "url": "https://www.inaturalist.org/observations?user_id=trumanbrown&iconic_taxa=Reptilia,Amphibia&subview=map",
    "heading": "My reptiles & amphibians, mapped",
    "blurb": "…",
    "limit": 300
  }
  ```

- **Real geography, still no map tiles.** All outlines are committed vector geometry, not tiles or a dependency, so the offline/CSP ethos holds. [scripts/build-herp-geo.mjs](../scripts/build-herp-geo.mjs) (`npm run build:herp-geo`) downloads two public-domain sources once — a US-states GeoJSON and **Natural Earth 110m admin_0 countries** — Douglas–Peucker-simplifies each outline (states finely, countries coarsely for world scale), and writes lon/lat rings + a bbox per state and per country (keyed by ISO A2) to [src/lib/hobbies/herp-geo.json](../src/lib/hobbies/herp-geo.json) (~150KB). The runtime projects those rings (equirectangular, cosine-corrected for latitude) onto a `<canvas>`; only the iNat API + already-allow-listed photo CDNs are contacted at runtime.
- **Three zoom levels.**
  - **World** (default): every country is drawn, those with data tinted, and all observations' real `geojson.coordinates` are accumulated into an offscreen alpha buffer and colourised (blue → lime → yellow → orange → red by density) so clusters glow hot — the author's light up the US Pacific NW, Hawaii, and China. The points are the grid-snapped ones, never the raw coordinates. Tap a highlighted country to zoom.
  - **US states**: tapping the US opens a US map (state outlines + a Hawaii inset) with the same heat map; tap a state to zoom. (Other countries skip straight to their detail view.)
  - **Country / state detail**: the region's outline blown up with a **pin per observation on the 0.1° grid**, colour-coded by class (amber = reptile, blue = amphibian), a legend, and a "← Back" button that walks the levels back up.
- **How regions are assigned.** Each observation is bucketed to a **country by point-in-polygon** of its exact coordinates (in memory only, before snapping) against the baked country rings (with a US fallback when a US state matched), and to a **US state** via its `place_ids` intersected with iNaturalist's known state place ids (admin_level 10 — e.g. Washington is `46`). Point-in-polygon also drives the map click + hover tooltips.
- **Grid with real info before you leave.** Below the map, the selected region's observations render as cards showing the **common name, scientific name, observed date, and town or region**, with an "approx." tag when iNaturalist obscured the coordinates (many sensitive herps are). Each card links out to its iNaturalist observation.
- **Reptiles vs. amphibians.** Two API calls (`iconic_taxa=Reptilia` and `=Amphibia`) back an **All / Reptiles / Amphibians** toggle that re-filters the heat map, pins, tints, and grid at every level. It's lazy (fetches on scroll), CSP-safe, and degrades gracefully if the API is unavailable.
- **Zoom + pan (any level).** A `zoom`/`panX`/`panY` transform wraps each view's base projection so you can blow up tightly-clustered areas, up to 6× (further would only spread the grid out). It's driven by **pinch on mobile, scroll-wheel on desktop, on-screen + / − / reset buttons, and drag-to-pan**, with renders throttled through `requestAnimationFrame` for smooth gestures. On touch, the canvas's `touch-action` is `pan-y` at fit (so a one-finger drag still scrolls the page and a tap still selects) and flips to `none` once zoomed in (so one finger pans the map); two-finger pinch works in both. Zoom resets when you change region.

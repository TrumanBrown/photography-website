# Hobbies section

A second, optional top-level section beside Photography. Photography lives at `/photographs/`, and the front door at `/` leads into both. Hobbies lives at `/hobbies` with one page per hobby, each able to mount a self-contained interactive "island."

This doc covers how the section is wired, how to add a hobby, the conventions every interactive follows, and the aquarium island as the original reference implementation. It's written so a future session, or you, can pick the work back up cold.

> Status: the shell, six islands and one daily puzzle are live: Aquarium keeping, Tide pooling, Fishing, Birding (selfie to bird), Herping (night-drive road cruising), Hiking (trail builder and postcard studio), and Narrow nature (a daily where-and-when puzzle, called Day list in the code and mounted by its `dayList` content rather than an `interactive` island). More are planned (a travel map and a repo explorer), to be built one at a time.

How it differs from the Photography (`sessions`) collection:

- Hobbies JSON is hand-authored and committed to git. Sessions are gitignored and generated by `scripts/prebuild.mjs` from Blob Storage. Core hobby content and interactive engines need no prebuild or Azure service; optional photo galleries and optimized catch-photo variants use the documented `hobby-media` Blob pipeline.
- A hobby page doesn't show the sessions sidebar. `BaseLayout` takes a `section` prop (`'photography'` default | `'hobbies'`); when `'hobbies'` it hides the `ArchiveRail` session list and its mobile drawer, and the Header highlights its "Things to try" nav item (the same two labels as the archive rail: "Photographs" and "Things to try").

The `sections.hobbies` flag only controls the header nav link (discoverability). The pages still build when it's off, so turning it off "ships dark" without removing the routes.

## Adding a hobby

1. **Create the content entry** `src/content/hobbies/<slug>.json`:

   ```json
   {
     "title": "Hiking",
     "summary": "Short blurb shown on the hobby card.",
     "intro": "A sentence or two shown on the hobby page above the interactive.",
     "plateNote": "Liberty Bell · Washington Pass, July 2026",
     "order": 3,
     "interactive": "pixel-hike"
   }
   ```

   - `slug` comes from the filename (`hiking.json` → `/hobbies/hiking`).
   - The card's picture is a stipple plate drawn from one of your photos: add a subject named after the slug to the [stipple-plates skill](../.github/skills/stipple-plates/SKILL.md) and render it into `src/assets/plates/`. `plateNote` is the caption under it. `npm test` fails while a hobby is missing any of its plates.
   - `order` sorts the landing grid (ascending); entries without `order` fall to the end, alphabetical.
   - `interactive` is one of the enum values in the schema, or omit it for a static page.

2. **(Optional) build the interactive island**: see the pattern below. If you only want a static page (text/photos), skip this and leave `interactive` unset.

3. **Wire the island** in [src/pages/hobbies/[slug].astro](../src/pages/hobbies/%5Bslug%5D.astro): import the component and add a branch:

   ```astro
   {interactive === "pixel-hike" && <PixelHike />}
   ```

4. **(Optional) give the card an opening scene** in `src/lib/scenes/`, keyed by the slug in [index.ts](../src/lib/scenes/index.ts). See [Opening scenes](#opening-scenes). Without one, clicking the card plays the plain dive into its plate.

That's all a dependency-free hobby without a photo gallery needs. Optional media, third-party data, or a new package may also need the documented Blob, CSP, dependency, or CI updates.

## Interactive island conventions

Every island follows the same rules so they stay cheap, safe, and consistent with the rest of the site:

1. **Self-contained core.** The playable interaction should not depend on a runtime API: geometry and game data are baked in, and graphics are procedural or local assets. Optional personal-data and CC-photo enrichments may use the allow-listed iNaturalist API/CDNs, but they load lazily and degrade without breaking the island. Birding separately bundles and self-hosts its landmark model; see [the birding implementation](#reference-implementation-the-birding-island-selfie-to-bird).
2. **CSP-safe by construction.** Use Astro's processed `<script>` (with `import`), never `is:inline`. Astro emits it as a same-origin module under `/_astro/…js`, which satisfies the strict `script-src 'self'` policy in [staticwebapp.config.json](../staticwebapp.config.json). There are no per-script hashes to maintain. (Confirmed in the build output: the aquarium ships as `/_astro/AquariumTank.astro_…js`.)
3. **Lazy by route.** An island's script only loads on its own `/hobbies/<slug>` page, so Photography pages stay zero-JS and the build stays light.
4. **Mobile-first-ish.** An island works on touch, even if it's richer on desktop, which is the same bar as the photography section. That means responsive sizing (`ResizeObserver`), touch input (`pointerdown`, native range inputs), and pausing offscreen.
5. **Keyboard too.** Anything a tap does needs a key. A canvas sits in a frame with `tabindex="0"`, `role="application"` and an `aria-label` that names the keys (the canvas itself is `aria-hidden`); the frame, not the canvas, takes focus because the frame's `overflow: hidden` would clip a ring on the canvas. Arrow keys move a pick that's ringed in dark and light while the frame has `:focus-visible`, Enter or Space does what a tap would, and a `sr-only` `aria-live="polite"` line says what's picked. Dialogs the toy opens hand focus back to the frame. Tide pooling, herping and the fishing maps work this way, the day-list map uses the same focusable frame, and the hiking canvas has its own arrow-key editing.
6. **Minimal dependencies.** Prefer vanilla + canvas/SVG. Add a small library only if it meaningfully improves graphics/accuracy, and document it here.
7. **Still under a scene.** While a card's opening scene plays over the page (`landing-scene` on `<html>`, see [Opening scenes](#opening-scenes)), an island keeps to its first frame: don't start an animation loop while `covered()` ([covered.ts](../src/lib/covered.ts)), and start it from `whenUncovered()`. A canvas that's read back with `getImageData` while the page loads is made with `{ willReadFrequently: true }`, so reading it doesn't hold up the GPU the scene is drawing with.
8. **The canvas follows the page too.** A toy may keep its own art colours inside its frame, but whatever a canvas draws around or on top of the art (the ground, labels, rules, rings) uses the tokens read off `<html>`, and a `MutationObserver` on its `class` redraws it when the theme toggle flips them. No fixed light ground in dark mode. Text on a canvas is Libre Franklin 300 or 400 from `canvasFont()` in [canvas-font.ts](../src/lib/canvas-font.ts), drawn once `canvasFontReady()` resolves: a canvas paints with whatever face is loaded when it draws and never repaints by itself, so text drawn sooner keeps a fallback face for good. A draw loop leaves its text out while `canvasFontIsReady()` is false and redraws when the promise resolves; a one-off render, like the hiking postcard, awaits it. Labels and rules that must stay sharp are drawn at the screen's resolution, over any art that's scaled up.

Markup lives in a `.astro` component under `src/components/hobbies/`; non-trivial logic lives in `src/lib/hobbies/<name>.ts` and is imported by the component's `<script>`. The component binds to the engine via `data-*` hooks, so the engine owns behavior and the markup stays static.

## Shared parts and the look

The hobby pages are dressed like the photography archive: ink on paper, hairline rules, tracked caps labels, square corners, one typeface. Every color comes from the tokens in [src/styles/global.css](../src/styles/global.css) (`--paper`, `--band`, `--ink`, `--ink-2`, `--ink-3`, `--rule`, `--rule-soft`, `--hover`), which switch for dark mode on their own. The same tokens are Tailwind colors (`text-ink-2`, `border-rule`, `bg-band`, `hover:bg-hover`...) in [tailwind.config.mjs](../tailwind.config.mjs). The Astro Tailwind integration reads that config once, so restart `npm run dev` after editing it.

The hobby UI leaves out things that read as generated: Tailwind's default hues (sky, emerald, lime, amber...), pills and `rounded-*` chrome, drop shadows and blur, an icon on every control, emoji, a badge above a headline, and Title Case. The toys' own pixel art and photographs are the only color.

A few interaction details come from React component libraries (Cult UI, Watermelon UI, Skiper UI). The site is Astro with no React, so each one is rewritten in plain CSS or TypeScript, keeping the mechanic and dropping the library's look:

## Opening scenes

Clicking a hobby card, on `/hobbies/` or in the home page's band, plays a short scene made from the card's own stipple plate, about two seconds long (1.8 to 2.4 s). The plate's dots lift off the card onto a sheet of paper and act something out, and the way the scene ends opens the hobby page. It plays on every click, every visit.

| Hobby            | Scene                                                                                                                                                                                                                                        | Module                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Narrow nature    | The globe spins and stops on a random inland spot; a red finder box closes in and locks on with its coordinates; the camera dives in, and the page opens through big dots.                                                                   | [globe.ts](../src/lib/scenes/globe.ts)       |
| Aquarium keeping | Bubbles rise, the gourami swims right, turns around head first, backs up a touch as its tail comes round and darts off the left of the screen; ripples spread from its wake with the page inside them.                                       | [aquarium.ts](../src/lib/scenes/aquarium.ts) |
| Tide pooling     | The crab rears up bigger and raises its right claw, open; it draws back and jabs in one go, snaps it on the screen, and a shockwave rings out from the pinch, sweeping the dots away.                                                        | [crab.ts](../src/lib/scenes/crab.ts)         |
| Fishing          | The trout holds in the current, tail working, while a rod swings in and casts; the lure lands a little way off its nose, the trout draws back and strikes, and it's hauled off the top of the screen; the page opens in dots behind it.      | [fishing.ts](../src/lib/scenes/fishing.ts)   |
| Birding          | The oystercatcher tips and turns its head, crouches and springs up, wings opening, and flies up out of the screen with its legs trailing; its shadow thins away and the page opens along its trail.                                          | [birding.ts](../src/lib/scenes/birding.ts)   |
| Herping          | A hand slides in along the ground, scoops up the salamander, lifts it up close and holds it there while its tail sways, then pulls it off the side; the page opens where it went. The hand is drawn in [hand.ts](../src/lib/scenes/hand.ts). | [herping.ts](../src/lib/scenes/herping.ts)   |
| Hiking           | A little hiker walks the ridge to the summit (the mountain's real skyline, read off its dots), turns to face you with his arms up, and the view rushes in on him as it fades.                                                                | [hiking.ts](../src/lib/scenes/hiking.ts)     |

Most scenes end by uncovering the hobby page itself, so that part has to play over the hobby page. Those scenes change page as soon as the plate has lifted off its card (`LEAVE` in [engine.ts](../src/lib/scenes/engine.ts)), before anything in them moves, and hold still for a beat (`ACT`), or for as long as the hobby page takes to bring the scene back up, which is usually longer: 0.2 to 0.4 s on a fast laptop. From the moment the page changes, the camera pushes in a touch, easing out over 1.4 s by the clock (`pushZoom`), so a hobby page that's slow to pick the scene up still shows it moving rather than frozen; the hobby page does the same in CSS until the scene's canvas is up (`landing-hold` in [global.css](../src/styles/global.css), timed off the note, on the same curve). The old page leaves a note with the scene's seed, the plate it was drawn from, its timing and the frame it left on, as dots, and, under a key of its own, the plate's dots and the scene's props ([carry.ts](../src/lib/scenes/carry.ts)), so the hobby page doesn't decode the plate or draw the props again.

Times in the scene files are scene time, at the pace the scenes were first approved at; every scene's clock runs `PACE` (1.2) times faster than that, so the whole choreography speeds up together.

On the hobby page, the head script ([landing.ts](../src/lib/landing.ts) `landingBootstrap`) paints that frame once, on a canvas of its own, before the first paint. As a CSS picture, the GPU would draw its thousands of dots again for every tile just as the scene needs it to start up. The same script starts the scene worker on a canvas under the frame, with what the last page carried, and puts `landing-scene` on `<html>`, which keeps the page's own animations still until the scene is gone ([covered.ts](../src/lib/covered.ts)). As soon as the worker has the scene's next frame up, the head script takes the painted frame down and lets the scene play all of its action over the page. It doesn't wait for the page's own scripts: those come last on every hobby page, after every island's, and on a first visit or a slow phone they used to hold the scene still for up to half a second. The head script also passes on the scene's fades, and clears the scene away if it ends before the page's scripts take it over (`carryOn()`). If the worker can't start, the page plays the scene itself ([index.ts](../src/lib/scenes/index.ts) `resume`); if that can't load within a couple of seconds, the frame just fades; and if the page's scripts never run at all, it shows itself after four seconds anyway, unless the scene is already up and playing. Pointing at a card also fetches its hobby page and that page's scripts and styles, so it comes up quickly. The globe works the other way: it ends zoomed into a few dozen big dots, and the hobby page opens through those, each one hollowing into a ring and then a window onto the page ([landing.ts](../src/lib/landing.ts) `planReveal`).

How it fits together:

- [worker.ts](../src/lib/scenes/worker.ts) plays scenes in a Web Worker on an `OffscreenCanvas`, so nothing the page does while it loads or runs its own scripts can make a scene stutter: the worker reads the plates, sets the scene up and draws every frame. Getting cards ready ahead of a click (reading their plates, drawing their props) goes one piece at a time behind anything a click needs, a card that's pointed at going ahead of the rest, and waits while a clicked card's scene sets up and plays. When a card is pointed at, focused or pressed, the worker also sets its scene up once and draws a few moments of it out of sight: the browser readies code slowly the first time it runs, so this way a click starts the scene in well under a tenth of a second rather than a quarter of one. On the page, [player.ts](../src/lib/scenes/player.ts) puts the canvas up, passes input on, draws the globe's labels in the page's fonts and changes page when it's told; [protocol.ts](../src/lib/scenes/protocol.ts) has the messages. Where a browser can't run a canvas in a worker, scenes play on the page itself, the same way.
- [pen.ts](../src/lib/scenes/pen.ts) works out where each dot lands, through the camera and any warp, and hands them to a sink: WebGL ([gl.ts](../src/lib/scenes/gl.ts): instanced circles, holes by blending, lines as quads, labels as textures) where the GPU runs it, or a 2D canvas. The two match to within a level of grey.
- [stage.ts](../src/lib/scenes/stage.ts) has everything that doesn't touch the page: dot sets, affine moves, the camera, easing (`cubicBezier`, for curves the scenes share with CSS), splitting a plate into named parts, `stipple()`, which draws props (the rod, the wing, the hand, the hiker) as blue-noise dots in the plates' own pen size and spacing, and the wakes (`wakeTimes`, `wakeHoles`): when the opening behind a moving figure reaches each point of the screen.
- [hand.ts](../src/lib/scenes/hand.ts) builds the herping hand out of rounded tubes, shaded as if lit from the upper left, with contours, creases and nails; the dark plates draw light as dots, so its shading flips for them. Pale props like it lay down discs of paper first (`pass: "halo"`), or whatever is behind would show through their few dots.
- [engine.ts](../src/lib/scenes/engine.ts) runs a scene: the lift off the card, the paper, the draw calls (`part`, `dots`, `line`, `label`, `cut` to open holes onto the page underneath, `look` to fade or blur the whole sheet) and the handover. `stageScene` sets a scene up on any sink without touching the page, which is how the worker uses it; `show` and `play` put it on a canvas on the page. [table.ts](../src/lib/scenes/table.ts) is the table of scenes both sides share.
- [plate-dots.ts](../src/lib/plate-dots.ts) reads the dots off a plate image, for the scenes on either page and for the plain dive.
- [open.ts](../src/lib/open.ts) loads the scenes on demand (fetched when the page is idle), gets a card ready when it's pointed at, focused or pressed, or has been in view a moment, and falls back to the plain dive into the plate if the scenes can't load. A click never waits more than about 0.6 s for its plate or the scene worker, however slowly they're arriving (the deadline runs from the click, in the worker too); once the worker has the plate, it gets to set the scene up. Past the deadline, the card dives into its plate, or, where the page can't read the plate's dots (production's plates come from the storage account, which only the worker reads with CORS), the plate itself sinks into paper, and the hobby page opens through its halftone. A home-page card shows the small mini plate; its scene plays from the finer card plate, the mini handing over to it during the lift.

Plate parts are outlines in card units (880 × 660; a mini plate's dots are scaled up to match), and the first part that claims a dot gets it. [scenes.test.ts](../src/lib/scenes/scenes.test.ts) plays every scene through a stand-in painter at desktop and phone sizes: each one has to last 1.5 to 2.6 s as played, each one that changes page has to do so as its lift ends and hold still from `leave` to `depart`, come out the same when it's built again, and end with the page open and none of its dots left on screen; the globe has to end on its big dots alone. The push in has to follow the same curve as the CSS. A scene draws each frame in well under a couple of milliseconds of script, so it keeps up with a 120 Hz screen: anything that works out a dot's place does what depends on the time alone once a frame, not once a dot.

A second click, tap, Enter or Space plays the rest of a scene four times faster, wherever it lands: during the lift; while the page changes, where the old page notes it for the hobby page (`globe-landing-hurry` in sessionStorage, against the note's time); and on the hobby page from its first paint, where the head script passes it to the worker and keeps it off the page underneath, so it can't press a link or button that's covered. A click the worker gets before its scene is set up counts too. Escape puts the page back before it changes. Under reduced motion a card just opens its page.

To look at a scene frame by frame, open `/hobbies/?scene-debug` on `npm run dev`, click a card, and call `__scene.seek(ms)` from the console (`__scene.duration`, `leave` and `depart` are its timings; `__scene.hand()` changes page, and the hobby page then has its own `__scene`). `?scene-main` plays scenes on the page rather than in the worker, `?scene-2d` keeps to the 2D canvas, and `?scene-gl` takes WebGL even where it's only in software, to compare them. Each switch carries over to the hobby page, and all of them are left out of production builds.

## Reference implementation: the hiking trail studio

A trail studio in three steps: build, walk, develop. Visitors shape a route, add up to ten trail moments, change landscape, season, weather, light, distance, and jacket color, then watch a tiny hiker walk it. Route length controls the scale of the world: a 3-mile outing is a single mountain, while an 18-mile route expands into a seven-mountain chain with smaller, denser scenery. The same scene recipe develops into a more detailed `2400 × 1600` postcard for local download or the device share sheet.

**Files**

- [src/components/hobbies/PixelHike.astro](../src/components/hobbies/PixelHike.astro), the accessible controls, responsive canvas, action bar, and postcard dialog.
- [src/lib/hobbies/hiking-model.ts](../src/lib/hobbies/hiking-model.ts), the validated state, four biome morphology profiles, variable mountain generator, moment-driven terrain deformation, smart moment placement, distance-based profile resizing, and playful effort estimate.
- [src/lib/hobbies/hiking-renderer.ts](../src/lib/hobbies/hiking-renderer.ts), the shared Canvas 2D renderer. Editor and postcard modes share elevation/aspect-driven rock, alpine turf, soil, treeline, snow, and terrain-aware moments; editor density is capped for responsive dragging. Postcard mode adds finer contour bands, cloud shadows, scree, gullies, ledges, trail stones, footprints, denser vegetation, and foreground depth.
- [src/lib/hobbies/hiking.ts](../src/lib/hobbies/hiking.ts), DOM binding, undo, pointer/keyboard editing, local persistence, animation lifecycle, responsive sizing, and PNG/share export.
- [src/lib/hobbies/hiking-drop.ts](../src/lib/hobbies/hiking-drop.ts), trail moments thrown from their buttons onto the trail, and the way each one lands. The motion is pure functions of time (`dropFlight`, `markerTurn`, `terrainGrow`, `emerge`, `bitAt`, `ripple`, `revealScroll`), tested in `hiking-drop.test.ts`, and `createDrops` is the driver.
- [src/lib/hobbies/hiking-model.test.ts](../src/lib/hobbies/hiking-model.test.ts), pure model coverage including variable mountain counts, silhouette variety, moment deformation and placement, distance resizing, legacy migration, and untrusted saved-state normalization.

The controls are plain HTML (radio groups, buttons, a text field, native selects and ranges) styled with the shared parts above; there are no icons and no UI dependencies. The model, animation, both canvas renderers, persistence, and export path are dependency-free and make no runtime network requests.

**Varied but deterministic.** Mileage determines a target of one through seven mountains. Seeded generation then chooses nonuniform horizontal spacing, height progression, and a form for every mountain: narrow spire, one-sided shoulder, broad massif, or near-plateau, weighted differently for Cascades, fjord, karst, and Himalayan terrain. Shuffle changes both seed and mileage; changing landscape regenerates the current route using that biome's morphology. Dragging the length slider resamples the current terrain profile into a larger or smaller world.

**Trail moments change the route.** Clicking a moment adds it at a sensible location: lakes seek low basins and carve them deeper, lookouts seek high points and raise a spur, waterfalls prefer steep faces and cut a drop, camps flatten sheltered ground, and meadows/wildflowers create broad benches. Forests clear and repopulate a corridor, while snowfields create a high crossing. Waterfalls inspect the local grade, choose the actual downhill direction, become stepped streams on gentler slopes or plunges on steep faces, cross rock ledges, and finish in a laterally aligned pool with foam and mist. Wildflowers grow in clustered, terrain-clipped alpine bands with restrained yellow/red/blue/violet/white/orange species variation; camps sit on sampled pads and lookout cross-braced footings reach the real left/right grade. Every placed moment has a visible route handle and can be dragged horizontally; terrain, effort, artwork, and the eventual postcard update together.

**Adding a moment is a throw.** Pressing a moment button throws a 9 × 9 pixel version of it out of the button's "+" onto the spot the studio picked, a little higher or lower and turning differently each time (the fish jump's `jumpArc` and `heading` from [aquarium-jump.ts](../src/lib/hobbies/aquarium-jump.ts)). The flight is drawn on a fixed `.hike-air` canvas on the page body that only exists while something's in the air. Where it lands, the ground eases into its new shape over 0.3 s through a `grow` value on the placed moment, which only the drawing sees and is never saved. The moment then comes in its own way, drawn in the scene at its own depth: the lake splashes, fills its basin from the floor and sends a ripple across, the waterfall runs down from its lip to its pool and leaves mist, forest, meadow and wildflowers grow outward from where it hit, the tent pitches with a puff of dust, the lookout rises out of the ground with dust, and snow puffs up and settles in patches. Every press is its own drop. Spots are picked as if the moments still in the air had already landed, and moments join the trail in the order they were pressed, so a fast run ends exactly where the same presses end under reduced motion. The count, the tags and the line under the scene change as each one lands. The trail holds ten, and it says so, because a moment that just bounced off read as broken (Truman needed a while to see why, 2026-11-16). The one that fills it says "That fills the trail at ten moments" under the scene, the count becomes "Full · 10 / 10 moments" in ink, and the "+" on every button fades to the rule colour while each button points a screen reader at the count. An eleventh press still flies over, hops off the trail and falls out of the bottom of the scene, and as it bounces three things say why: a "Full, 10 of 10" ink stamp slams onto the scene's top right corner under the distance chip and drifts away (`stamp()` from [motion.ts](../src/lib/motion.ts), one per press, so a burst stacks them), the ten tags under "On your trail" hop in turn from left to right as if counted off (`countOffFrames` in hiking-drop.ts), and the line under the scene says "Trail full. Remove a moment below to add another." until the next change. Under reduced motion the stamp appears and fades in place and the tags stay still. Start over and Shuffle clear anything in the air, and a drag, an undo or any other change finishes the landings at once. A moment that lands during a drag goes into undo ahead of the drag, so undoing the drag keeps it and a second undo takes it away. On a phone the buttons sit under the scene, so if the landing spot is off screen the page scrolls up over about 0.38 s, keeping the pressed button in view. Under reduced motion the moment is just there.

**One scene recipe, two renderers.** Both canvases consume the same `HikeState`, so the developed image cannot silently invent a different route. The responsive editor uses the same terrain-sampled moments and elevation materials at reduced branch/grass/bank detail so direct dragging stays fast; the export canvas is created only on request at a fixed `2400 × 1600`. Mountain materials are biome-specific and driven by elevation, local steepness/aspect, and continuous seeded noise rather than a single green fill: Cascades transition from dark lower forest through patchy olive alpine turf/heather into neutral volcanic/granitic rock, ledges, and scree; fjords expose vertically jointed gray walls; karst uses pale limestone with vegetation pockets; Himalaya uses brown-gray metamorphic faces and sparse tundra. Summer snow is generated as separate retained couloirs with blue-gray melt shadow and embedded rock, while Winter permits broader connected accumulation with avalanche gullies and exposed arêtes. Postcard mode adds finer contour bands, cloud shadows, hundreds of scree marks, gullies, ledges, biome-specific waterfalls/vines, trail stones, footprints, denser vegetation, and foreground depth. Lakes find the spill line inside their actual carved basin and use the sampled basin floor as their submerged boundary, behind irregular banks, stones, and reeds. Forests use individually grounded conifers with local slope, root shadow, altitude-aware size, varied age, and feathered edges; meadows are clipped grass-and-heather bands that follow and extend down the local face rather than horizontal decals. Generation uses only the visitor's CPU/GPU and browser memory. It makes no API calls, uploads nothing, and incurs no per-generation Azure cost.

**Persistence and sharing.** The normalized scene is saved under `trail-studio-v2` in `localStorage`; a saved v1 five-point route is migrated and blended into the new distance-scaled profile on first load. Export uses `canvas.toBlob()` rather than a base64 data URL. Browsers supporting file sharing receive a real PNG through `navigator.share`; other browsers always retain the download action.

**The postcard develops.** When the dialog opens, the finished canvas comes up like a print in the tray: pale, warm and soft under a dot grain, reaching full contrast in about 1.7 seconds while the status reads "Developing at 2,400 × 1,600...". It's only CSS on top of the finished canvas, so the downloaded PNG is identical either way, and under reduced motion the print is simply there. Once it's up, a round postmark with the trail's name and the day slams onto the top right corner (`makePostmark` in [postmark.ts](../src/lib/postmark.ts), which "Write to me" also stamps on its envelope); it's painted into the canvas as it lands, so the PNG does keep that, in dark ink on a pale sky and pale ink on a dark one. The type is the site's own: the trail's name in Libre Franklin 300, the tracked capitals above and below it and the postmark in 400 (`canvasFont`). The develop waits for `canvasFontReady()`, because a PNG drawn before the font arrives keeps a fallback face; until November 2026 it was Georgia bold and Arial (TTT-4).

**Input parity.** Every generated terrain point has a visible canvas handle and a dynamically generated native range control (the shared `.range` slider) under "Fine-tune the terrain"; points support direct pointer dragging and arrow-key editing on the focusable canvas. Moment buttons add a moment on every press, Enter and Space included. Moment handles support pointer dragging and the itinerary tags remove a moment. Landscape and light are underline-tab radio groups (arrow keys move between them), and every other option is a real button, select, or slider. Reduced-motion users get the completed walk immediately instead of the animation.

## Reference implementation: the aquarium island

A planted-tank stocking sandbox. Tap a species to add it, resize the tank, and watch a bioload meter react. It is meant to be fun and roughly believable, not a real stocking calculator.

**Files**

- [src/components/hobbies/AquariumTank.astro](../src/components/hobbies/AquariumTank.astro), the markup (canvas, the species picker rendered at build time, the tank panel) and the mounting `<script>`.
- [src/lib/hobbies/aquarium-species.ts](../src/lib/hobbies/aquarium-species.ts), the species data: a pure module, so the page can render the picker from it at build time.
- [src/lib/hobbies/aquarium.ts](../src/lib/hobbies/aquarium.ts), the whole engine: the canvas pixel rendering, adding and removing fish, and the UI sync. It has no dependencies.

**Single source of truth.** The `SPECIES` array in `aquarium-species.ts` (35 freshwater species) drives everything. The picker lists them grouped by where they swim (top, middle, bottom), each with a two-color swatch taken from its own sprite colors and its minimum tank size; the stocking list is built from it at runtime. Each entry stores an approximate adult length (inches), a relative `bioload` weight, a sensible `minGallons`, a swim `zone` (top/mid/bottom), a body `shape`, and two colors.

### How the stocking math works

Two tunable constants at the top of `aquarium.ts` plus one sum:

```
capacity = gallons × PLANTED_CAPACITY_PER_GALLON     // 0.55 "load units" per gallon
load%    = Σ(bioload of every fish in the tank) / capacity
```

So a 20-gallon tank has a capacity of `20 × 0.55 = 11` units. Seven neon tetras at `0.3` each (`2.1`) plus four pygmy cory at `0.35` (`1.4`) plus five cherry shrimp at `0.05` (`0.25`) plus one honey gourami at `0.9` come to `~4.65`, or about 42% of capacity, which reads "Healthy". The formula lives in [src/lib/hobbies/stocking.ts](../src/lib/hobbies/stocking.ts), a pure module split out from the canvas engine and unit-tested in `stocking.test.ts`.

The meter label comes straight from `load%`. The meter itself is a 1px ink rule (`.hair`) with the percent rolling to its new value, so the word carries the state rather than a color:

| Load         | Label           |
| ------------ | --------------- |
| `< 40%`      | Lightly stocked |
| `40 to 85%`  | Healthy         |
| `85 to 100%` | Heavily stocked |
| `> 100%`     | Overstocked     |

Separately, each species carries a `minGallons`. If the current tank is smaller than any stocked species likes, a note appears (for example "Angelfish likes 29+ gallons"). That check is independent of the bioload percentage, because some fish need swimming room regardless of waste.

**Tank size also scales the scene.** The canvas stays the same size, but a bigger tank renders the fish smaller (apparent size roughly 1/∛volume, clamped ~0.72 to 1.3×) and grows the plant and floating-cover density (~0.65 to 1.7×). A small tank shows big fish and sparse planting. Dragging the gallons slider changes the scene at once: fish resize live and the planting re-aquascapes on a short debounce. See `fishScale()` / `plantFactor()` in [src/lib/hobbies/aquarium.ts](../src/lib/hobbies/aquarium.ts).

### Where the numbers and species come from

I want anyone to be able to learn how this works, so here is where it all comes from:

- **The species roster is hand-picked from general fishkeeping knowledge** (the fish people actually keep in planted community tanks), not pulled from any database, API, or dataset.
- **The per-species numbers are approximate and tuned by feel.** The adult sizes are ballpark hobby figures; the `bioload` weights roughly track how big and messy a fish is; the `minGallons` values are common community recommendations. None of them are precise or authoritative. The bioload weights don't come from measured waste data: they were chosen and play-tested until the meter behaved sensibly.
- **The model is a miniature of real stocking heuristics.** The old rule of thumb is "one inch of fish per gallon," and community tools such as AqAdvisor estimate stocking from a large species database. This sandbox uses the same idea with a single "load per gallon" constant instead of a database. The `0.55` figure and the 40 / 85 / 100% thresholds were picked so a normal community tank reads healthy and obvious overstocking turns red.
- **It's a toy.** If you're stocking a real tank, research each species properly rather than trusting this meter.

### How the pixel art is made

Everything you see in the tank (fish, plants, rocks, driftwood, bubbles, light) is drawn in code with canvas `fillRect` calls. There are no image files, sprite sheets, stock photos, or AI-generated art anywhere in the scene, so there is nothing to license or attribute. (Real tank photos are separate: see [Photo galleries](#photo-galleries-hobby-media) below.)

- **The pixel look** comes from a fixed block size `PIX` (4 CSS pixels). Every shape snaps to that grid and image smoothing is turned off, which gives the chunky 8-bit feel. Dropping `PIX` makes finer pixels; raising it makes chunkier ones.
- **Fish are procedural.** Each one is built from its species params: a body drawn as horizontal pixel rows of an ellipse (`fishBody`), a tail, fins, a lateral stripe or vertical bars, and a small eye. A `shade()` helper mixes the body color toward white for the top rows and toward black for the bottom for a bit of lighting. There are eight silhouettes: `fish` (tetras/barbs/livebearers), `gourami` (oval body with its trailing pelvic feelers), `betta` (small body, big flowing fins), `angelfish` (tall diamond with long swept-back dorsal/anal fins + ventral filaments), `tall` (oval cichlids/rams), `long` (cories/loaches/plecos, with a downturned barbeled snout), `shrimp`, and `snail`, routed in `drawFish` by `shape`. Fish are drawn back-to-front by depth `zone` for layering.
- **The scene is layered for performance.** A baked offscreen background (water gradient, dark silhouette plants for depth, four rocks, two driftwood pieces, gravel substrate, and a carpet of plants along the front) is rendered once and only redrawn on resize. Each animation frame just blits that image and then draws the moving parts: slanted caustic light, two swaying foreground plant types (tall vallisneria and stems), fish, floating surface plants with dangling roots, and rising bubbles.
- **Layout is seeded, not random each frame.** Plant, rock, and bubble positions come from a tiny seeded pseudo-random generator (`makeRng`) keyed to the tank width, so the scene is stable but adapts when the canvas resizes.

### Mobile and performance

- The canvas resizes to its container via `ResizeObserver`; height clamps to 220 to 460px and fish scale with canvas width.
- Because the static background is baked and blitted, only fish, foreground plants, floaters, and bubbles are recomputed per frame.
- The loop pauses when the canvas scrolls offscreen (`IntersectionObserver`) or the tab is hidden (`visibilitychange`), so it costs nothing when not in view.
- Touch friendly: native range slider, a species list with 32px rows, and tap-to-add (after picking a species, tapping in the tank drops one at that point).
- **On a phone the tank stays in view.** Held upright (below 1024px wide, and at most 4:5 wide to tall), the tank pins to the top of the screen on a strip of paper while the tank panel and the species list scroll under it, so a fish you add always lands where you can see it. It's one list at every size; a phone on its side, a short window and a desktop keep the page as it was. Because a pinned tank moves on the page as you scroll, the jump, its splash and the tip's pour follow it (`where` in [aquarium-jump.ts](../src/lib/hobbies/aquarium-jump.ts)), controls you tab to scroll clear of it (`scroll-margin-top`), and `main` clips sideways overflow (`overflow-x: clip`) so the tipped tank can't widen the page and slide out of place.
- **Adding a fish is a jump.** It leaps from the swatch you tapped, growing from the two-colour swatch into its sprite and flicking water off its tail, comes down through the surface with a splash, and sinks to its depth nose-first, levelling out and trailing bubbles. A tap in the tank drops one in over that spot the same way. The leap is drawn on a fixed canvas that only exists while something's in the air, snapped to the tank's pixel grid so the fish lands on the pixels it flew on; the tank takes over at the surface. Each tap is its own jump, so tapping fast sends a run of fish in, and the stocking list counts each one as it lands. See [aquarium-jump.ts](../src/lib/hobbies/aquarium-jump.ts).
- **Taking a fish out is a net.** The "−" beside a species takes one off the list at once and sends a pixel net down for it: in from above the surface, a quick scoop, then up and out with the fish (`netPath`). Several can be in the water at once.
- **Start over tips the tank.** The frame leans over on its low bottom corner (`tipLean`); everything in it rushes for the low corner of the rim and pours out with the water, falling clear on the same layer the jumps use, and the tank rocks back level, empty.
- `prefers-reduced-motion` slows everything, stops the plant sway, and adds and removes fish straight away, without the jump, the net or the tip.
- A hard cap of 55 fish keeps the loop smooth on phones.
- It all runs in the visitor's browser, so frame rate depends on their device, not on the hosting tier.

### Tweaking it later

- Species roster and balance: the `SPECIES` array in [aquarium-species.ts](../src/lib/hobbies/aquarium-species.ts). The picker, the swatches and the "35 species to stock" line all follow it.
- Overall stocking feel: `PLANTED_CAPACITY_PER_GALLON` (now in [src/lib/hobbies/stocking.ts](../src/lib/hobbies/stocking.ts), unit-tested).
- How tank size scales the visuals: `fishScale()` (fish shrink in bigger tanks) and `plantFactor()` (denser planting).
- Starting community shown on load: `STARTER`.
- The look of anything: the `draw*` / `bake*` functions and the `PIX` constant.

## Reference implementation: the tide pooling island

You look straight down at a metre and a bit of Washington shore at low tide, one of six beaches. It opens on a sandy beach with loose rocks, one big rock and a small pool at its foot, and New beach goes on to a cobble beach, a sandstone bench of potholes, a gravel flat with one big boulder, a mussel bench, and a surge channel full of seaweed. Tap a loose rock and it turns over onto its back, showing the damp gravel and whatever was under it, and the crabs under it run for the shade. Tap it again to put it back. The big rocks take three heaves. In the channel you brush the seaweed aside to see under it, and anywhere there's water a tap sends rings across it. Tap an animal to meet it. Today's three are three animals on the sandy beach, found from their clues, the same for everyone that day. A field journal tracks how many of the 40 species you've found and remembers them between visits. It replaced the pixel beach in November 2026, after two rounds of mocks ([design-mocks](../.github/skills/design-mocks/SKILL.md)).

**Files**

### The species data and where the facts come from

The dataset is 40 common PNW tide-pool species, each tagged with a `category` (16 in all: crabs, hermit crabs, sea stars, anemones, nudibranchs, chitons, snails, limpets, urchins, barnacles, mussels, sculpins, eel-shaped fish, shrimp, sea cucumbers, octopus), a `rarity`, and two short facts. On each find one fact is picked at random.

Here too, I want anyone to be able to learn how this works:

- **The facts are curated, not generated live.** They were written from standard references (Wikipedia and field guides such as _Between Pacific Tides_ and the Walla Walla University / Rosario intertidal key) and a representative sample was checked against live web research while the dataset was built. They favor well-established, interesting tidbits over obscure claims.
- **They were checked again in October 2026.** The doubtful claims were looked up a second time, which corrected the leather star (the anemone that lets go and swims off when one touches it is the swimming anemone, not the giant green), the giant green anemone's color (its own pigment as well as algae), the painted anemone's diet, the turban snail's worn tip, the purple shore crab's hours out of water and the octopus's tool use. The wording was redone to the [site copy rules](../.github/instructions/site-copy.instructions.md) at the same time, and [species-facts.test.ts](../src/lib/hobbies/species-facts.test.ts) checks their mechanical parts (two or three facts, one sentence each, no dashes or banned words) for both this and herping.
- **It's a learning game.** A quick review pass by someone who knows these animals is recommended before treating any single fact as authoritative, and the dataset header says the same.
- **Today's clues are the animals' own facts.** `CLUE_FACT` picks, for each species, the fact that best says how to know it, so a clue adds no new claim to check. A test makes sure no clue gives the animal's name.
- The journal counts _distinct_ species found and keeps them in `localStorage` (`tidepool-discovered-v1`), so it builds up across visits, and today's finds sit beside it (`tidepool-today-v1`). New beach doesn't wipe the journal.

### How the beaches are made

Nothing in a beach is a photograph of a real place. Round 1 of the mocks put the toy on real pool photos, and every one held organisms the toy didn't know about, so a tap on an orange crust said "Just rock", and animals pasted into them floated. So each beach is built from parts, and nothing alive is in it unless the build put it there and wrote it into the label map.

- **Surfaces are CC0 scans from Poly Haven** (polyhaven.com): `dark_rock`, `dark_rock_02`, `seaside_rock`, `rock_surface`, `rock_08`, `low_tide_rocks`, `ganges_river_pebbles`, `coast_sand_05`, `damp_beach_sand`, `aerial_beach_01` (only its ripples) and `sandstone_cracks`, each with its colour, normal and height maps. The script downloads the 2k versions once into `~/.cache/tidepool/tex` (or `$TIDEPOOL_TEX`).
- **Each beach is laid out in code** (`build_cobble`, `build_potholes` and so on): where the pools are, the fixed stones, the loose rocks, cracks, the mussel bed, the barnacle band. The whole height field is lit by one sun from the upper left, about 35 degrees up, with cast shadows marched across it, ambient occlusion in the hollows, and wet highlights where the rock is wet. Tops of rocks dry paler and their sides stay dark.
- **What lives on the rock is drawn on purpose**: acorn barnacles as shaded cones about a centimetre and a half across with their plates and opening, California mussels packed into a bed, aggregating anemones closed up and coated in gravel, coralline crust in the pools, green algae film, a washed-up bull kelp and eelgrass on the sand. Each goes into `labels.png`, so a tap on it is named right.
- **Loose rocks are separate sprites**, a top and an underside, with the bed they sit on (darker, damp, a pale line where the edge sat) baked into the ground. The underside is the same stone, wet and filmed with silt, with patches of coralline crust, now and then a thin red sponge, and tube worms. `settle_falls` picks which way each one tips: onto open ground, clear of the fixed stones, the pools, the other rocks and where the others land.
- **Slots** are the spots animals can sit, by kind (`stone`, `gap`, `puddle`, `pothole`, `bench`, `pool`, `sand`, `runnel` for shallow water over sand, `crack`, `bed-edge`, `rock`, `floor`, `ledge`), written to `beach.json` with the rocks, the seaweed anchors in the channel, and the field's scale (20 px per cm).
- **Seaweed in the channel is drawn by the toy**, so it can sway and part: blade textures in `public/tidepool/<v>/weeds/` bent along a path slice by slice (surfgrass in tufts, kelp, rockweed hanging off the bench edge toward the water) and sea lettuce as translucent sheets.

Run it with the stipple-plates venv: `~/.cache/stipple-plates/venv/bin/python scripts/tidepool/build-beaches.py [beach ...]` (about a minute and a half for all six, plus `weeds`). It writes `public/tidepool/<v>/<beach>/`: `base.webp` (the lit ground, 2400 by 1500), `water.png` (depth at half size), `labels.png` (half size), `rock<n>.webp` and `rock<n>-under.webp`, and `beach.json`. The files are served with a one-year cache (`/tidepool/*` in [staticwebapp.config.json](../staticwebapp.config.json)), so a change to the art bumps `VERSION` in both scripts and `ART_VERSION` in tidepool-beaches.ts. Move the folder with `git mv public/tidepool/v2 public/tidepool/v3` before rebuilding the beach that changed, so the files that didn't change stay the same blobs in git (v1 became v2 that way when the sandy beach was rebuilt in November 2026).

### The animals

Each animal on a beach is a CC0 photo of it seen from above, from iNaturalist, cut out by hand. They're a different set from the reveal card's photos, which are side-on and mostly CC BY-NC: a toy's details use copyright-free photos ([hobby-pages](../.github/skills/hobby-pages/SKILL.md)). The candidates and cutouts are in the gitignored `staging/tide-pooling/top/` (`animals.json` records each one's observation page, author, licence, view and size), and `scripts/tidepool/prep-animals.py` turns them into `public/tidepool/<v>/animals/<id>.webp`, evens out their exposure, darkens each a little where it meets the rock, writes a height map (`<id>-h.webp`) from its outline and surface, and writes [tidepool-animals.json](../src/lib/hobbies/tidepool-animals.json). Three are weaker than the rest: the tidepool sculpin is a camouflaged fish shot through water, the kelp crab a dead one on the beach with a strand of eelgrass in its legs, and the sea lemon runs off the edge of its photo.

In the toy each animal is drawn at its real size against the rest (`cm` times the beach's 20 px per cm, with a floor so a periwinkle can be seen), turned at random, relit from its height map by the scene's sun at whatever angle it lies, and set down on two shadows: a tight dark edge where it touches and a softer one the sun casts. Under water the shadows are fainter. Hermit crabs wander, snails and nudibranchs creep and shrimp hover, about ten redraws a second.

**Where each animal goes** is `HABITAT` in tidepool-beaches.ts: a weight per kind of spot. Crabs, gunnels and cockscombs live under rocks, the red rock crab and the octopus under the big boulders, stars at the edge of the mussel bed and in pools, goosenecks in cracks, moon snails on sand, and so on. `deal` gives each kind of spot a few animals that live there, rarer ones less often, keeps them off each other and clear of where the rocks land, and hides none to two under each loose rock (three to five under a big one). Today's three are placed first: each one that lives under rocks gets its rock before anything else does, a loose one it fits under if it can, so a crab can't take the room a sea cucumber needs under the big rock, and one whose spots are all taken shares one. The test deals them at their real sizes, 1.2 to 30 cm.

### The water

The beach and everything under water draw into an offscreen canvas, and [tidepool-water.ts](../src/lib/hobbies/tidepool-water.ts) puts water over it in one WebGL pass wherever `water.png` says there's depth: the bottom bent by a moving surface, light focused into caustics on it, colour soaked up with depth (red first, then green), the sky and a sun glint on the surface, and a bright wet line at the edge. A tap on water sends rings across it. Without WebGL the same scene gets a cool tint instead. The rocks, drips, the focus ring and the wave draw on a 2D canvas on top.

### How a rock, a heave, a find and a new beach move

- **A rock turns over** about the edge it tips toward (`overAngle`): it takes the weight for a beat, comes up faster as it passes standing on end at about 0.36 s, lands on its back beside where it lay and rocks once. It's drawn as its own picture squashed toward the hinge, with its side showing as it lifts, its underside past standing, each face shaded by how it faces the sun, and a shadow thrown further the higher its far edge gets. Drops of water fall off the rising edge (sand on the sandy beach) and ring where they land.
- **The animals under it react** by kind (`critterReact`) once light gets under: crabs scuttle out toward the shade of the rock lying beside them, fish dart and wriggle, shrimp flick back, anemones squeeze shut and open again, and the rest stay put. Put back, the ones that ran go back under first, then the rock comes over and down where it was (`backAngle`).
- **A big rock takes three heaves** (the boulder, and the one on the sandy beach). The first two lift it part way, it trembles and slips back down with a thud (`heaveAngle`), and the line under the beach says why ("It's heavy. It comes up a little and slips back. Heave again."). Heaves count for six seconds, so three taps in a row turn it.
- **In the channel**, a tap on seaweed brushes it aside for nine seconds, and whatever was under it can be tapped.
- **A find's photo arrives** through one of three reveals, being tried: the animal lifts off the beach, arcs into the card and lands in the middle of its frame, and only then does its photo come up under it as it fades (lift); a hand lens slides over it, magnifies it and opens out into the card (lens); or the photo drops onto the card like a print (print). `?reveal=lift|lens|print` picks one and shows a switch under the toy. The pixel reveal they replace (pixel-reveal.ts) is gone.
- **A first find hops into the journal** when its card closes, as before ([journal-hop.ts](../src/lib/hobbies/journal-hop.ts)), and a find in today's three crosses out its clue and names the animal.
- **New beach sends a wave in** (`makeTide`): churned water and foam wash down over the whole beach, the next beach goes in underneath once the water covers it (it's loaded ahead while you play), and the water drains back. Leave a rock turned over and the next beach says what that does to whatever lived under it. A press while a wave is running is ignored.
- **Rapid presses.** Each rock turns on its own, so taps on five rocks turn five. A tap on a rock that's turning is ignored until it lands. Taps and keys wait while the card is open or a wave runs.
- **Reduced motion** keeps the information and drops the movement: rocks are over or back at once, the boulder goes over on its third press, the card shows the photo at once, seaweed and animals stay still, and New beach swaps the beach at once.
- `?slow=4` plays rocks and the wave four times slower, for checking the motion.

### Playing it

- **Keyboard.** The frame takes focus as one stop. The arrow keys (and Home and End) walk everything you can act on from left to right (rocks, animals you can see, and patches of seaweed with something under them), a ring marks it, and the live line says what it is ("4 of 11: something in the water"). Enter or Space does what a tap would. The card hands focus back to the frame.
- **Phones.** The beach is taller than wide on a phone, so it shows a slice of the field you drag sideways, with a 1px bar under it showing where you are. A vertical drag scrolls the page.
- It pauses off screen and in a hidden tab, and only redraws while something moves (the water keeps moving on beaches that have it).

### Real photos in the reveal card

The reveal card leads with the photograph: it runs across the top of the card at 4:3, 600 px wide on a desktop and the full card width on a phone, with a specimen label under it (name, Latin name, fact, credit, button). Until November 2026 the photo was a 132 px square beside the label (104 px on a phone), too small to see the animal; a mock compared a bigger square, this layout and a side-by-side one, and this one won ([design-mocks](../.github/skills/design-mocks/SKILL.md)). Without a photo, or if it fails to load, the card shows the animal as it looked on the beach.

A first find gets "New to your journal" stamped in ink on the card as it opens, the way a new specimen gets its accession stamp. It lands on the paper to the right of the names, under the photo, so it never covers the animal. A find you already have just says "Found again". The herping card is the same card and does the same ([specimen.ts](../src/lib/hobbies/specimen.ts)).

- **Where photos come from.** Optional per-species photos live in [src/lib/hobbies/tidepool-photos.json](../src/lib/hobbies/tidepool-photos.json) as `id → { photo, credit }`. The engine merges that in when it builds the card: if a photo is present it's shown with its attribution line; otherwise, or if the image fails to load, the card shows the animal as it looked on the beach. So a dead link never breaks the card.
- **Licensing.** Photos are Creative Commons only (CC0, CC BY, CC BY-NC), with attribution shown in the card.
- **Every photo is picked by eye.** [scripts/reveal-photos.mjs](../scripts/reveal-photos.mjs) gathers each species' candidates, the photos on its iNaturalist taxon page and the first photos of its most-faved research-grade observations, and writes a numbered contact sheet per species to `staging/<hobby>/candidates/` (gitignored): `node scripts/reveal-photos.mjs tide-pooling candidates`. Look at every sheet and pick the sharpest photo that shows the whole animal clearly, with no hand holding it, no watermark and no tank, and ideally the feature its fact talks about. Then `node scripts/reveal-photos.mjs tide-pooling pick ochre-star=3,...` writes the picks into the JSON with their credits. The older [fetch-tidepool-photos.mjs](../scripts/fetch-tidepool-photos.mjs) took the first licensed photo it found, which put blurry and hand-held shots on the cards until both hobbies' photos were picked again in November 2026.
- **Two sizes.** The JSON holds iNaturalist's 500 px copy, which the toy preloads so a card opens at once. The card then loads the 1024 px copy and swaps it in once it's decoded and the reveal has finished (`largePhoto` and `upgradePhoto` in [specimen.ts](../src/lib/hobbies/specimen.ts)), so the bigger photo stays sharp without slowing the reveal.
- **Two ways to serve them.** `--wire inat` writes the iNaturalist photo URLs straight into `tidepool-photos.json` (works immediately, since the iNat image hosts are allow-listed in CSP). `--wire blob` instead points at your own `hobby-media` copies for self-hosting; upload `staging/tide-pooling/photos/*` to `hobby-media/tide-pooling/species/` first. Either way the attribution travels with the photo. Today it's wired with iNaturalist hotlinks (mostly CC BY-NC / CC BY, a few CC0).

## Reference implementation: the fishing island

A clickable pixel map of the two places I fish: Minnesota and Washington. Each map is drawn from a baked land/lake/river/sound mask, and every named water shows up as a small fish sprite of its signature species. Tap a water and its fish leaps out of the water, then a panel lists what you can catch there. From the keyboard each map is one Tab stop: the arrow keys walk its waters from west to east, ringed and named, and Enter or Space opens the panel. The Twin Cities metro gets its own zoomed inset, since those lakes are tiny at full state scale. Below the maps, a catch gallery of real photos sits beside the matching pixel sprite, split into Washington and Minnesota; tapping a photo opens it full-screen in the same PhotoSwipe lightbox the photography pages use. There are 37 waters across the two states, 32 species, and 16 catches today.

**The look.** The pixel art keeps its own land and water colours, a step darker in dark mode (`LIGHT` and `DARK` in fishing.ts, rebaked when the theme toggle flips), and the canvas leaves everything outside the state clear, so the map sits on the page's own paper in both themes. Everything on top of the art follows the page and is drawn at the screen's resolution, so it stays sharp: the Twin Cities box is a 1px ink rule with a tracked "Twin Cities" caption that moves off any fish, water names sit on paper tags in Libre Franklin 400, and the only ring is round the fish the arrow keys are on, in ink and paper. The fish have no halos. On a phone the Minnesota and Washington tabs name the map, so the label above it only shows from 768px up. Until November 2026 the maps kept a pale `#e9eff0` ground, a Tailwind blue box and bold system-font labels in black boxes, which glared out of the dark page (TTT-2).

**Tapping a water.** The water's fish leaps before its panel opens ([fishing-leap.ts](../src/lib/hobbies/fishing-leap.ts)). `planLeap` picks a height of 28 to 50 CSS px, a distance of 10 to 42 px, a direction (about one leap in four goes the other way from the way the fish faces), a small twist at the top and, about one time in five, a roll. `aimLeap` reads the map's cells where the fish would come down and shortens or turns the leap until it lands in water, or makes a short hop on a thin river. The path is the aquarium's `jumpArc` and `heading`, timed by the same 1400 px/s² pull, so a fish is 0.4 to 0.53 s out of the water: nose up, over the top, nose down. While it's out, the map draws only its shadow on the water. The fish itself goes on one fixed canvas over the page (`.fish-air` in Fishing.astro, made by `createAirLayer` and removed once nothing is in the air), so near the top of a map it leaps clear of the frame, and it follows the map if the page scrolls. It's drawn at the map's art size, turned on a scratch canvas with smoothing off and only then scaled up, so it stays on the map's pixel grid. Where it goes in, a crown of pixel drops in the map's water colours (`splashDrops`, `dropAt`) and two rings spread out (`ringAt`, `ringPixels`, drawn on a grid of the fish's own pixel size and stopped at the shore). A smaller splash and ring mark the spot it left. It stays under for 0.16 s, then comes back up through the surface on its own spot with one more ring, so the map ends as it began. The panel opens as the fish goes back in, never more than 550 ms after the tap, and fades in over 180 ms so the splash shows through it. With a mouse, the fish under the pointer rises (`riseAt`): it lifts a little and leaves one ring, at most once every 0.7 s. The arrow keys do the same, and Enter or Space leaps like a tap.

Rapid taps: each tap on another fish sends that fish up, and the panel waits for the last fish tapped and opens as that one goes in. A fish already in the air doesn't go again. Switching map tabs on a phone mid-leap drops that leap, its drops and its panel. Under reduced motion nothing leaps or rises, the panel opens at once, hover grows the fish and names its water as before, and no layer is made. [fishing-leap.test.ts](../src/lib/hobbies/fishing-leap.test.ts) checks that a leap leaves its spot and goes in where it was aimed inside 0.55 s, varies between presses, goes up and comes down nose first, rolls back upright, never jumps between frames, and that the rings, drops, rise and resurfacing start and end where they should.

## Reference implementation: the birding island (selfie to bird)

Take or upload a selfie and the page turns you into a bird-person hybrid: it keeps your real face from the photo and gives it a real bird's bill and feathers. A single triangle-mesh warp over the face, with no seams, enlarges and rounds the eyes, narrows the lower face toward a bird skull, and pulls the nose and mouth down under the bill. The bird is one of three I've photographed (black oystercatcher, keel-billed toucan, yellow-crowned night heron), and its bill and plumage come from my photo of it. The label under the picture names the bird, its scientific name and where I took the photo, and See the bird opens that photo in the site's lightbox, the same as on its session page: a 1600 px copy first, then the original from Blob, with the camera line and the download button. The bird stays on the page behind it. Birding.astro looks each photo up in its session at build time (`photo` in `SPECIES`), and when it isn't in the build, as in the fixture builds, the button stays hidden for that bird. Another bird steps through the other two on the same selfie. The same selfie always starts on the same bird.

**The bill.** Each bill is cut from a side-on photo by `bird_parts.py` (the [stipple-plates](../.github/skills/stipple-plates/SKILL.md) skill, "Bird parts for the selfie bird"), which writes its outline as alpha and its base line and tip to `bird-parts.json`. On the face the bill is seen head on, pointing down from between the eyes, so `renderBillHeadOn` reads the real bill's depth along its length (`billProfile`) and uses it as the taper. Its colours are the real bill's: at each step along it, the ridge, the side and the edge of the upper bill are averaged into three bands, smoothed a little and given back the saturation that averaging takes out. Wrapping the photo's pixels round it directly came out streaky and mirrored, like a Rorschach blot. It's shaded as a rounded surface lit from above, with a soft highlight along the ridge, a nostril slit each side near the root, a fine grain along its length, and a soft shadow on the face. It's drawn after the feathers, so a long bill's tip lies over the neck feathers instead of under them. It's never brightened past its own colour, so a pale face doesn't wash an orange bill pink, and a dark selfie darkens it to match (`lightGain`).

**The feathers.** Each bird also has a crown patch and a neck patch of plain plumage from the same photo. Their colours are read into a small palette, and each feather is drawn the way a feather is built: a curved shaft with fine barbs either side, swept toward the tip, downy and faded at the root so it grows out of the head. A scattered crest rises from the hairline, taller toward the middle and taller still for raised brows, and short feathers run along the jaw and under the chin. Solid feather shapes filled with the photo read as leaves or a costume collar, which is why it's barbs.

**How "you" shows up:**

- **It's your own photo.** The selfie is drawn as the base, so every human feature (your eyes, skin, face shape, hair) is real and there is no synthetic face. The bird parts are overlaid and anchored to your facial landmarks.
- **Your features pick the bird and shape it.** Your features and colouring seed which bird you start on and how its feathers fall, so two friends get different birds and any meaningful selfie change gives a new one. The bill grows from between your eyes and its length follows your nose, the crest follows your hairline and your brows, and the feathers follow your jaw.
- It's a composite over the photo, not a painting. That's as far as an on-device approach without AI can go. (The only way to a painted look is a generative image model, which would mean sending the selfie off-device, and I declined that to keep it private.)

**This island breaks two of the conventions above.** It's the first island with a bundled dependency and the first that ships large vendored assets. That's a chosen tradeoff: anchoring bird parts to a real face needs real facial landmarks, and a from-scratch heuristic can't find them reliably.

**How it stays safe and private:**

- **Local-only.** The selfie is read into a canvas and the landmark model runs entirely in the browser (WASM). Nothing, neither the photo nor the landmarks, is ever uploaded. There is no database and I never see it. The only network calls are fetching the same-origin model and WASM. The result PNG leaves the device only if the user clicks Download.
- **CSP-safe, still same-origin.** The model and WASM are self-hosted under `public/birding/`, so `connect-src 'self'` still holds. Running WASM requires `'wasm-unsafe-eval'` in `script-src` and the worker it spawns needs `worker-src 'self' blob:`; the selfie preview uses an object URL so `img-src` gains `blob:`. The camera needs `Permissions-Policy: camera=(self)` (it was fully disabled before). `.wasm` is mapped to `application/wasm` in `mimeTypes`. All of these live in [staticwebapp.config.json](../staticwebapp.config.json).
- **Lazy by route, and lazier within it.** The heavy `@mediapipe/tasks-vision` bundle and the model (about 15 MB with the WASM) are dynamically `import()`ed only when the visitor taps Take a selfie or Upload a photo, so the birding page is light until then and other pages are unaffected. Starting at the tap means they download while the visitor frames the shot or picks a photo: on a phone profile (4x CPU throttle, 20 Mbps) the first bird lands about 2.8 s after the photo is chosen, and Another bird takes under a second. The bird parts (about 100 KB for all three) load at the same tap.

**Input.** Two choices are always offered: live camera via `getUserMedia({ facingMode: 'user' })` (works on desktop and mobile), and a normal file upload. If the camera is denied or unavailable, it falls back to a native `<input capture="user">`, which opens the phone camera on mobile.

**Vendored assets** (under `public/birding/`):

- `face_landmarker.task` (~3.8 MB): Google's MediaPipe Face Landmarker model (478 landmarks, including iris points), Apache-2.0. It's committed because it isn't published to npm, and committing it keeps builds offline and reproducible.
- `wasm/`: the MediaPipe vision WASM runtime, gitignored and copied from the pinned `@mediapipe/tasks-vision` dependency at build time by [scripts/copy-birding-assets.mjs](../scripts/copy-birding-assets.mjs) (chained into the `dev` and `build` npm scripts). It's reproducible from the lockfile, so there is no need to commit ~22 MB of it.
- `parts/`: each bird's bill, crown and neck, about 100 KB for all three birds, committed. They're served from here rather than imported from `src/assets/`, because the deploy's [sync-variants.mjs](../scripts/sync-variants.mjs) moves every webp under `/_astro/` to Blob and rewrites only HTML and CSS, so a URL the script imports 404s. That broke the toy for a few minutes on 2026-11-15.

**Files**

- [src/components/hobbies/Birding.astro](../src/components/hobbies/Birding.astro), the markup (choose / camera / busy / error / result states) and the mounting `<script>`. The page says once, in the intro, that the photo stays on the device, and the facts line under the title says "Selfie · nothing uploads". It used to describe the toy a second time and add a privacy paragraph under it; both came out in November 2026 as repetition.
- [src/lib/hobbies/birding.ts](../src/lib/hobbies/birding.ts), the engine: camera and file input, lazy-loading the landmark model, turning landmarks into normalized features, sampling the palette (hair, accent, skin, and iris colours), loading each bird's parts, and the label. Split out the same way `stocking.ts` is split from the aquarium.

The canvas ends identical to the finished bird, and Download finishes the ink-in first.

### Honest notes on the look

The bills' outlines and colours and the feathers' colours are the real birds', from my photos. The head-on shape is read from the side-on outline, and the feathers are drawn, so both are approximations tuned by feel. The parts are composited over the real photo, which keeps it private and on-device, at the cost of looking like a composited hybrid rather than a painted artwork. Reaching a painted look would take a generative image model and sending the selfie off-device, which I chose not to do.

In November 2026 (TTT-5 in the site review) the old version's flat orange oval bill and rows of identical grey spikes read as a phone filter beside the stipple plate on the card. A version that redrew the whole selfie as a stipple plate was tried and rejected as worse, so this one keeps the old warp and framing and swaps in the real bills and feathers.

## Reference implementation: the herping island (night drive)

A road-cruising game: you drive slowly down a forest road at night, about 12 km/h, and the roadside is drawn in stipple only where your headlights reach. Skunk cabbage sits in the ditch, sword ferns line both verges, Douglas fir and red cedar trunks stand behind them, moss-hung limbs reach over the road, a post-and-rail fence runs along some stretches, and the road has edge lines, centre dashes and puddles. The low beams light the road ahead and the near verges. A spotlight you steer with the pointer, a finger or the arrow keys draws the rest of the forest wherever it goes. Salamanders, newts and the odd frog are out on the road ahead, crossing it, and snakes lie along its edge. Their eyes glint in the headlights: faint in the low beams and just past the spotlight's rim, brightest once the spotlight is on them. That glint (a salamander's or frog's eyes catching the light) is the tell real herpers look for. Tap one that's lit, or press Enter, and the car stops: the reveal card shows the common and scientific name, a CC photo and a fact, and "Keep driving" sets off again. The field journal (localStorage) tracks how many of the 20 species you've found. It's the night twin of the tide pooling flip-a-rock game, with the same reveal card and journal.

A visitor downloads only their theme's, imported with `?url` so it gets a hashed `/_astro/` address and the year-long cache. `staticwebapp.config.json` serves `.bin` as `application/octet-stream`.
- [src/lib/hobbies/herping-species.ts](../src/lib/hobbies/herping-species.ts), the 20-species PNW roster, salamander-forward (12 of the 20 are salamanders or newts) and led by the animals I've logged, each with a `category` (the outline it's stippled from), `color` (how densely), `size`, `rarity`, `eyeshine` colour and two or three facts.
- [src/lib/hobbies/herping-photos.json](../src/lib/hobbies/herping-photos.json), the CC-licensed reveal photos. If one fails to load, the card shows the animal stippled instead.

**How the roadside is drawn.** Each plant and tree is a prop, cut out of a public-domain or CC0 photo from Wikimedia Commons and stippled by the same pipeline and pen as the hobby card plates: the `herping-drive` entry in the stipple-plates skill's `subjects.json` (`"kind": "drive"`), where each prop's `credit` gives its author, licence and page. My own photos stay on the hobby cards; a toy's background gets the clearest free photos there are. The props:

- A sword fern by Steve Redman at Mount Rainier (NPS, public domain), cut out by colour (`"mask": "green"`), since rembg sees ferns and forest litter as one texture.
- Skunk cabbage by Martin Bravenboer (public domain), in the ditch at the road's edge.
- A Douglas fir trunk by Yog Sot (CC0), with a forester's paint band covered by bark grafted from higher up the trunk and the trunk stretched 1.5x tall, and a western red cedar from the North Cascades NPS museum collection (public domain). Both are traced by hand.
- Moss-hung limbs from Entychologist's Quinault rain forest photo (CC0), cut out as the darkest part of the canopy (`"mask": "darkest"`) with ragged ends. They hang from 9.5 m and reach over the road from both sides, and don't clear paper behind them, so the trunks show through.

Each is drawn at 48, 96, 192 and 384 px tall (trunks at 768 too), so the dots stay the pen's size whether it's 60 m ahead or beside the car, with a silhouette for clearing paper behind it. To redraw them: `$PY .github/skills/stipple-plates/scripts/stipple.py herping-drive`, which writes both `.bin` files here and a review sheet; `review.py masks herping-drive` shows each cutout. The road marks (gravel, edge lines, dashes, puddles) and the fence's posts and rails are drawn in code in the same pen.

**How the drive works.** The road is a straight lane 6.4 m wide seen from a car's driver seat, built in 20 m stretches from a seed, so a stretch comes out the same every time it's built, and "New road" changes the seed. Each frame, everything within 95 m is projected: road marks first, then props, fence posts and animals from furthest to nearest. Each prop clears a ring of paper the shape of its silhouette before its dots go down, so nearer things hide what's behind them. The number of dots kept for anything shrinks with distance (`keepShare`), so far-off ferns don't turn into solid grey.

**How the lighting works.** Every dot has a fixed rank between 0 and 1, and a dot shows when the light on it is above its rank. So light thins a drawing dot by dot rather than fading it, and there are no gradients, glows or alpha. The light is the larger of two parts ([herping-drive.ts](../src/lib/hobbies/herping-drive.ts)):

- The low beams, fixed: full on the road and verges ahead, a cone that widens with distance and reaches higher up the trunks further away, gone by about 60 m.
- The spotlight, which follows the pointer: an ellipse on screen, full strength inside and soft over its outer half, carrying about 90 m.

Animals take their light from the same functions, and a ring of paper is cleared round each one so it reads against the road. Every outline dot of an animal shows once a third of the light is on it, and enough of its inside to make a small animal a solid shape, so one far up the road reads as an animal and not a few specks. Animals further off are also drawn larger than the road would make them, up to 1.7x from 26 m out. The eyes are cleared, then drawn side by side as two solid dots whose size and strength follow `eyeshine()`. Snakes lie at the road's edge and barely move; they're about one animal in seven. Rain is short dotted streaks, seen only where the light catches them. The dots go to the GPU through the WebGL sink the hobby card scenes use ([scenes/gl.ts](../src/lib/scenes/gl.ts)). Where WebGL2 isn't available, or would run in software, they're stamped into a pixel buffer at 1x and put on a 2D canvas once a frame, since filling a path of tens of thousands of tiny shapes made the browser rasterize each one. Measured on Windows Edge with an integrated GPU, moving the spotlight the whole time: about 10 ms a frame on WebGL at 1440 and 8 ms on a phone, and 24 ms and 11 ms on the fallback.

**The animals.** Each kind (salamander, newt, frog, toad, lizard, snake) is an outline of tapered capsules, top down, stippled once at 64 px on a jittered grid: every dot along the outline and more inside the darker the species prints in the theme's ink. They're drawn about twice life size so you can make one out from the car (larger still further off), lie on the road in its perspective and crawl across it slowly. New ones turn up 50 to 75 m ahead, and the car closes on them.

**Salamander-forward on purpose.** The game is about finding salamanders on a wet night, so a `CATEGORY_WEIGHT` table biases spawning heavily toward caudates (salamander 10, newt 7, snake 5, frog/toad 2, lizard 1.2), multiplied by each species' rarity weight. So the road is mostly salamanders, with a garter snake at the edge about one animal in seven and the occasional frog, and the ~20-species journal fills salamander-first. Snakes were rarer until I asked for "somewhat more common snakes on side of road" (2026-11-15).

**Where the species and facts come from.** Hand-picked PNW herps you'd actually meet cruising a rainy road west of the Cascades, led by the salamanders I've logged on iNaturalist (ensatina, western red-backed, Dunn's, northwestern, rough-skinned newt, Pacific giant), plus more PNW caudates (Cope's giant, Cascade torrent, Van Dyke's, clouded, western tiger, long-toed). Facts are curated from standard references and are meant to be interesting, not authoritative. A second check in October 2026 corrected the chorus frog's color change (it takes weeks, not minutes), the western tiger salamander's size and the rubber boa's lifespan, and dropped two claims only documented for related species (Cope's giant barking, Van Dyke's sticky slime). Names are sentence case, as everywhere on the site; 15 of the 20 were Title Case until November 2026. The American bullfrog is flagged `nonNative`, and its card reads "Non-native" where others read "New to your journal" or "Found again".

**Real photos.** Same pattern as tide pooling, picked by eye with [scripts/reveal-photos.mjs](../scripts/reveal-photos.mjs) (`herping candidates`, then `herping pick`). Until November 2026 [scripts/fetch-herping-photos.mjs](../scripts/fetch-herping-photos.mjs) took each species' iNaturalist default photo, and nobody looked: the Dunn's salamander was a sliver beside a rock and the ensatina a blurry shot of someone's hand. All 20 were picked again from about 50 licensed candidates each, sharp and of the whole animal, with no hands in them (the page asks people never to handle salamanders). Where a photo could show what the card's fact says, it does: the red under the red-legged frog's legs, the red flecks on the common garter snake, the blotched eastern Washington form of the tiger salamander, and a rough-skinned newt crossing a wet road. The older script still does `--wire blob`, for self-hosted `hobby-media` copies. Attribution travels with each photo and is shown in the card.

**Snappy reveals (photo preloading).** So the reveal card feels instant, the engine preloads every species photo in the background once the island mounts (on `requestIdleCallback`, so it never competes with the initial page load). By the time you find your first animal the image is already in the browser cache, so the card shows a real photo with no per-reveal network round-trip. That and the right-sized `medium` images are why reveals are immediate rather than waiting on iNaturalist's CDN. The 1024 px copy the card swaps to is fetched only for the animal on the card. (The site itself is served from Azure Static Web Apps' global CDN. Only these CC photos come from iNaturalist, and preloading hides that hop. To drop the third-party dependency entirely, `--wire blob` serves your own copies from the `hobby-media` blob instead.)

Like the other islands, the loop pauses offscreen and when the tab is hidden, and it honors `prefers-reduced-motion`: the car stays parked, nothing crawls, there's no rain or flicker, a found animal is replaced at once, and the beam jumps to where it's aimed instead of easing. Then the canvas only draws when something changes, so a still drive costs nothing.

**From the keyboard**, the road takes focus as one stop: the arrow keys steer the beam in all four directions, and Enter or Space stops for the unfound animal nearest the middle of the spotlight, or failing that the one whose eyes shine brightest (or says "Nothing in the beam yet." through a polite live region).

**A first find hops into the journal**, the same hop as tide pooling's ([journal-hop.ts](../src/lib/hobbies/journal-hop.ts)). The find is logged and "Last find" changes as the card opens, and the count waits. When "Keep driving" closes the card, a copy of the animal, stippled as it lay in the spotlight, hops from where it is on the road up to the count and goes to solid ink as it comes down, and the count rolls as it lands. "Found again" doesn't hop. On a phone with the count scrolled off the top, it hops off the top edge, and under reduced motion the count changes as the card opens.

## Reference implementation: Narrow nature (daily puzzle)

A daily puzzle that asks you to read a community rather than a single organism. Six species were
all recorded at one real place in one month. They're revealed the most widespread first: the
opening line gets you to the right part of the world, each one after it is more local, and the last
one is often local enough to name the valley. The visitor drops a pin on a world map, picks a
month, and scores on distance, month accuracy, and how few species they needed.

This is the inverse of a "what is this organism" quiz. One species gives you a range; an assemblage
gives you a point, which is how field ecologists actually read a habitat (indicator species).

There are two modes on one board. Today's list is the same round for everyone, picked by date.
More lists deals up to ten more a day per browser, from a separate set of places.

### How the page reads

People who tried the first version couldn't tell what the game was. It had three explanations with
three different metaphors, and the cost of each extra species was never shown. The page now leads
with the rules and uses one set of words throughout:

- **Premise, then steps.** The hobby `intro` is the premise in one line ("Six species were all seen
  at the same place in the same month. Guess where and when."). Under it, "How to play" is four
  numbered steps in the largest body text on the page. They use the same words as the controls
  ("show the next one", "tap the map", "Lock it in") and say that there's only one guess.
- **The six species are the board.** Six squares, three to a row at every width, sit under a
  "Widespread → Local" rule. A shown species gets its photo, name, Latin name and how far from the
  place half its sightings are ("Half its sightings within 3,300 km of the spot", `reachLine`), so
  the numbers shrink across the row and show how much each one narrows. The next square is the
  button and says what it costs ("−600 points"), and the rest wait with their number. The photos are up to 360px across, so on a laptop the map sits below
  them. That's more than iNaturalist's 500px medium size holds on a sharp screen, so each photo
  also offers the 1024px large size (`photoSrcset`) and the browser picks whichever the screen
  needs. Preloads ask for the same size, so a reveal is still instant.
- **Photo credits are a closed footnote.** A photographer's name can give the place away, so
  credits aren't under the photos. They sit in a "Photo credits" `<details>` at the foot of the
  page, which lists only the photos on the board (`photoCredits`) and closes again whenever a new
  round loads. CC BY and CC BY-NC are still met, since the credit is on the same page as the photo.
- **The stakes stay on screen.** The guess panel opens with "Up to 6,000 points", the most a perfect
  guess can still score (`bestPossible`). It rolls down with each species you ask for (`rollTo`).
  The panel is under the map, usually off screen when you ask, so the price is also stamped in red
  on the corner of the species it bought (`stamp()` in [motion.ts](../src/lib/motion.ts)). It slams
  down, sits for half a second, then drifts down toward the points and fades. The species itself is
  dealt into its square: it slides in 10 to 18px from the square the next one sits in, turned a
  degree, and settles square over 230ms (`dealFrames` in
  [pin-drop.ts](../src/lib/hobbies/pin-drop.ts)). The stamp waits about 110ms (`DEAL_MS` less
  `STAMP_TOUCH_MS`, the moment a stamp touches the paper) so it lands as the card settles. Each fast
  press deals its own card and stamp. Under reduced motion the species appears in place and the
  stamp comes with it, as before. Once the answer is down,
  the verdict ("Spot on", "Not quite"...) is stamped in ink with the distance under it, and stays
  there with the result. It goes in the map corner farthest from your pin, the line and the place
  (`placeVerdict`), worked out before the camera moves and clear of the zoom buttons and the scale
  bar. A phone's map is short enough that sometimes no corner is clear: then the framing leaves a
  band for the stamp along the top or bottom, and when the answer spans so much of the world that
  the map can't move, the stamp slides along an edge to the clearest spot.
- **The result is a receipt.** "Lock it in" swaps the panel for the verdict, the place and where the
  points came from: Place (distance, and how many species were showing), Month, Total. On the
  daily list, "Copy result" copies it as text: "Narrow nature list 25, November 15", a square per
  species (a book for each one read), one for the distance and one for the month, the numbers,
  then `trumanbrown.com/hobbies/narrow-nature`. The list number is today's place in the daily set,
  so two people a time zone apart can tell they played the same list. On a phone the button says
  "Share result" and opens the share sheet with the same text. The full list
  with facts follows under the board, one written sentence per species (see the accuracy rules).
  `tidyFact` still guards the page against a fact taken straight from Wikipedia: it trims a
  bracketed Latin name or IPA pronunciation, shows only the first sentence, and shows no line for a
  fact under 15 characters or cut off with "...". A species with no fact shows no fact line.
- **The answer lands in one beat.** The map glides to frame the pin and the place together
  (`CAMERA_MS`, 650ms, no closer than 48x). Over its last 80ms the pin presses into the map, a
  fifth smaller with a heavier line. Then a dashed line runs from the pin to the nearest edge of
  the place over 600ms (`LINE_MS`), the same point the distance is measured to, while the pin comes
  back up over 130ms. The press fits inside the camera's and the line's time, so the reveal takes
  no longer, and it only changes how the pin is drawn, never where the camera frames. The "km off"
  figure and the total start counting with `rollTo` as soon as you lock in, and land as the line
  arrives and the boundary closes. The line goes the short way round, so a pin in Hawaii reaches
  Japan off one side of the map and back in the other, and the distance is written on it once it's
  long enough to carry a label. Then the boundary strokes in (`BOX_MS`, 300ms), the place name
  appears on the map, the verdict and the place fade into the panel over 200ms, and the species
  still hidden fill in 70ms apart. The panel holds them back until then, because it used to print
  the answer while the map was still moving. Under `prefers-reduced-motion`, and for
  a finished round restored on load, everything is drawn at once. After locking in, the map scrolls
  into view if it's off screen, so on a phone the line can be watched with the result right under
  it.
- **Native controls.** The months are radio inputs, so arrow keys and screen readers work with no
  extra code. The lock button stays outlined until there's a pin and a month, then turns ink. A pin
  drops on a tap that didn't move, so a scroll, pan or pinch that starts on the map never drops one.
- **The pin drops in.** A tap drops the pin from 18 to 24px above the spot, up to 3px to one side,
  under a steady pull, so it lands in 128 to 148ms. It squashes wide and flat for a frame as it
  hits, and a 1px ink ring spreads from its circle (6px) to 22px and fades over 300ms. There's
  only one pin: a tap somewhere else lifts the old one 8px as it fades over 140ms while the new
  one drops, and a pin re-aimed mid-fall lifts out from wherever it got to. Every tap leaves its
  own ring, so tapping around leaves a short trail. A tap within 8px of the pin moves it and rings
  without lifting it, so a double-tap to zoom doesn't throw the pin about. Arrow keys slide the
  pin with no drop, since a held arrow repeats about thirty times a second. The key that places
  the first pin drops it like a tap. The pin, its rings and anything lifting out are drawn on the
  map's canvas at their place on the globe, so they stay put if the map moves under them, and the
  map only keeps redrawing while one of them moves ([pin-drop.ts](../src/lib/hobbies/pin-drop.ts):
  `planDrop`, `dropPose`, `liftPose`, `ringPose`, `pressPose` and the `createPinMotion` driver).
  Under reduced motion the pin appears where you tap, with no ring and no press.
- **Keyboard and screen readers.** Revealing a species from the keyboard moves focus to the next
  square, and a polite live region reads out the new species and the new ceiling. Locking in moves
  focus to the result. A finished round restored on load doesn't move focus or replay anything.

The layout takes its structure from the daily game Originle (a guess card with the stakes on it, and
a reveal button that shows its cost) and redraws it in the archive's ink on paper.

### The map

The map is plate carrée, the projection the puzzle boundaries are published in, so a pin, a
boundary and the terrain line up with no reprojection. It's one canvas, drawn by
[day-list-map.ts](../src/lib/hobbies/day-list-map.ts), with the borders from
[day-list-borders.ts](../src/lib/hobbies/day-list-borders.ts) over the terrain.

**Zooming.** Zoom runs from the whole world (1x) to 64x, where a pixel is about a kilometre on a
laptop and the terrain is still sharp. All of these work:

| Input                      | Does                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Pinch (touch)              | Zooms around the fingers, and two fingers pan                                                                                                  |
| Double-tap or double-click | Zooms in 2x there (and drops the pin there, like any tap)                                                                                      |
| `+` and `−` buttons        | Zoom 2x, toward the pin if there is one                                                                                                        |
| Ctrl or ⌘ + scroll         | Zooms around the pointer. A trackpad pinch arrives this way, and Safari's as `gesture*` events                                                 |
| Plain scroll               | Scrolls the page. If the mouse was just moved onto the map, a "Hold Ctrl and scroll to zoom" hint shows for a moment, the way embedded maps do |
| Keys                       | `+`, `−` and `0` (whole world). Arrows move the pin, by less the further in you are; after the answer they pan instead                         |

On touch, one finger scrolls the page while the whole world is showing (`touch-action: pan-y`) and
pans the map once you've zoomed in (`touch-action: none`), the same deal as the herp map. A scale
bar shows from 1.5x, for the latitude in the middle of the view. "Whole world" zooms back out, and
after the answer "Back to your guess" reframes the pin and the place. On a phone the map runs edge
to edge.

**Terrain.** The tiles are Natural Earth's "Gray Earth with Shaded Relief, Hypsography, and Flat
Water" at 1:10m (21600 × 10800, public domain), cut by
[build-day-list-relief.mjs](../scripts/build-day-list-relief.mjs) into a six-level pyramid of
256px WebP tiles: about 2,900 files and 7.6 MB, committed under `public/day-list/relief/v1/`. Tiles
that would be all sea aren't written; the manifest says which exist and the map paints open water
itself. A tile is one grey channel: 0 is water and 48-255 is the land's relief and height shading.
The browser maps that grey through the page palette (`buildLut`), so one set of tiles serves light
and dark mode and follows the theme toggle. Light mode keeps the archive's tan sea and paper land
shaded toward ink. Dark mode turns it round, with a sea darker than the page under land lit a few
steps toward ink, because relief shaded down from near-black has nowhere to go.

The map loads the coarsest level first and keeps it underneath, so a zoom never shows a blank, then
sharpens with the level the zoom needs (and the one under it, which arrives four times faster).
Before any tile arrives, the coarse coastline from `src/lib/geo-land.json` stands in. About 100
decoded tiles are kept and the oldest are dropped. The tiles are same-origin on purpose: the map
reads their pixels to recolour them, which a tile from another origin would block without CORS.
`staticwebapp.config.json` serves them as immutable, so bump `VERSION` in the build script when
the tiles change.

```bash
npm run build:day-list-relief   # downloads ~46 MB to .cache/natural-earth once, then ~40 seconds
```

The free Azure Static Web Apps plan allows 15,000 files per deployment. The tiles are about 2,900
of them, and the photo variants (12,000+) move to Blob Storage before deploy, so there's room, but
another zoom level from a finer source would be about 8,000 more files.

**Borders.** Country and state borders are lines drawn over the tiles, from Natural Earth's 1:10m
boundary lines (v5.1.2, public domain).
[build-day-list-borders.mjs](../scripts/build-day-list-borders.mjs) joins Natural Earth's 53,000
fragments into about 8,700 lines and simplifies them into three levels of detail, each to within
half a pixel at the closest zoom it's drawn at. Level 0 is one file (52 KB gzipped) that loads with
the map. Levels 1 and 2 are cut into 60° and 30° cells, the largest 45 KB and 74 KB gzipped, and the
map loads only the cells in view, drawing the coarser level until they arrive. The files (about
920 KB in all) sit in `src/lib/hobbies/day-list-borders/` and load as Vite chunks, so they get
hashed names and the immutable caching `/_astro/` already has. A file groups its lines by kind and
zoom, each group one polyline-encoded string, so the map strokes a group in one go.

Country borders show at every zoom, with disputed and indefinite ones dashed. State lines stay off
at world view, then fade in country by country once that country's states average about 10 pixels
across. On a laptop-width map that's about 1.2x for the US, 2x for Mexico, 3.4x for Germany and 16x
for the UK's councils. Lines between regions, like France's regions as against its departments, go
by the size of the regions. Natural Earth's own `MIN_ZOOM` favours the big federations, which left
Mexico blank beside a fully drawn US, so the script works the zoom out from the state polygons
instead. It also drops the state lines Natural Earth draws across bays and straits, like Chesapeake
Bay, by testing both sides of each line against those polygons, which stop at the coast.

```bash
npm run build:day-list-borders   # downloads ~62 MB to .cache/natural-earth once, then ~10 seconds
```

The script overwrites its files and deletes only the ones it no longer makes. Deleting the whole
folder loses the dev server's watch on it, and the dev server keeps serving the old lines until it
restarts.

### More lists

**Ten a day, from their own places.** More lists deals from
[day-list-extra.json](../src/lib/hobbies/day-list-extra.json), 68 places that the daily rotation
never uses, so playing extras can't spoil a future daily list. The builder refuses to write if the
two sets share a place, and a test checks it too. The cap is ten a browser a day (`EXTRA_PER_DAY`):
the pool is finite, so without one a keen player would run through it in an afternoon and start
seeing repeats. The data is a dynamic import, so the daily page doesn't download it until More
lists is opened.

**What it remembers.** `localStorage` key `day-list-extra-v1` holds today's played places and
scores, every place this browser has ever started (`seen`), and the round in progress. A new list
is a place not yet seen. Once all 68 have been played it goes back to the one started longest ago.
The count resets at the date change; a list left half-played carries over as the next day's first.
Today's list (`day-list-v2`) now remembers a round in progress as well, so a reload can't wipe how
many species you've seen. Older saves from before that, which were only ever written at lock-in,
still read as finished.

**Where it shows.** The board's title is a pair of underline tabs, "Today's list" and "More lists"
(`initUnderlineTabs`, the Cult UI direction-aware-tabs port). The daily result offers "Play more
lists", and each extra result offers "Next list" until the tenth, which shows the day's total
instead. Extras have no share button, because the share string is about the daily list. A link to
`/hobbies/narrow-nature/#more-lists` opens straight onto More lists.

### Accuracy rules

The puzzle is aimed at people who know the species, so the builder is strict about provenance.

- **Locations are real iNaturalist places with published boundaries**, not arbitrary circles. Every
  query is anchored to a place id, and the reveal links to that place so a player can check it.
- **Scoring is against the boundary, not a centre point.** Madagascar is 1,500 km long; a pin on its
  north coast is a correct answer, and measuring to a centroid would call that a 700 km miss. A pin
  anywhere inside the bounding box scores as exact.
- **Every clue is a research-grade record** from that place in that month, with at least two local
  observations. A single record is too often a vagrant, an escape, or a misidentification.
- **Animals are preferred over plants.** A birder can picture a kookaburra and reason about where it
  lives; "Parry's Townsend-daisy" is a dead end for all but a handful of botanists. Animals sort
  ahead of plants inside every band, a round allows at most two botanical clues, and plants only go
  in the three widest bands (500 km and up), because the last lines are the ones that give the
  place away.
- **Species are labelled native, introduced or endemic for that place**, from iNaturalist's own
  establishment means. The Laughing Kookaburra on the Cradle Mountain list, for one, is introduced
  to Tasmania, and presenting it as a native indicator would be wrong. iNaturalist flags
  each record against every place that contains it, so one stray listing can mislabel a species: a
  user-made place called Mallards introduced, which tagged them introduced in the Danube Delta,
  Iceland and four other rounds. So the label goes with the majority of the place's own flagged
  records (175 native Mallard records in the Danube Delta against 3 introduced). An endemic label
  also has to hold worldwide: at least half the species' records anywhere must be flagged endemic.
  That drops island listings of a local subspecies, like Grey Wagtail on Madeira (2% worldwide),
  and keeps real endemics, which run from 66% (Red-necked Wallaby, introduced abroad) to 100%.
- **Facts are written by hand from Wikipedia** and ship with the article link so they can be
  checked. Each is one sentence of 12 to 25 words that leads with something about the animal, the
  site's rule for species facts. Until November 2026 the builder kept the first 230 characters of
  each Wikipedia summary, so the full list read like a scraped encyclopedia: taxonomy ("a member of
  the duck, goose, and swan family Anatidae"), facts cut off at "subspecies of P." and lines of
  "...". In the daily set 10 of 234 facts were empty or "..." and 136 ran over 25 words. All 368
  species were then written again from their Wikipedia articles, each checked against its article.
  Seven with no article of their own carry a fact that holds for their whole genus or a close
  relative, linked to that article, and a few links iNaturalist didn't have were added. Eleven
  species have nothing on Wikipedia but taxonomy, so they have no fact, and the file says why. The
  facts live in `day-list-facts.json`, and
  [day-list.test.ts](../src/lib/hobbies/day-list.test.ts) fails on a fact in either set that's
  empty without a reason, over 25 words, more than one sentence, taxonomy, cut off at "..." or an
  abbreviation, or joined with a dash. A species without a written fact gets the first sentence of
  its Wikipedia summary that isn't taxonomy, if that's 25 words or fewer, and the build lists it so
  one gets written. iNaturalist returns article URLs with raw spaces in the title, which do not
  resolve, so the builder normalises them.
- **Photos are openly licensed only.** The builder walks `default_photo` then `taxon_photos` until it
  finds an acceptable licence, because the best-known species often have an all-rights-reserved lead
  image. The photographer and licence travel with the photo and are rendered under it on the
  board, since CC BY and CC BY-NC require attribution.
- **Clue order uses reach, not record counts.** A species' reach is the distance from the place
  that holds half of its research-grade records worldwide. The builder counts every candidate's
  records inside 17 rings around the place, 25 to 6,400 km and about √2 apart, with one
  `species_counts` call per ring, and reads the halfway point between rings on a log scale
  (`reachFrom`). Each of the six comes from its own band of reach: 1,500 km and up, 900, 500, 250,
  100, and under 100. The card rounds the reach up to two figures, so "half within" stays true.
  iNaturalist's records are heaviest in the US, Europe and South Africa, so a reach measures where a
  species gets recorded, not its range: from the Serengeti, a lion reaches about 2,000 km and a
  zebra about 2,300, because so many of their records come from South Africa.
- **The opener belongs to this part of the world.** Inside a band, species with at least 80% of
  their records within 4,500 km of the place go first, then animals, then ones the set hasn't used
  yet, then ones with a common name, then the best known. Until November 2026 the order came from
  worldwide record counts, and the opener had to have 120,000 of them so the puzzle wouldn't start
  half-solved. A count says how often a species is recorded, not where, so Hokkaido opened on
  Mallard, Common merganser, Reed bunting and Pine grosbeak, four birds that rule out nothing, and
  people had no chance before the fifth. The 4,500 km test keeps them out: from Olympic National
  Park 58% of Mallard records are that close, against 99% of American robins. At 3,200 km the
  robin failed too, since Olympic sits in a corner of the continent, and the Mallard came back as
  the opener. When nothing in a band passes, the band takes the species with most of its records
  nearby, never the most recorded.
- **A band with nothing in it** takes the nearest fit from what's left, measured on a log scale
  from a target inside the band, so the steps stay as even as the place allows. Iceland in June has
  nothing under 900 km but plants and one dolphin, and plants only go in the wide bands, so its
  ladder runs Eurasian blackbird 2,586, then a whelk, a puffin and a goose at 1,670 to 1,830, the
  great skua at 1,096 and the white-beaked dolphin at 265 km. A round never drops out over a short
  band, since dropping a daily round moves everyone's today. The build notes any round whose first
  species reaches under 900 km, since that one would start close to solved. None does yet, but
  remote islands narrow in one jump: Haleakala opens on the convergent lady beetle, a North American
  beetle brought to Hawaii, and its second line, at 191 km, already points at Hawaii.

**Rebuilding the puzzles.**

```bash
npm run build:day-list                       # daily set
npm run build:day-list -- --extra            # More lists set
npm run build:day-list -- --retag [--extra]  # refresh the labels only, same species
npm run build:day-list -- --facts [--extra]  # refresh the facts and links only, same species
```

A full build takes around an hour per set: the script throttles to one request a second, and it
tries up to eight candidates per band so a species without a usable photo costs a request rather
than a whole round. Measuring reach costs 20 requests a place (the place, its species, their
worldwide counts and the 17 rings), and those counts are cached in `.cache/day-list/` for a week,
so a rebuild to retune the bands only pays for photos and labels. Failed calls retry with a
widening pause, because a build is well over a thousand requests and a dropped socket is a matter
of when rather than if. It refuses to write a set with fewer than ten rounds. Rebuilding the daily
set changes the rounds people are partway through, so do it near midnight. A daily place marked
`hold: true` is skipped: the four the old 120,000-record rule left out (Sinharaja, Kinabalu,
Crocker Range, Komodo) would build now, and a new daily round moves everyone's today, so they join
in a rebuild that ships close to midnight. The five More lists places that rule left out (Yasuní,
Bwindi, Taman Negara, Bako and the Daintree) went straight in, since a More list is dealt at random
and nobody's today depends on the set's size. `--retag` keeps every round's species and only
relabels native, introduced and endemic, so it's safe to run any time (about ten minutes for both
sets). `--facts` does the same for the facts and their links, from `day-list-facts.json`. After a
full build, write a fact for each species the build lists as missing, then run `--facts`.

**No runtime API calls.** Puzzle data ships as JSON, the terrain ships as same-origin tiles, and
photos load straight from the iNaturalist CDNs already allow-listed in `img-src`, so the island costs
nothing per play and keeps working if the API is down.

**Scoped styles.** The species squares, the result receipt and the full list are all
built by the script at runtime, so Astro's scoped styles never reach them. The component uses
`<style is:global>` with every selector namespaced under `dl-` instead.

## Photo galleries (`hobby-media`)

Any hobby can show a photo gallery, a hero image up top plus a thumbnail grid, each click opening the full-resolution original in the same PhotoSwipe lightbox the photography pages use. It's driven by the optional `media` field on the hobby (`hero` + `gallery`), with `mediaTitle` setting the heading (e.g. "My tank"). The render lives in [src/pages/hobbies/[slug].astro](../src/pages/hobbies/%5Bslug%5D.astro) and only appears when `media` is present.

**Where the photos live.** A dedicated `hobby-media` blob container (public read) holds them, separate from `originals/`. The photography prebuild scans `originals/` and turns every folder there into a photography session, so hobby photos must live elsewhere to stay off the photography side. The container is defined in [infra/modules/storage.bicep](../infra/modules/storage.bicep). The site's CSP already allows blob images, so nothing else needs changing to display them.

**Adding photos to a hobby:**

1. Drop full-res files in `staging/hobby-<slug>/` (e.g. `staging/hobby-aquarium-keeping/`).
2. Run the uploader:
   ```bash
   AZURE_STORAGE_ACCOUNT=<account> node scripts/upload-hobby-media.mjs <slug> [--hero <file>]
   ```
   For each photo it uploads a full-resolution blob (`full/…`, opened in the lightbox) and a smaller display JPEG (`display/…`, shown inline, max 1600px wide), reading orientation and true dimensions with `sharp`. It then writes the `media` block (hero + gallery) into `src/content/hobbies/<slug>.json`. The full-resolution files go through the private `incoming` container and are published by the next build, so their lightbox links work once that build has run.
3. Optionally add `caption` text in the JSON, then commit + push. The gallery goes live on the next build. A photo without a caption is announced as "Open full-resolution photo", so captions are what make the gallery describable to a screen reader.

Web-friendly originals (JPG/PNG/WebP) are published byte for byte as uploaded, with one exception: hobby photos are often taken at home, so the build removes any GPS position before they're public (metadata only, the image is untouched; [security.md](security.md#photo-locations)). HEIC/TIFF, which browsers can't show, become one full-size JPEG at quality 95 with full colour resolution, the same settings the photography build uses (HEIC needs `libheif` available to `sharp`). The `--hero` flag (or the first file alphabetically) chooses the large image at the top.

## A video of the real thing

A hobby can show one of my YouTube uploads at the top of its media section, in place of the hero photo. The aquarium page plays the 10-hour video of my tank this way. It's driven by the optional `video` block in the hobby JSON:

| Field | What it does |
|---|---|
| `youtubeId` | The 11-character id from the watch URL. |
| `title` | The player's accessible name. |
| `lengthSeconds` | The upload's length, so the start point stays inside it. |
| `linkText` | The link out to YouTube beside the section heading. |
| `caption` | An optional line under the heading (the aquarium lists who lives in the tank, from the video's description). |
| `moments` | `{ species, label, at }`: a species id from the toy, how its name reads in a sentence, and a second in the video where it's easy to see. |

How it behaves ([HobbyVideo.astro](../src/components/hobbies/HobbyVideo.astro), [hobby-video.ts](../src/lib/hobbies/hobby-video.ts)):

- Until the visitor scrolls near it, the box is the hero photo, linking to the video on YouTube (which is also all a visitor without JavaScript gets). Nothing loads from YouTube before then.
- Then an iframe from `www.youtube-nocookie.com` (YouTube's privacy-enhanced mode) replaces it, playing muted and looping, from the second of the video that matches the visitor's time of day (seconds since local midnight, wrapped to `lengthSeconds`). Browsers only autoplay muted video, so the visitor turns the sound on in the player.
- It pauses when it scrolls off screen or the tab is hidden, and carries on when it's back, unless the visitor paused it. With reduced motion it loads without autoplay, with sound, and waits for the play button.
- Any link with `data-video-at="<seconds>"` scrolls to the video and plays it from that second. The aquarium picker writes one per `moments` entry, under the hint: "A few of these live in my tank. See the honey gourami, ... in the video below."
- The page sends the player commands (`seekTo`, `playVideo`, `pauseVideo`) and reads its state over `postMessage`, the protocol YouTube's iframe API uses. That keeps YouTube's script off the page, so the CSP only needs `frame-src https://www.youtube-nocookie.com` ([security.md](security.md#the-csp-unpacked)). The /privacy/ page says what YouTube sees.
- The hero photo moves to the start of the thumbnail grid, so it still opens full size in the lightbox.

To find moments in a long upload, YouTube's scrub thumbnails (the `storyboards` spec in the watch page's player response) give a 320×180 frame every 10 seconds. They showed the tank video is 16 min 40 s of footage looped 36 times, so moments only had to be found once. Small fish need full-resolution frames: `yt-dlp -f 299 -g <url>` prints a direct 1080p stream URL that a local `<video>` page can seek through. The aquarium moments, checked on 1080p frames on 2026-10-25: honey gourami 220 s (front and centre), celestial pearl danios 660 s (several in front of the rock), pygmy cories 90 s (two on the gravel, middle), amano shrimp 300 s (on the rock, left of centre).

If the upload ever gets a copyright claim that turns off embedding (its music is from Minecraft), the box shows YouTube's error and the link beside the heading still works. Swap in another upload or remove the block.

### iNaturalist observations embed

The tide pooling page ends with a live grid of the tide pool animals I've logged on iNaturalist, each linking out to its observation.

- **Component:** [src/components/hobbies/INatObservations.astro](../src/components/hobbies/INatObservations.astro) + logic [src/lib/hobbies/inaturalist.ts](../src/lib/hobbies/inaturalist.ts), with the filter in [src/lib/hobbies/inat-query.ts](../src/lib/hobbies/inat-query.ts). Any hobby switches it on with an optional `inaturalist` block in its content JSON, and the block has to say which animals belong to the hobby (`taxa` is required):

  ```json
  "inaturalist": {
    "userId": "trumanbrown",
    "heading": "My tide pooling observations",
    "blurb": "...",
    "taxa": [{ "id": 47115, "name": "Molluscs (Mollusca)" }],
    "withoutTaxa": [{ "id": 47485, "name": "Land snails and slugs (Stylommatophora)" }],
    "withoutPlaces": [{ "id": 29310, "name": "La Cruz, Costa Rica: snorkeling at Islas Murciélago, Aug 2026" }],
    "maxRank": "order",
    "wildOnly": true
  }
  ```

  Each `id` is an iNaturalist taxon or place id, and `name` is only there so the file reads. Look ids up with `https://api.inaturalist.org/v1/taxa?q=<name>` and `https://api.inaturalist.org/v1/places/autocomplete?q=<name>`.

- **It's lazy and CSP-safe.** The grid shows skeleton tiles until the section scrolls near the viewport. Then a `fetch` to the public iNaturalist API fills in the 12 most recently observed, each linking to its observation. The script is an Astro-processed module, so it satisfies `script-src 'self'`.
- **"View all" opens the same set.** The page turns the filter into one query string at build time ([inat-query.ts](../src/lib/hobbies/inat-query.ts)). The grid's API call and the "View all on iNaturalist" link both start from it, so the link opens the same observations in the same order, newest observed first. Two things about iNaturalist's Explore page shaped it, both read from its source (`app/assets/javascripts/ang` in inaturalist/inaturalist):
  - Explore runs `parseInt` on `taxon_id`, so a comma list there shows only the first taxon (molluscs alone, 29 records). Several taxa go as `taxon_ids`, which the API reads the same way.
  - Explore drops parameters it doesn't know, and `not_id` is one of them, so a single observation can't be left out by id. Leave out its place with `not_in_place` instead.

  The link also adds `verifiable=any`, because Explore hides casual records unless told otherwise and the API doesn't, and `place_id=any`, because a signed-in visitor's preferred place would otherwise narrow it. [inat-query.test.ts](../src/lib/hobbies/inat-query.test.ts) keeps the link and the call in step.

- **Filtering to the hobby.** iNaturalist has no tide pooling filter, and a place can't stand in for one: its coast places (Pacific Northwest Coast, Salish Sea) take in Issaquah and Kittitas County, and land slugs turn up on beach days. So the taxa do the work, worldwide, because the grid covers every trip and not just the PNW:
  - `taxa`: molluscs, echinoderms, cnidarians, true crabs, hermit and porcelain crabs, barnacles, _Heptacarpus_ shrimp, rockweed isopods, bristle worms, ribbon worms, polyclad flatworms, peanut worms, sculpins, gunnels, pricklebacks, clingfish and midshipman. Sculpins means Cottidae and Psychrolutidae, not all of Cottoidei, which also holds greenlings and lingcod. Jellies and squid found at low tide stay in (Truman's call).
  - `withoutTaxa`: their land and freshwater relatives anywhere in the world: land snails and slugs, freshwater snails and nerites, freshwater mussels and clams, ghost crabs, land crabs, land hermit crabs, freshwater crabs, hydras, freshwater jellyfish and freshwater sculpins (_Cottus_).
  - `maxRank: "order"` (`hrank`) leaves out vague IDs like "Bivalves" or "Tectipleura", where a land snail can hide, and `wildOnly` leaves out aquarium animals.
  - `withoutPlaces`: La Cruz, Costa Rica, where five August 2026 records were snorkeling, not tide pooling. It's a standard iNaturalist place, so it won't be edited or deleted, and an id iNaturalist doesn't know is ignored rather than breaking the grid.
- **What it can't see.** The filter knows what an animal is and where it was, not how it was found. A snorkel trip or a crab from a pot could still show up, so look over the grid after a trip like that and leave its place out the same way.
- **Checked 2026-11-12.** The old filter (`iconic_taxa=Animalia,Mollusca,Actinopterygii`) took every animal on the account, so the grid opened on a Death Valley pupfish, then a centipede, apple snails and tilapia. The November 2026 review's list (molluscs, echinoderms, cnidarians, crabs, marine worms, sculpins) plus a Pacific coast place still let through 43 records: 28 land slugs and snails, 6 vague IDs (one a clam held next to a fishing rod), 5 jellies, 2 squid and 2 freshwater sculpins. The filter above returns 208 records, and every photo was looked at: tide pools, beaches, wading and dip nets in Washington, Oregon, Kauai, Guanacaste and Cape Cod. iNaturalist's Explore page, opened from the link, showed the same 208 and the same first 12.
- **CSP additions.** Showing this required allow-listing iNaturalist in [staticwebapp.config.json](../staticwebapp.config.json): the API host in `connect-src` (`https://api.inaturalist.org`) and the two photo CDNs in `img-src` (`https://static.inaturalist.org`, `https://inaturalist-open-data.s3.amazonaws.com`). Those are the only third-party hosts the hobbies section talks to, and they're documented in [docs/security.md](./security.md).

### Birding life list and spark bird

The birding page shows two things from my iNaturalist account, and unlike the observations grid above, the build fetches both and writes them into the page, so they arrive with the HTML and the hourly build keeps them fresh. The requests, paging and shaping live in [src/lib/hobbies/birding-inat.ts](../src/lib/hobbies/birding-inat.ts), shared by the build and the browser. If iNaturalist doesn't answer the build, the build logs a warning and carries on, and the page fetches the same data in the browser once the section nears the viewport (same hosts as above, so no new allow-listing). There are no skeletons: while the browser fetches, the life list shows one line, "Loading my life list from iNaturalist...".

- **Life list.** [src/components/hobbies/BirdingLifeList.astro](../src/components/hobbies/BirdingLifeList.astro) + [src/lib/hobbies/birding-life-list.ts](../src/lib/hobbies/birding-life-list.ts). Switched on with an optional `lifeList` block:

  ```json
  "lifeList": {
    "userId": "trumanbrown",
    "url": "https://www.inaturalist.org/observations?user_id=trumanbrown&iconic_taxa=Aves",
    "heading": "My birding life list",
    "blurb": "…",
    "iconicTaxa": "Aves",
    "featured": 6
  }
  ```

  It pages `/observations/species_counts` until `total_results`, going by what each page returned. One page of 200 used to stop the list at 200 of 242 species, with the rarest bird I've logged among the missing (TTT-19 in the November 2026 review, and `birding-inat.test.ts` pages past 200). It sorts by the species' global iNaturalist `observations_count` (fewer records worldwide = more unique) and shows the `featured` rarest as cards (with a link to Wikipedia, but no quote from it: the summaries' first lines, "is a species of bird in the sparrow family", read as filler and were dropped in November 2026). It also pages my `/observations` to the end, by id, and shows each species' most-faved photo of mine, the newest on a tie, rather than a generic representative one. Ordered by faves, where nearly all of them tie at none, iNaturalist's pages overlapped and 14 of 467 observations never came back. A card's "My sighting" opens the observation its photo comes from, and so does a row for a species I've logged once. A row for one I've logged more than once opens the list of those sightings. The rest are grouped by taxonomic family (largest family first) into a compact list. "Rarity" here is global record count, not a formal conservation status. A count reads ×2 everywhere, on cards and rows.

  The markup is written once, in [src/lib/hobbies/birding-life-markup.ts](../src/lib/hobbies/birding-life-markup.ts): the build turns it into HTML, and the browser fallback turns the same description into elements, so the two can't drift. Search is a field with one rule under it, like the contact form, and sort is the site's underline tabs (By family, Recent, Name, Most seen, Rarest). Both move the rows already on the page rather than drawing them again. Each row's link has `content-visibility: auto` with its exact 81 px height: with all 242 rows in the HTML, every font swap used to lay all of them out, up to 230 ms a pass on a phone at 4x CPU.

  The family grouping needs no extra API calls: `species_counts` already returns each species' `ancestor_ids`, and [src/lib/hobbies/bird-families.json](../src/lib/hobbies/bird-families.json) maps every iNaturalist bird-family taxon id to its name, so the grouping is worked out wherever the list is drawn. Regenerate that file with `node scripts/fetch-bird-families.mjs` if iNat ever adds or renames a family.

- **Spark bird.** [src/components/hobbies/BirdingSpark.astro](../src/components/hobbies/BirdingSpark.astro) + [src/lib/hobbies/birding-spark.ts](../src/lib/hobbies/birding-spark.ts). Switched on with an optional `spark` block:

  ```json
  "spark": {
    "userId": "trumanbrown",
    "taxonId": 4838,
    "heading": "My spark bird",
    "species": "Black oystercatcher",
    "scientificName": "Haematopus bachmani",
    "story": ["First paragraph…", "Second paragraph…"]
  }
  ```

  The written `story` never depends on the network. The build fetches my most recent observation of `taxonId` with a photo, and Astro cuts the original photo into square WebP copies at 360, 720 and 1080 px, which go to Blob with the other page variants. It's the first-screen picture on phones and desktops, so it loads eagerly with `fetchpriority="high"`. It used to be a 240 KB iNaturalist JPEG that a script fetched after the page loaded, and the page's phone LCP was 2.8 to 3.7 s (4G, 4x CPU). Measured the same way on a build, it's about 1.7 s now. Astro downloads a remote photo after the pages render, and a failed first download fails the build, so the component checks the photo answers first and otherwise leaves it to the browser, which shows iNaturalist's 500 px copy. The two iNaturalist photo hosts are in `image.remotePatterns` in [astro.config.mjs](../astro.config.mjs).

### Herping reptiles & amphibians map (world → country/state, ink heat map + finds)

The herping page ends with a live, real geographic map of my reptile and amphibian observations: a world heat map you can drill from world → country (or the US → state) down to each find.

- **Coarse on purpose.** An unobscured iNaturalist observation is exact to metres, a reptile's spot is what a collector looks for, and a backyard observation would map the yard. So every coordinate is snapped to a 0.1° grid (about 11 km) before it's drawn, zoom stops at 6×, and places are cut down to a town or region ([src/lib/hobbies/inat-place.ts](../src/lib/hobbies/inat-place.ts)). The same place rule applies to the observations grid and the spark bird. For a site you'd rather keep vaguer still, set the observation's geoprivacy to Obscured on iNaturalist.

- **Component:** [src/components/hobbies/INatHerpMap.astro](../src/components/hobbies/INatHerpMap.astro) + logic [src/lib/hobbies/inat-herp-map.ts](../src/lib/hobbies/inat-herp-map.ts). Switched on with an optional `herpMap` block:

  ```json
  "herpMap": {
    "userId": "trumanbrown",
    "url": "https://www.inaturalist.org/observations?user_id=trumanbrown&iconic_taxa=Reptilia,Amphibia&subview=map",
    "heading": "My reptiles & amphibians, mapped",
    "blurb": "…",
    "limit": 300
  }
  ```

- **Real geography, still no map tiles.** All outlines are committed vector geometry, not tiles or a dependency, so the map keeps to the offline and CSP conventions. [scripts/build-herp-geo.mjs](../scripts/build-herp-geo.mjs) (`npm run build:herp-geo`) downloads two public-domain sources once (a US-states GeoJSON and Natural Earth 110m admin_0 countries), simplifies each outline with Douglas-Peucker (states finely, countries coarsely for world scale), and writes lon/lat rings and a bbox per state and per country (keyed by ISO A2) to [src/lib/hobbies/herp-geo.json](../src/lib/hobbies/herp-geo.json) (~150KB). The runtime projects those rings (equirectangular, cosine-corrected for latitude) onto a `<canvas>`, and only the iNat API and the already allow-listed photo CDNs are contacted at runtime.
- **Drawn in the page's ink and paper.** The map reads `--paper`, `--band`, `--ink`, `--ink-2` and `--rule` off `<html>` and redraws when the theme toggle flips them, so dark mode is the same map in the dark tokens. Water is paper, land is band with a 1px rule for each border, and the finds are a heat map in flat tints of ink: each find adds a soft bump of density, worked out at the screen's own pixels, and the density is cut into four bands at 14%, 28%, 48% and 72% ink (`HEAT_BANDS`). A density of 1 is one find on that spot, so a lone find is a pale patch with a slightly deeper middle, and the two darkest bands take several finds stacked up. The band edges are hard, eased only enough not to stair-step, so the patches print like a range map in a field guide and don't glow in dark mode, and nothing is inked more than about two sigma from a find ([inat-herp-map.ts](../src/lib/hobbies/inat-herp-map.ts) `heatBands`, tested in `inat-herp-map.test.ts`). The review's mock drew this heat as stipple, and the scattered dots read as sightings where there were none, so it went back to a heat map in the page's own ink (2026-11-12). Labels are Libre Franklin 400 on a rim of paper, drawn once the font has loaded ([canvas-font.ts](../src/lib/canvas-font.ts)). There's no navy, no Tailwind amber or sky and no glow; the November 2026 review called the old dashboard look out (TTT-1).
- **Three zoom levels.**
  - **World** (default): every country, and the heat. Patches are named, biggest first, after the places that hold 80% of their finds: "Costa Rica", "Washington and Oregon", "Arizona and California", or the country when it takes three or more (`nameClusters`). The points are the grid-snapped ones, never the raw coordinates. Tap a shaded spot to zoom, and hovering a country with finds rules its outline in ink-2. A tap on the patch counts as well as a tap on the land, out to three sigma and 10px past each find, so a patch that spills past a coarse outline into the sea still opens its place (`placeAt`).
  - **US states**: tapping the US opens the lower 48 (state outlines and a Hawaii inset) with the same heat and labels; tap a state to zoom. (Other countries skip straight to their own level.)
  - **Country / state**: the place among its neighbours, its outline ruled in ink-2 and its name in tracked capitals in the corner. All the heat stays, so it's true past the border, and each of this place's finds gets a mark on a rim of paper, a dot for a reptile and a ring for an amphibian, with a legend. A "← Back" button walks the levels back up.
- **How regions are assigned.** Each observation is bucketed to a country by point-in-polygon of its exact coordinates (in memory only, before snapping) against the baked country rings (with a US fallback when a US state matched), and to a US state via its `place_ids` intersected with iNaturalist's known state place ids (admin_level 10, for example `46` for Washington). Point-in-polygon also drives the map click + hover tooltips.
- **Grid with real info before you leave.** Below the map, the selected region's observations render as cards showing the common name, scientific name, observed date, and town or region, with an "approx." tag when iNaturalist obscured the coordinates (many sensitive herps are). Each card links out to its iNaturalist observation.
- **Reptiles vs. amphibians.** Two API calls (`iconic_taxa=Reptilia` and `=Amphibia`) back an All / Reptiles / Amphibians toggle that re-filters the heat, marks, labels and grid at every level. It's lazy (fetches on scroll), CSP-safe, and degrades gracefully if the API is unavailable. The land is drawn straight away, so the frame has its size while "Loading my finds from iNaturalist..." shows under it.
- **One line under the map** says what a tap does at this level, then how to move around, in the words for the device: "Pinch to zoom and drag to look around." on a touch screen, "Scroll to zoom, and drag or use the arrow keys to look around." with a mouse. The blurb above the map doesn't repeat it.
- **Zoom + pan (any level).** A `zoom`/`panX`/`panY` transform wraps each level's base projection so you can blow up tightly-clustered areas, up to 6× (further would only spread the grid out). It's driven by pinch on mobile, scroll-wheel on desktop, the + and − buttons, the keys, and drag-to-pan, with renders throttled through `requestAnimationFrame` for smooth gestures. The buttons are the site's square `.btn`, stacked in the corner on paper like Narrow nature's, 40px on a touch screen. On touch, the canvas's `touch-action` is `pan-y` at fit (so a one-finger drag still scrolls the page and a tap still selects) and flips to `none` once zoomed in (so one finger pans the map); two-finger pinch works in both. Zoom resets when you change level.
- **Keyboard and reduced motion.** The frame round the canvas is one Tab stop (`role="application"`, the keys in its label). While it has keyboard focus a ring marks what the keyboard is on, starting in the middle. The arrows move it by 5% of the width (20% with Shift): once zoomed in they pan the map under the ring, and whatever the map can't take, at its edges or at the whole-map view, moves the ring itself, so every place and the Hawaii inset can be reached. `+`/`=` and `-`/`_` zoom about the ring, `0` fits the level again, Enter or Space opens the place or find in the ring, and Escape steps back out. A polite live region says what's in the ring ("Costa Rica, 106 observations. Enter zooms in."). Moves from the keys and buttons ease over 260ms; with reduced motion they jump straight there.

### Trails I've walked (hiking)

The hiking page ends with my hikes from the photo archive: a card for each, newest first, with the place and the date, that opens its session.

- **Component:** [src/components/hobbies/TrailsWalked.astro](../src/components/hobbies/TrailsWalked.astro) + logic [src/lib/hobbies/hiking-trails.ts](../src/lib/hobbies/hiking-trails.ts) (tested in `hiking-trails.test.ts`). Switched on with an optional `trails` block that lists the sessions that were hikes, by slug:

  ```json
  "trails": {
    "heading": "Trails I've walked",
    "hikes": [
      { "session": "mt-baker-fall-2026" },
      { "session": "lijiang-may-2026", "photo": "DSC07937.JPEG" }
    ]
  }
  ```

- **Built from the sessions at build time.** Each card takes the session's title without its month, its date and a photo from the sessions collection, so nothing is fetched in the browser and the list of slugs is the only thing to keep up. The order in the JSON doesn't matter: the page sorts by the session's date, and the count beside the heading is the number of cards.
- **The photo is the session's cover**, the frame its card in the archive shows, unless `photo` names another file in that session. Session headers aren't used, because many of them are an animal (a marmot, an ice crawler, a crab). Tiger Leaping Gorge and Shannan and Shigatse name a photo, since their covers are rooftops and gulls.
- **A card is a session card:** the photo cropped to 4:3 on two sheets of paper, the place, and the date in tracked capitals. It uses the session card's widths (320 to 960) and formats, so a cover reuses the variant files the archive already has, and it loads lazily, since the section sits below the studio. A click opens the session with the same plain page change as a card in the archive (`data-open="session"`, [open.ts](../src/lib/open.ts)).
- **Miles and gain only as I give them.** A hike can carry `miles` and `gainFt`, shown as a second tracked line ("9.5 mi · 4,300 ft gain"). They're my numbers or nothing, never estimated from the photos or looked up on a trail site. None were given in November 2026, so none show.
- **Renamed or missing sessions.** A hike whose session isn't in the build is left out with one warning in the build log, so a fixture build still passes and a renamed session can't break a deploy. When a session is renamed or split, change its slug here in the same commit (the photo-sessions skill has the steps), and add a new hike by adding its slug.
